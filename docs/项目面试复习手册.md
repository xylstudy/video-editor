# 旅行 Vlog 多智能体视频编辑项目：面试复习手册

> 按 2026-09-21 仓库实现整理。目标是“能讲清楚、能落到代码、经得起追问”，不是把所有技术名词堆到一起。代码以后变动时，以实际代码为准。建议先背第 1、2、10、11 节，再按面试岗位复习专题。

## 1. 先统一项目定位和说法

### 1.1 一句话介绍

这是一个面向旅行 Vlog 的“参考视频结构迁移 + 用户素材自动成片”系统：先分析参考视频的镜头功能、节奏和情绪结构，再结合用户素材生成可编辑分镜，用户确认后渲染视频，并分别评估规划方案、Agent 执行过程和最终 MP4。

它既有 **React + FastAPI 的可交互产品链路**，也有 **LangGraph 多智能体引擎**。面试时先说清楚二者的接线方式：当前 Web 的可编辑生成链路采用分阶段脚本编排；独立 CLI 入口才调用 LangGraph 图。不要说“Web 每个任务都跑完整 LangGraph 图”。

### 1.2 60 秒口述版

> 我做的是旅行 Vlog 自动创作系统。前端提供项目、素材、任务和分镜确认界面，后端通过 FastAPI 管理任务状态，用进程内异步队列执行耗时的视频分析、规划和渲染，并通过 WebSocket 推送进度。核心是先从参考视频提取镜头时间轴、视觉语义和语音，结合用户素材生成 `VideoScheme`；这个方案既是规划的结构化输出，也是用户可编辑的分镜和渲染输入。独立 LangGraph 引擎侧还有 Supervisor + 7 个专职 Agent，并把参考结构抽象成 Gene、按需路由剪辑 Skill。Agent 工具层按角色注册 `name / description / inputSchema` 并实现参数校验，不过当前主流程主要直接调用专家方法，动态工具选择循环还未接入主链路。评测分三层：方案 Reviewer、成片技术与抽帧视觉检查、运行记录/产物完整性报告。工程难点是把不确定的模型输出收敛为可验证的数据与状态流，并在用户确认、异常降级和结果追溯之间维持一致性。

### 1.3 3 分钟版：按“问题—架构—难点—效果—局限”讲

1. **问题**：直接照搬参考片画面不可行；要迁移的是 Hook、镜头功能、节奏和情绪骨架，同时尊重用户素材和用户修改。
2. **架构**：Web 管理用户与任务；分析层提取参考结构和素材库存；规划层生成 `VideoScheme`；确认层让人改分镜；渲染层输出 MP4；评测层输出方案、成片和运行报告。独立 LangGraph 引擎把分析、素材、规划、渲染策略、补全、合成、审核拆成 Supervisor + 7 节点。
3. **难点**：模型决策不稳定，于是为工具层建立角色白名单和 JSON Schema 校验能力，用 `VideoScheme` 限定规划输出；异步长任务用数据库任务状态和实时进度；方案分镜在确认前可编辑，确认后重评；评测区分“方案看起来合理”和“实际 MP4 可播放/画面达标”。工具注册/动态派发能力与主流程的接线边界见第 5 节。
4. **结果**：已经形成从项目/素材、草案生成、人工确认、渲染到评测报告的代码链路，并有单测覆盖工具注册、Skill、时长归一、评测和部分 Web 隔离逻辑。**没有经过你自己记录的真实批量样本与人工标注时，不报成功率、提效百分比或商用并发能力。**
5. **局限**：Web 队列是单进程内存队列；Web 当前不直接调用 LangGraph 图；成片视觉评价基于抽帧而不是逐帧理解；MCP 是工具定义格式兼容，不是完整协议接入。

## 3. 全栈架构与任务状态：从点击到成片

### 3.1 端到端数据流

用户注册/登录 → 创建项目 → 上传参考视频和用户照片 → 创建 `end_to_end` 任务 → 后端读取当前用户的模型配置并复用/分析参考视频与素材 → 生成草案 `VideoScheme` → 任务变成 `awaiting_confirmation` → 用户在分镜编辑器修改镜头顺序、素材、时长、字幕、转场 → 后端校验并保存新版草案 → 用户确认 → 任务进入 `render` 阶段 → Remotion 渲染 → Reviewer 和成片检查 → 任务页展示结果和评测报告。

对应代码：[项目/素材路由](../web/backend/routers/projects.py)、[任务路由](../web/backend/routers/tasks.py)、[任务队列](../web/backend/queue_manager.py)、[任务流水线](../web/backend/pipeline_runner.py)、[分镜编辑器](../web/frontend/src/components/StoryboardEditor.jsx)、[任务详情](../web/frontend/src/pages/TaskDetail.jsx)。如果某个文件名变动，以 `web/backend/routers/` 下实际文件为准。

### 3.2 任务状态与“人工确认点”

`pending → running → awaiting_confirmation → pending → running → success/failed`。`awaiting_confirmation` 不是最终成功；对应评测报告里的 `ready_for_render`，批量最终成功率会排除待确认任务。任务数据库记录 `status`、`workflow_stage`、`draft_revision`、`scheme_path`、`result_path`、进度、日志；长任务的数据产物落磁盘，不把 MP4/BLOB 塞数据库。草案渲染前的人为确认是 **human-in-the-loop checkpoint**：既让用户掌控内容，又让昂贵的最终渲染只在方案确认后执行。

分镜 PUT 使用 `revision` 做冲突检测，旧版本返回 409；镜头数 1—200、单镜头 0.2—30 秒、总长最多 600 秒，还检查素材 ID、转场和字幕长度；先写 `.json.tmp` 再替换原 JSON。面试里应说“有版本冲突检测和原子文件替换”，**不要说已经实现数据库与文件的跨资源原子事务或严格 CAS**——当前读取、写文件和数据库提交仍有并发窗口。见 [任务路由](../web/backend/routers/tasks.py)。

### 3.3 异步队列、进度与 WebSocket

`TaskQueue` 是单进程内的 `asyncio.Queue`，一个 worker 顺序消费任务，另一 broadcaster 转发进度。执行阶段调用子进程并解析进度，再写数据库 `Task.progress/logs` 并推给任务 WebSocket。前端打开 `/api/tasks/{id}/ws` 接收状态/进度，仍可主动拉取任务状态。好处是 API 请求不必一直阻塞，坏处是进程重启可能丢排队消息、多实例之间不能共享队列、单 worker 限制吞吐。生产化方案：Redis/RabbitMQ + Celery/RQ/Arq 一类持久队列、幂等任务、心跳/租约、重试与死信、WS pub/sub、多实例恢复；这属于**下一步**，不是现状。

**安全边界**：常规 HTTP 任务/评测/分镜接口使用用户身份和归属校验，模型 API Key 加密存储且返回掩码；但当前 WebSocket 端点没有像 HTTP 路由那样做 token/任务归属校验，因此不能宣称“全部实时消息已完成鉴权”。面试被问到应主动说明待补：握手认证、归属验证、限制连接数和消息暴露范围。见 [HTTP/WS 路由](../web/backend/routers/tasks.py)、[认证](../web/backend/auth.py)、[密钥存储](../web/backend/secret_store.py)。

### 3.4 为什么不用一个同步接口一次性生成？

VLM 调用、转写和视频渲染都可能持续数十秒至数分钟；同步 HTTP 会遇到超时和糟糕的用户体验。拆任务后可以保存状态、观察进度、失败定位，并插入“编辑/确认”节点。**但 `async` 不等于无限并行**：当前 worker 数量、模型 API 限流、FFmpeg/Remotion 的 CPU/内存开销才是真正瓶颈。

### 3.5 前后端接口、数据库与安全追问

前端的 Axios 拦截器给普通 API 加 Bearer token，401 时清理登录状态；任务页通过 WebSocket 收进度，分镜编辑器调用 GET/PUT/确认接口。后端用 FastAPI 依赖注入取得当前用户、SQLModel/SQLite 管理用户/项目/素材/任务。`check_same_thread=False` 允许当前使用场景下跨线程访问连接，但不意味着 SQLite 已具备生产级高并发写入能力。长任务采用“DB 存索引/状态，文件系统存视频/JSON”的混合存储，需关注一致性和备份。

媒体 `<video>` 标签不能附带自定义 Authorization 头，当前前端把 token 放在媒体 URL 查询参数；它虽能播放受保护媒体，但 URL 可能出现在日志、浏览器历史或外链上下文中。加之 token 存 `localStorage`，还要考虑 XSS 暴露。改进可以是短时效、限资源的签名 URL 或同站点 HttpOnly Cookie，并配套 HTTPS、CSP 和 WS 握手鉴权。**这些是待优化方案，不是当前实现。**见 [前端 API](../web/frontend/src/api.js)、[前端 token 存储](../web/frontend/src/auth.js)、[数据库配置](../web/backend/database.py)、[媒体接口](../web/backend/media.py)。

### 3.6 通信方式梳理：HTTP REST、LLM 调用、SSE 与 WebSocket

先记住层级关系：**HTTP 和 WebSocket 是通信协议；REST 是基于 HTTP 设计接口的风格；“HTTP 非流式”是一次请求拿一次完整响应的使用方式；SSE 是构建在 HTTP 之上的服务端单向事件流。**不能把 REST、SSE、WebSocket 说成三个平级协议。

```text
HTTP 协议
  ├── REST API：用 URL 表示资源、用 GET/POST/PUT/PATCH/DELETE 表示操作
  ├── 普通非流式响应：请求一次，完整返回一次 JSON/文件
  └── SSE：Content-Type: text/event-stream，服务端持续单向推送事件

WebSocket 协议
  └── 建立长连接后，客户端与服务端可双向主动发送消息
```

本项目实际有三条不同的通信链路，不能混为一谈：

| 链路 | 当前方式 | 传递什么 | 为什么这样选 |
|---|---|---|---|
| 浏览器 ↔ Web 后端的业务操作 | HTTP REST | 登录、项目/素材 CRUD、创建任务、编辑/确认分镜、查询/下载结果、发送聊天消息 | 一次业务操作对应一次结果；便于鉴权、校验、状态码处理。 |
| Web 后端 → 浏览器的长任务进度 | WebSocket | `running`、阶段名、进度百分比、成功/失败状态 | 分析/规划/渲染耗时长，后端需要主动通知前端，避免前端高频轮询。当前主要是后端单向推送，前端仅发送 `ping` 保活。 |
| Agent/Web 后端 ↔ LLM Provider | 普通 HTTP 非流式 POST | 完整的聊天文本、Planner 方案 JSON、Reviewer 评分 JSON、路由决策 JSON | Agent 必须先拿到完整结构化结果，才能解析、校验、保存并进入下一阶段。 |

#### HTTP REST 是什么

REST 不是协议，而是 HTTP 接口的组织方式：URL 表示资源，HTTP Method 表示动作。例如 `GET /api/tasks/123` 查询任务，`POST /api/projects` 创建项目，`PUT /api/tasks/123/storyboard` 更新分镜，`PATCH /api/chat/sessions/1/context` 更新部分聊天上下文，`DELETE /api/tasks/123` 删除任务。前端通过 Axios 在请求头带 Bearer token，后端按用户身份和资源归属做校验。

#### 当前 LLM 输出究竟怎样返回

当前是：

```text
Planner / Reviewer / Chat 服务
  → httpx POST OpenAI-compatible /chat/completions
  → 等待模型生成完整内容
  ← 一次性取得 choices[0].message.content
  → 解析 JSON、执行校验或保存结果
```

因此，**LLM 的 token 没有通过 SSE 或 WebSocket 被逐个推送**。聊天页显示的“正在思考”只是前端等待 HTTP 响应时的 loading 状态；拿到完整回答后才渲染整段消息。对 Agent 而言，完整结果尤其重要：例如 Planner 必须拿到完整 `VideoScheme` JSON，才能检查镜头时长、素材 ID、转场等字段；Reviewer 也必须拿到完整评分 JSON 后才能决定是否重规划。见 [LLM 客户端](../viral-structure-engine/config/llm_client.py)、[聊天接口](../web/backend/routers/chat.py)、[聊天前端](../web/frontend/src/pages/Assistant.jsx)。

#### 为什么 Agent → LLM 不用 SSE

SSE 很适合将“模型正在逐字生成”的内容展示给用户，例如 ChatGPT 的文字流。Agent 内部却依赖完整的结构化结果：即使流式接收，也要等 JSON 完整后才能校验和执行下一步；流式 JSON 拼接、半截响应、断线恢复会增加复杂度，而当前没有等价收益。因此当前选择 HTTP 非流式。未来若要提升聊天页体验，可以保持 Agent 内部按完整 JSON 决策，同时仅把对用户可见的自然语言回答转为 SSE 逐 token 展示。

#### 为什么 Agent → LLM 不用 WebSocket

WebSocket 适合高频、长期、双向实时交流，例如语音对话、多人协作编辑、实时控制。当前 Agent 调用 LLM 是低频、阶段式的请求—响应：`“请生成方案” → “返回完整方案”`，没有必要维持一条长连接。改为 WebSocket 会额外带来心跳、断线重连、请求关联 ID、消息顺序、连接资源与多路复用等问题；并且当前模型服务采用 OpenAI-compatible HTTP API，本身就是 `POST /chat/completions` 形态。WebSocket 留给任务进度推送更合适。

#### 面试口述版

> 项目按通信对象拆分协议：前端的资源操作走 HTTP REST；长视频任务的实时阶段与进度由后端通过 WebSocket 推送；Agent 调用模型仍采用 OpenAI-compatible 的 HTTP 非流式请求。因为 Planner、Reviewer 等阶段必须先拿到完整的结构化 JSON，才能做 Schema/业务校验并推进工作流，所以当前不需要把模型 token 通过 SSE 或 WebSocket 流式传输。SSE 更适合后续给聊天助手做逐 token 展示，WebSocket 则用于需要后端主动实时通知的任务进度。

## 4. Agent 编排：图、状态、路由、失败

### 4.1 为什么是 Supervisor + 7 Agent，而不是一个大 Prompt？

职责边界更清楚：Analyst 负责参考片、Material Manager 理解素材、Planner 生成/迭代分镜、Renderer 决定渲染策略、Creative 处理素材缺口、Assembler 合成、Reviewer 审方案。Supervisor 负责根据阶段选下一位；节点通过共享 state 传递结构化产物。这样容易单测局部能力，也能给不同 Agent 限定工具，避免“任何角色都可以执行任何操作”。代价是编排更复杂、更多模型调用以及状态一致性问题；职责划分过细也会增加时延。**不是因为 Agent 越多效果越好**。

`build_graph()` 注册 1 个 Supervisor + 7 个专家节点，Supervisor 经条件边选择专家；专家返回 Supervisor 或结束。`ViralEngineState` 保存输入、参考结构/Gene、素材库存、方案、缺口、视频路径、Reviewer 结果、阶段、轮次、错误、日志等。它是**本次运行的工作记忆/共享状态**；历史项目知识、Gene 和 Skill 文件/库存是另外的持久化层，别混称为“无限长期记忆”。见 [图状态](../viral-structure-engine/graph/state.py)、[图构建](../viral-structure-engine/graph/builder.py)。

### 4.2 Supervisor 怎么避免乱跳？

`decide_next` 先看 `phase` 和已有产物做硬路由，阶段不明确时才让 LLM 在给定的专家列表中选择。既保留可扩展性，又减少每一步都依赖模型造成的随机性/成本。面试可用一句话总结：**确定性流程做主干，LLM 做有限决策与异常兜底**。见 [Supervisor](../viral-structure-engine/agents/supervisor.py)。

### 4.3 Reviewer 反馈为什么能形成闭环？

Reviewer 看参考结构、Gene、素材清单和方案，输出 `pass`、问题类别、修改建议。若未通过，且未达到 `max_iterations`，状态回到 `planning`，Planner 在原方案和反馈上修订。图默认最大迭代 3 次以控制时延/费用并防无限循环。当前代码还在 Hook 分低于 4 时直接结束；这更像保护/停止条件，并非“自动修好”，面试被深挖时应承认存在可优化空间（例如区分不可修复与需强制重规划）。**Reviewer 对方案的循环不是渲染后逐帧回炉再渲染**。见 [图构建](../viral-structure-engine/graph/builder.py)、[Reviewer](../viral-structure-engine/agents/reviewer.py)。

### 4.4 报错和降级在哪里？

参考视频场景切分失败会退为整段镜头；Whisper/语音提取失败会跳过 ASR，继续视觉分析；部分镜头 JSON 解析失败会重试/用默认结构，避免整条分析立刻中断。图引擎的 Assembler 在 Remotion 返回空值后尝试 FFmpeg 智能渲染，再尝试基础拼接。**注意异常并不保证全部回退**：当前 `assembler_node` 的外层异常分支会记录失败并离开，Web 的 `run_storyboard_render.py` 也只调用 Remotion。因此简历可写“引擎侧设计了多级渲染降级，分析侧有局部失败兜底”；不要写“Web 线上所有渲染异常都自动 FFmpeg 兜底”。见 [分析脚本](../viral-structure-engine/analyze_video.py)、[图合成节点](../viral-structure-engine/graph/builder.py)、[Web 确认后渲染](../viral-structure-engine/run_storyboard_render.py)。

## 5. Function Calling、Tool Scoping、MCP：必须分清三层

### 5.1 项目实际调用链

各 Agent 在初始化时通过 `register_tools` 注册自己的处理函数；`ToolDefinition.from_handler` 从带类型标注的函数签名生成 Pydantic 参数模型和 JSON Schema，公开 `name / description / inputSchema`。`BaseAgent.execute` **实现了**一个动态工具选择循环：将工具列表放进 prompt，要求模型输出 JSON 决策 `{thought, action, action_input, is_final}`；本地按工具白名单查找、校验 `action_input`（不允许额外字段）、执行 handler，并把结果写回步骤历史，默认最多 15 步。未知工具、校验失败和执行失败被记录为 observation。

**实际接线边界**：当前 `graph/builder.py` 和 `run_pipeline_e2e.py` 调用的是 `planner._generate_scheme`、`reviewer._review_scheme` 等专家方法；代码中没有主流程调用 `agent.execute()`。因此“有严格工具注册及动态派发基础设施”是事实，“主工作流由模型动态 Function Calling 调用全部工具”不是事实。见 [BaseAgent 与 ToolDefinition](../viral-structure-engine/agents/base.py)、[图节点](../viral-structure-engine/graph/builder.py)、[Web 规划脚本](../viral-structure-engine/run_pipeline_e2e.py)、[工具注册单测](../viral-structure-engine/tests/test_tool_registry.py)。

### 5.2 高频追问的标准答案

**问：你们实现 Function Calling 了吗？**

> 基类实现了“模型选择结构化 action → 本地派发工具”的机制，也为每个 Agent 注册了严格工具定义，但当前图/Web 主流程直接调用专家方法，**没有接入这个动态派发循环**；`LLMTools.chat` 使用 JSON 文本响应，也不是模型厂商 API 的原生 `tools/tool_calls`。简历里更严谨地写“为 Agent 建立按角色隔离的工具注册与参数校验机制”，不要写“所有 Agent 已通过原生 Function Calling 动态调工具”。若要接入，需将图节点改为调用 `execute()` 并处理结果，或增加原生 `tool_calls` 适配器并完成端到端测试。

**问：按 MCP 格式注册就是实现了 MCP 吗？**

> 不是。`name / description / inputSchema` 是 MCP Tool 定义可兼容的元数据形状；当前工具仍是同进程本地函数，没有 MCP Server、Client、传输层、`tools/list` 与 `tools/call` 协议交互。因此只能说“MCP Tool 定义兼容格式”，不能说“通过 MCP 协议接入外部工具”。要真正接 MCP，需要增加 Server/Client、能力发现、调用协议和鉴权/生命周期处理。

**问：Tool Scoping 能否完全防止危险调用？**

> 它把可见/可执行工具限制为当前 Agent 白名单，并用 Schema 拒绝非法参数，是一道应用层边界；不是完整沙箱。对文件路径、命令执行和外部副作用还需 handler 内做路径与权限校验。Schema 有结构保证，不保证语义正确，也挡不住被授权工具内部实现有漏洞。

**问：为什么工具签名里有类型标注？**

> 类型标注让 JSON Schema 自动生成，并在执行前做类型/必填字段校验，减少“模型凭空多给参数”或给错类型导致的隐蔽错误。可选字段由默认值表达；`*args/**kwargs` 在注册时被拒绝，因为无法形成严格契约。

## 6. Gene、Memory、Skill、知识沉淀

### 6.1 三者分工

| 概念 | 生命周期 | 在本项目里的东西 | 面试回答 |
|---|---|---|---|
| Working Memory | 单次执行 | `ViralEngineState` 中的结构、素材库存、当前 Scheme、Reviewer 反馈和阶段 | “Agent 之间共享的工作状态”，不等于持久记忆。 |
| Reference Gene | 跟参考视频关联，可复用 | Hook、镜头功能、节奏/情绪骨架、结构约束 | “迁移什么”；尽量内容无关、结构可迁移。 |
| Editing Skill | 跨任务复用 | Hook、节奏、转场、情绪、素材匹配、结构适配、字幕包装的剪辑策略 | “怎么剪”；按需注入而非全部塞 Prompt。 |
| 用户/项目知识 | 持久化 | 可复用知识条目、项目关联信息 | 对历史经验的保存；是否真正改善质量仍需对照实验。 |

优先级：**用户明确要求 > Gene 硬约束 > Skill 建议 > 模型自由发挥**。例如参考视频 Gene 的首镜功能必须是场景建立，即使 Hook Skill 通常推荐人物特写，也不能无条件覆盖 Gene。Gene 是“结构约束”，不是照搬参考素材；Skill 是策略，不是独立运行的 Agent。

### 6.2 Skill 具体怎么注入

在 **LangGraph 引擎路径**，`SkillRouter.route_for_gene` 根据 Gene 的 shot function 映射到相关 reference 文件；`collect` 只加载命中的 Markdown；Planner 把 Gene 文本、所选 Skill 上下文、素材库存等一起用于方案生成。`VideoScheme.skill_refs_used` 和每镜 `skill_refs` 记录用了哪些策略，Reviewer 记录对应引用，能做“策略 → 方案 → 评价”的关联追溯。规则主路由是**确定性的**，有可选 `route_by_llm` 兜底，**没有向量库/RAG，也没有证明 Skill 导致评分提升**。当前 **Web `run_pipeline_e2e.py` 没有调用 `SkillRouter`**：它读取预分析结构和最多 20 条用户个人知识并传给 Planner；虽然读取/打印了 `techniques` 摘要，但代码没有把该变量传入规划调用，不能据此声称 Web 的剪辑 Skill 已按需注入。见 [Skill 主文档](../viral-structure-engine/skills/video-editing/SKILL.md)、[Skill Router](../viral-structure-engine/skills/router.py)、[图状态注入](../viral-structure-engine/graph/builder.py)、[Web 规划脚本](../viral-structure-engine/run_pipeline_e2e.py)、[Scheme](../viral-structure-engine/models/scheme.py)。

### 6.3 追问：怎么证明沉淀有效？

目前 `skill_refs_used` 只是可追溯，不是因果证据。合理的实验是固定参考视频/用户素材/模型/温度，用同一批任务做有 Skill 与无 Skill 的 A/B，统计方案通过率、人工盲评、素材覆盖、重复镜头、成本/时长，控制评审模型的偏差；看分场景而非只看总平均。没有做这套实验之前，只能说“建立了知识注入与追溯机制”，不能说“显著提升成片质量”。

## 7. 多模态理解、结构规划、`VideoScheme`

### 7.1 从视频到结构，不把 ASR 说成画面理解

基础媒体信息/场景切分提供时间轴；每镜抽关键帧交给视觉模型分析主体、镜头语言、镜头功能等；Whisper 对提取出的音频做语音转写，给旁白/口播/字幕语义；音频节奏分析可补充 BPM/能量变化。最后结合镜头序列和文本总结 Hook、叙事、节奏和情绪结构。Whisper **只做语音转写**，不是由它单独识别 Hook 或情绪。场景切分是启发式，镜头时间轴不等于精确到每帧的剪辑语义；关键帧可能漏掉镜头内动作，故结果需容错和抽检。见 [分析脚本](../viral-structure-engine/analyze_video.py)、[Analyst](../viral-structure-engine/agents/analyst.py)、[音频工具](../viral-structure-engine/tools/audio_tools.py)。

### 7.2 为什么需要 `VideoScheme`？

把模型的自然语言规划变成可审、可改、可渲染的结构化中间表示（IR）。`VideoScheme` 包含标题、目标时长、镜头列表、素材关联、字幕/转场/情绪、包装、BGM、渲染提示，以及 Gene/Skill 引用；`StoryboardFrame` 把单镜时长、素材 ID、镜头功能、图层、效果等固定成字段。它降低 Planner/Renderer/前端之间的耦合：更换模型或渲染实现时，契约仍可保持；人工编辑后按同一 Scheme 渲染和重评。代价是 schema 演进、字段兼容和前后端验证要同步。

**面试高分回答**：`VideoScheme` 的价值不只是“存 JSON”，而是把“非确定性模型计划”变成“确定性接口与可审计产物”。一旦渲染失败或评分异常，可以定位到具体镜头、素材引用和技能来源。见 [Scheme 模型](../viral-structure-engine/models/scheme.py)、[Web 分镜接口](../web/backend/routers/tasks.py)。

### 7.3 时长、素材映射和工程约束

模型建议的镜头时长会按目标时长归一化，设置单镜最短值并修正最后一镜误差；Web 编辑时重新校验镜头/总时长。模型给的素材 ID 必须与库存映射，否则渲染找不到文件；前端只提交允许编辑的字段，后端再做材料归属与有效性校验。面试被问“模型输出错了怎么办”：先区分解析失败、Schema/业务校验失败、渲染失败，分别给重试、修复/拒绝、降级或失败报告，不能一句“Prompt 改一下”了事。见 [规划脚本](../viral-structure-engine/run_pipeline_e2e.py)、[Web 分镜接口](../web/backend/routers/tasks.py)。

### 7.4 Remotion 与 FFmpeg 为什么同时出现？

Remotion 基于 React 组件表达字幕、图层、动画和画面包装，适合结构化分镜的程序化渲染；FFmpeg 擅长媒体探测、裁切、转码、合成和技术校验，也可作为更基础的渲染路径。**当前 Web 确认后主渲染是 Remotion**；Graph Assembler 的 Remotion 空结果回退 FFmpeg 智能渲染/拼接，不能把两条路径混说。容错不是“质量必不下降”：回退通常牺牲部分转场/包装复杂度，目标是尽量产出可用视频，同时记录所走路径和失败原因。

## 8. Agent 与成片评测：三种对象，三套问题

| 对象 | 输入/时间点 | 主要关注 | 本项目实现 | 不能误说成 |
|---|---|---|---|---|
| 方案 Reviewer | 渲染前/确认后；Gene、参考结构、素材清单、Scheme | 结构保真 + 素材适配 | 10 个扁平分数：`structure_fidelity`、`hook_appeal`、`content_adaptation`、`rhythm`、`emotion_coherence`、`gap_filling_quality`、`packaging_consistency`、`completeness`、`subtitle_quality`、`material_coverage`；另有 Fidelity/Quality 子维度、通过标志和修改建议 | “看了最终视频的画质”。 |
| 成片检查 | 渲染后 MP4 + 确认 Scheme | 文件可解码、时长/音轨、疑似黑屏/静帧、视觉兑现程度 | FFprobe/FFmpeg 全片解码；OpenCV 采样技术诊断；按分镜最多抽 12 镜、每镜 3 帧给 VLM 评审，问题附秒级证据 | “逐帧审完所有视觉质量/音画同步”。 |
| 运行评测 | 本次运行的日志和产物 | 是否真的执行完、有无失败/mock、质量产物是否最新 | 阶段覆盖、方案/素材产物、错误、方案指纹、模型调用、MP4 有效性、目标时长和综合报告 | “单一 LLM 打分就是 Agent 成功率”。 |

方案 10 维见 [Reviewer Prompt](../viral-structure-engine/prompts/reviewer_prompts.py)；成片检查见 [Video Review](../viral-structure-engine/evaluation/video_review.py)；运行评测见 [Run Evaluator](../viral-structure-engine/evaluation/run_evaluator.py)；Web 最终评测的衔接见 [Web Run](../viral-structure-engine/evaluation/web_run.py)。

### 8.1 评测报告里的 `score` 和 `success` 怎么区分？

`score` 是一组检查项的加权通过率，用于诊断和比较；`success` 是阶段达到 `completed` 且所有关键项通过，包括运行元数据、阶段覆盖、结构化产物、无错误、方案 Reviewer 当前且通过、媒体可解码、目标时长和非 mock 模型执行等。**高分不等于成功**。成片视觉分目前作为诊断项，不是硬成功门槛，因为还没对人工标注数据做阈值校准；素材覆盖率 >=80% 也是诊断项，不是硬门槛。待确认阶段用 `ready_for_render`，批量最终成功率不把它计作已完成。完整解码和时长容差 `max(1 秒, 目标时长 10%)` 属于明确可复算的检查。

### 8.2 方案变了，旧 Reviewer 分数还能用吗？

不能直接用。保存方案指纹，确认分镜后重新运行 Reviewer；评测器将方案指纹与审核产物比对以识别“旧分数评价新分镜”。Web 确认后即使 Reviewer 不可用，已生成视频仍可交付，同时报告评测失败，而不是悄悄写“通过”。注意“方案指纹 + 重评”是当前实现；模型评分本身仍有主观性。见 [Web Run](../viral-structure-engine/evaluation/web_run.py)、[Run Evaluator](../viral-structure-engine/evaluation/run_evaluator.py)。

### 8.3 成片评测的可信边界

全片解码能证明视频流基本可读取，不能证明内容好看。黑屏/静帧是采样启发式，纯黑转场、刻意定格可能误报；短黑帧也可能漏报。VLM 看的是代表帧 + 镜头上下文，能检查画面与分镜的对应程度，但很难可靠判断完整动作流畅度、音画同步和所有字幕瞬间。当前音轨存在性可探测，`volumedetect` 使用的日志级别会抑制其统计输出，**不要宣称可靠静音检测已完成**。若被问怎样改：使用可解析的 FFmpeg 统计输出/音频能量窗口、做人工标注校准，并对抽样策略增加风险导向覆盖。

### 8.4 评测体系怎么继续做得更像生产级？

准备固定评测集（不同素材数量、转场、BGM、时长、模型失败样本），明确人工标注口径；对 LLM Judge 做盲评一致性/人评相关性；做阈值校准与误报/漏报分析；统计任务成功率、端到端耗时、各阶段 P95、token/成本、重试次数、人工修改次数、素材覆盖、失败归因；对 prompt/model/Skill/Gene 版本做实验分组。当前仓库有评测代码和部分 fixture/单测，但**没有从代码本身证明大规模真实用户实验、显著效果提升、持续线上监控**。

## 9. 高频深挖问答（按主题练，每题先用 30 秒答）

### 架构与全栈

1. **为什么要把参考结构和用户素材分析分开？** 输入不同、复用粒度不同。参考片 Gene 可由多个项目引用；用户素材库存随上传变化。分开能避免重复 VLM 调用，但复用前要比对源文件指纹，避免“旧结构配新视频”。
2. **任务重试会不会重复渲染或覆盖结果？** 现状以任务 ID 隔离目录并记录阶段，但内存队列没有生产级幂等/租约。应设计 idempotency key、状态 CAS、输出临时文件+完成标记、失败重试策略，尤其避免重复扣费和同时写同一 MP4。
3. **数据库放什么，文件系统放什么？** DB 放用户/项目/素材元数据、任务状态/路径/日志、配置；大型媒体、结构 JSON、Scheme、评测报告放任务目录。优点是查询与大文件分离；风险是 DB 与文件写入没有跨资源事务，需要校验/修复机制。
4. **WS 断线怎么办？** 实时消息是体验层，不应作为唯一事实来源。重连后 GET 任务状态/日志补齐；当前页面能拉任务详情。生产化应加事件序号/断点续传和广播 pub/sub。
5. **用户 A 能拿到用户 B 素材吗？** HTTP 路由用当前用户做项目/任务归属校验，任务存储按用户/项目/任务隔离；但 WS 仍需补握手鉴权，不能给“绝对安全”的回答。
6. **用户确认分镜时为什么不直接覆盖原模型结果？** 编辑的 Scheme 是渲染时的权威输入；保留版本号和评价指纹可知道评的是哪一版。更完整的方案是草案/确认版分离和审计历史；当前实现主要是当前草案 + revision，不是完整版本库。
7. **为什么前端也要管评测？** 用户不仅想知道“完成/失败”，还要看到失败项、Reviewer 分、技术诊断和秒级证据，才能决定编辑、重试还是接受结果。
8. **吞吐瓶颈在哪？** 单 worker 首先限制并发；模型响应、视频解码/渲染占时间与资源；带宽和临时磁盘也可能是瓶颈。先做分阶段耗时统计，再决定缓存、并发度和任务队列扩容，不凭感觉报 P95。

### Agent 与工具

9. **为什么 LangGraph？** 适合把阶段、条件路由、共享状态和回环表达成可检查的图；代价是状态 schema 和图循环需要严格管理。这里并非所有流程都必须 Agent：Web 为编辑确认采用更明确的分阶段脚本。
10. **Supervisor 和普通函数编排有什么区别？** 明确阶段走硬路由时等价于稳定状态机；状态不明确才让模型辅助选专家。这样保留灵活性但不把所有控制权交给模型。
11. **怎样避免无限循环？** `BaseAgent.execute` 基类设置最多 15 步（当前主流程未调用）；Review/Planner 迭代有 `max_iterations`；失败写 error/log，评测识别缺失阶段。还应增加全局 timeout/成本上限；当前不是完整预算调度器。
12. **Agent 之间传原始视频吗？** 主要传结构化分析产物、库存、Scheme、引用和路径；避免把原视频字节放 state/prompt。模型调用读取抽帧/文本等必要上下文。
13. **Function Calling 的 arguments 校验在哪层？** 在 `BaseAgent.execute` 动态派发分支里，工具执行前调用 `Pydantic model_validate`；业务语义还要 handler 内检查。不过当前主链路没有进入该分支，不能说所有主流程方法调用都经过该校验。LLM 返回合法 JSON 也不代表 action/素材 ID 真实存在。
14. **MCP 格式与 MCP 协议的最小差别？** 前者是 Tool 元数据；后者还包含 Client/Server、transport、能力发现/调用消息和生命周期。当前只有前者，而且动态派发尚未接入主链路。
15. **工具调用失败如何恢复？** Agent 的 observation 收到校验/执行失败，可以在后续步修正；达到步数上限后返回失败。关键业务节点还有异常处理；但不能保证所有故障自动修复。
16. **是否有真正的多 Agent 并行？** 当前 LangGraph 路径以 Supervisor 顺序调度为主，Web 单 worker 更不是并行 Agent 集群。不能说“七个 Agent 并行运行”。

### 多模态、规划、知识

17. **“爆款结构”为什么可迁移？** 把具体人/景/台词抽象为镜头功能、节奏、情绪与叙事位置，才有跨素材复用可能。评价应看结构保真与用户素材适配的平衡，而非像素相似。
18. **如何处理 VLM 幻觉？** 镜头时间戳由媒体工具给事实基础，提示词限定可见证据，解析结果落结构化字段；无法确认时保留不确定性，最终分镜允许人审。若声称“完全无幻觉”不可信。
19. **为什么不把全部 Skill 文档塞入 Prompt？** 增加 token 成本与相互冲突；按 Gene/阶段路由只加载当前相关片段，更容易追溯与单测。
20. **Skill 与 RAG 的区别？** Skill 是预定义的可执行/可遵循方法与条件路由；RAG 通常按查询检索外部知识。此项目的 Skill 是规则路由 Markdown，尚无 embedding/向量检索。
21. **Memory 真的长期记得用户偏好吗？** Graph state 是运行期工作记忆；用户/项目知识与 Gene 库可持久化，但是否自动长期学习、效果如何，需要看具体读写策略和实验，不能把所有存储都称作 Agent long-term memory。
22. **没有匹配素材怎么办？** 尝试按镜头功能找替代、调整表达方式、补文字卡/视觉策略，必要时标记缺口；核心是保留结构功能而非硬贴不相关画面。素材覆盖并非越高越好，强行使用全部素材会损害质量。
23. **为什么 `VideoScheme` 不是普通 prompt 输出？** 因为它是跨模型、前端、审核、渲染的契约；可验证/可编辑/可追溯，并将不确定性限制在明确字段内。

### 渲染与质量

24. **Remotion 与 FFmpeg 谁负责什么？** Remotion 做组件化视觉排版/动画主渲染，FFmpeg 做音视频处理、校验和图路径下的回退。两者不是同一层的重复实现。
25. **分镜总时长和 MP4 时长差异怎么查？** 先看 Scheme 时长归一与编辑后目标值，再查帧率取整、转场重叠、音轨/尾帧、Remotion composition 时长，最后用 FFprobe 核实并比对容差。
26. **如何避免坏视频被标为成功？** 不只检查文件存在：FFprobe 校验视频流/时长，FFmpeg 全流解码，运行报告的关键条件包含媒体有效和目标时长。仍需人工/视觉评价补创意质量。
27. **Reviewer 10 维是不是成片视频的 10 维质量？** 不是，是方案层对结构与适配的评价；真正 MP4 的画面证据在另一层 `video_review.py`。
28. **视觉 Reviewer 的证据为什么有秒数？** 把问题映射到抽帧时间窗，便于定位镜头和人工复核。秒级证据并不等于精确测得连续片段全部问题。
29. **方案 Reviewer 和成片 Reviewer 冲突怎么办？** 先确认是否评价同一版 Scheme；再区分计划问题还是执行问题。例如方案素材匹配好，但渲染时素材路径错误，归因渲染层；方案节奏本就不合理，归因规划层。二者不能取平均掩盖冲突。
30. **如何评估“好看”这种主观指标？** 拆解成有依据的子维度，保存人可复核证据，做人工盲评与评审一致性验证；当前 VLM 分只能作为辅助诊断，不能替代用户真实偏好。

### 工程可靠性与测试

31. **怎么控制模型成本？** 先复用已分析的参考 Gene/素材库存；LangGraph 路径按需加载 Skill、Supervisor 硬路由减少无谓调用；限制循环轮数；记录 token/请求数。进一步可做缓存键、并发限流和成本预算。没有真实账单/对照实验不要报节省百分比。
32. **模型供应商切换难在哪？** 当前 `LLMTools` 走 OpenAI-compatible chat completions，但不同供应商对 JSON 模式、视觉输入、响应结构/限流的兼容性不一致；需要适配层、回归用例和能力检测，不是只换 base URL。
33. **API Key 怎么保护？** 每用户模型配置的 Key 加密保存、界面只返回掩码，运行时解密注入该任务进程环境。要保护服务端加密密钥、限制日志输出、轮换/撤销并隔离用户。当前 `.local` 文件密钥适合本地部署，正式多实例要改为安全的集中式 secret 管理。
34. **哪些单测最有价值？** Tool Schema/非法参数、Skill 路由、Gene→Scheme 合同、时长归一、评测报告 critical gate、用户隔离、分镜编辑冲突、模型失败/mock。仓库已有 [引擎测试](../viral-structure-engine/tests/) 和 [Web 测试](../web/backend/tests/)，但真实渲染 E2E 还需固定媒体样本和外部依赖环境。
35. **怎样复现一次运行失败？** 用 `run_id` 找 `run_info`、各阶段 JSON、`agent_logs.jsonl`、确认 Scheme、评测报告；先定位阶段/错误，再确定输入指纹和模型配置版本，最后在隔离环境重跑该阶段。
36. **为什么不能只看单次 Demo？** 输入分布、模型波动、渲染机器资源都会变；需要固定评测集、重复运行、失败归因和版本化基线，否则“跑通一次”不等于稳定系统。

### 前后端与数据安全进阶

37. **React 与 FastAPI 的职责边界？** React 管界面状态、表单与交互反馈；FastAPI 是鉴权、业务校验、任务状态和文件归属的权威层。前端校验改善体验，但不能替代后端校验。
38. **为什么分镜保存返回 409 而不是最后写入者获胜？** 多标签页编辑时旧草案可能覆盖新草案；revision 可以提示用户先刷新。当前它不是数据库原子 CAS，严格并发场景应把比较和更新放在事务条件更新中，并协调文件替换。
39. **媒体播放为什么不用普通 Axios 请求？** 原生 `<video>` 不会自动附带 Axios 的 Bearer 头，项目使用 `?token=`；这带来 token 泄漏风险，生产改进可用短时签名 URL 或 HttpOnly Cookie。
40. **SQLite 能扛多少并发？** 不能只凭框架猜数字；SQLite 写锁和单进程队列适合本地/低并发场景。若要多 worker、更多并发写入和可靠任务恢复，考虑 PostgreSQL 与持久队列，并先跑负载测试。

## 10. 最容易被问穿的 12 个边界：请主动坦诚

1. **Agent 数量**：代码是 Supervisor + **7** 个专家节点，不要照 README 旧段落说 9 个正在图里执行。
2. **Web 与 LangGraph**：Web 的 `agent_pipeline` 名称不意味着它调用 `build_graph()`；它当前跑分析脚本 + `run_pipeline_e2e.py` 分阶段路径。LangGraph 图由独立 `main.py` 调用。
3. **Function Calling**：基类有结构化 action 工具派发机制，但**主流程未调用该循环**，也不是供应商原生 `tool_calls` API。
4. **MCP**：有兼容 `name / description / inputSchema` 的 Tool 描述，没有完整 MCP Client/Server/transport。
5. **Memory**：单次图状态是 Working Memory，不能统称长期记忆；持久知识是另一层。
6. **Skill**：LangGraph 路径按规则路由 Markdown；Web 路径尚未接入 SkillRouter。它不是向量 RAG；记录引用不等于证明提效。
7. **队列**：`asyncio.Queue` 不是 Celery、Redis 或分布式/持久队列。
8. **渲染降级**：图引擎有 Remotion 空结果后的 FFmpeg 路径；Web 确认后目前无自动 FFmpeg 回退。异常也可能绕过图路径回退。
9. **Reviewer 10 维**：它读分镜方案，不是直接看 MP4。
10. **成片视觉评分**：代表帧抽样，不能宣称逐帧审核或可靠检测音画同步/静音。
11. **成功率与提效**：评测框架有 `success_rate` 计算，不代表已经拿到可信的大样本成功率或生产 KPI。
12. **安全与并发**：HTTP 有归属校验，但 WS 鉴权、队列持久化、文件/DB 原子一致性仍可完善；不要说成生产级多租户高并发。

面试中承认边界不是减分，**把“现状—为什么这样设计—下一步怎么补”讲清楚，通常比夸大更可信**。

## 11. 五个“重点难点”的完整回答模板

### 难点 A：模型生成的分镜怎样可靠落地？

> 我没有让模型直接生成最终视频命令，而是先生成 `VideoScheme` 这样的结构化中间表示。它固定了镜头时长、素材 ID、字幕、转场、结构功能等字段；Planner、Web 编辑器、Reviewer 和 Renderer 都围绕同一契约工作。执行时先做 Schema 与业务约束校验、归一化时长，渲染后还要独立验证 MP4。这样模型可以负责创意决策，但不能绕过工程校验。最大挑战是版本一致性，所以确认版方案会重新审核，并用方案指纹标记评测对应哪一版。

### 难点 B：怎么把参考片风格迁移到不同用户素材？

> 我先把参考片的内容和形式拆开：内容是具体地点/人物，形式是 Hook、镜头功能、节奏比例和情绪曲线。Gene 保存参考片专属的结构功能；Planner 再按用户素材的语义和质量做匹配，素材不足时使用 Skill 给出的替代手法，而不是照搬画面。Reviewer 同时看结构保真和素材适配，防止“像参考片但不适合用户素材”或“用了素材却丢了节奏”。

### 难点 C：多 Agent 怎么可控？

> 控制分三层：图层通过状态阶段和条件边约束执行顺序/最大迭代；Agent 基类具备按角色注册工具白名单、输入 Schema 校验和步骤上限，但图节点目前直接调用专家方法，工具派发循环尚未接入主链路；运行层记录阶段日志、模型调用、错误和产物，最后由离线评测器检查完整性。Supervisor 优先按确定性规则调度，只把模糊决策交给模型。这样的目标不是消除模型的不确定性，而是让它的影响可观察、可回退、可定位。

### 难点 D：Web 如何承载长任务和人工确认？

> API 创建任务后快速返回任务 ID，单进程异步队列负责执行，数据库存储权威状态和进度，WebSocket 用于实时展示。草案生成后暂停到 `awaiting_confirmation`，用户可以修改 Scheme；后端做 revision 冲突检测和字段校验，确认后再入队渲染。这让耗时生成和用户交互分离，也避免不满意的方案直接消耗渲染资源。当前单进程队列适合本地/原型，生产部署需要持久队列与幂等恢复。

### 难点 E：如何证明系统不是只会生成一次 Demo？

> 我把“规划质量、最终媒体质量、执行可靠性”分开评测。方案 Reviewer 看 10 维结构/适配；成片做全片解码、时长和采样视觉检查；运行评测核对阶段、错误、模型 mock、产物与方案指纹，并支持批量汇总。这样至少能避免“生成了一个文件就算成功”。但真正证明质量提升还需要固定评测集、人工标注和 A/B，现有代码不能替代真实实验数据。

## 12. 快速自测：你能不看文档答出这些吗？

6. 用户把分镜改了，为什么旧 Reviewer 结果不能继续用？

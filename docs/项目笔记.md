## 1. 项目定位与端到端流程

### 1.1 一句话介绍

这是一个面向旅行 Vlog 的“参考视频结构迁移 + 用户素材自动成片”系统：系统分析参考视频的 Hook、镜头功能、节奏和情绪结构，理解用户素材，生成可编辑的 `VideoScheme`；用户确认分镜后，系统使用 Remotion 和 FFmpeg 渲染 MP4，并输出方案、成片和运行层面的评测报告。

### 1.2 系统解决的核心问题

传统“一句话生成视频”存在三个问题：

- LLM 容易生成看似合理、实际无法执行的自然语言计划；
- 参考视频与用户素材内容不同，不能机械复制镜头；
- 最终效果不好时，很难判断是分析、规划、素材匹配、渲染还是评测出了问题。

本项目的思路是：

```text
参考视频
→ 提取结构 Gene，而不是复制具体物体

用户素材
→ 提取 MaterialInventory / MaterialGene

Gene + 素材 + 用户要求 + Editing Skill
→ Planner 生成结构化 VideoScheme

VideoScheme
→ 用户编辑/确认 → 渲染 → 双层评测 → 必要时重新规划
```

### 1.3 两条执行入口

```text
Web 产品链路
React → FastAPI → 分阶段分析/规划 → 用户确认 → 渲染 → 评测

独立 CLI 链路
LangGraph Supervisor → 7 个专业 Agent → 审核回环 → 完成
```

Web 路径强调产品交互和人机协作；CLI 图强调完整 Agent 编排。两条路径复用底层模型、数据结构、Skill、渲染和评测能力，但编排方式不同。

## 2. 全栈架构

### 2.1 总体结构

```text
┌─────────────────────────────────────────────────────┐
│ React + Vite 前端                                    │
│ 登录、项目、素材、任务、分镜编辑、进度、视频、报告 │
└──────────────────┬───────────────────┬──────────────┘
                   │ HTTP REST         │ WebSocket
                   ▼                   ▲
┌─────────────────────────────────────────────────────┐
│ FastAPI 后端                                         │
│ Router、JWT、归属校验、数据库、文件、任务队列、WS  │
└───────────────┬─────────────────────┬───────────────┘
                │                     │
       ┌────────▼────────┐   ┌────────▼──────────────┐
       │ SQLite + 文件    │   │ AI / 视频引擎         │
       │ 用户/项目/任务   │   │ VLM、Whisper、LLM    │
       │ JSON/日志/MP4    │   │ LangGraph、Remotion  │
       └─────────────────┘   │ FFmpeg、评测          │
                             └───────────────────────┘
```

### 2.2 前端职责

前端位于 `web/frontend`，使用 React 构建页面，Vite 提供开发服务器和构建能力。它负责：

- 登录注册；
- 创建和查看项目；
- 上传参考视频和用户素材；
- 创建任务并展示状态、进度和日志；
- 展示、编辑、保存和确认分镜；
- 播放最终视频并展示评测报告；
- 提供项目助手聊天界面。

前端不直接访问 SQLite、服务器文件系统、LLM API Key、FFmpeg 或 Agent 内部状态。所有能力都通过 FastAPI 暴露。

### 2.3 后端职责

后端位于 `web/backend`，使用 FastAPI，主要分为四层：

| 层次 | 职责 |
|---|---|
| Router/API 层 | 定义认证、项目、素材、任务、分镜、模型、聊天等接口 |
| Service 层 | 组织业务规则、权限校验、任务创建和脚本调用 |
| 数据与文件层 | SQLite 保存结构化元数据；文件目录保存媒体、JSON、日志和 MP4 |
| AI/视频引擎层 | 调用 VLM、Whisper、LLM、LangGraph、Remotion、FFmpeg 和评测模块 |

准确说法是：

> FastAPI 是业务入口和调度层，不等于 AI 引擎；后端通过服务层调用 AI/视频引擎完成分析、规划、渲染和评测。

### 2.4 为什么 SQLite 和文件系统分开保存

SQLite 适合保存：

- 用户、项目、任务等关系数据；
- 状态、进度、日志摘要；
- 文件路径、版本号和时间戳；
- 分镜和评测报告的索引。

文件系统适合保存：

- 用户上传的图片、视频和音频；
- 分析中间产物；
- `VideoScheme` JSON；
- 抽帧、日志和最终 MP4。

大型二进制媒体直接塞进 SQLite 会增加数据库体积、备份和读写压力，所以数据库主要保存元数据和路径。

## 3. 前后端与 LLM 通信

### 3.1 本地开发为什么也需要 HTTP

HTTP 不等于访问互联网。浏览器和后端即使在同一台电脑上，也仍然是两个进程：

```text
React + Vite：http://localhost:5173
FastAPI：      http://127.0.0.1:8000
```

`localhost` 或 `127.0.0.1` 表示本机；端口用于区分同一台机器上的不同服务。

URL 示例：

```text
http://localhost:5173/api/tasks/123?detail=true
│      │         │    │              │
协议    主机名     端口  路径           查询参数
```

### 3.2 Vite Proxy

前端代码使用 `/api/...` 相对路径，Vite 在开发环境把请求代理给 FastAPI：

```text
浏览器 → localhost:5173/api/tasks/123
       → Vite Proxy
       → 127.0.0.1:8000/api/tasks/123
       → FastAPI
```

这样可以避免前端写死后端地址，并减少本地跨域配置。Vite 的 `ws: true` 也会转发 WebSocket。

### 3.3 HTTP、REST 和 JSON 的区别

| 名称 | 含义 |
|---|---|
| HTTP | 请求—响应通信协议 |
| REST | 使用 URL、HTTP Method 和状态码组织资源接口的设计风格 |
| JSON | 结构化文本数据格式 |
| HTTP 非流式 | 等待服务端一次返回完整响应的使用方式 |

REST 不是协议，JSON 也不是通信协议。

当前常见业务操作：

| 操作 | 方式 |
|---|---|
| 登录、创建项目/任务 | `POST` |
| 查询任务和报告 | `GET` |
| 编辑分镜 | `PUT` |
| 删除项目/素材 | `DELETE` |
| 上传图片/视频 | `multipart/form-data` |

### 3.4 WebSocket 在项目中的作用

WebSocket 是全双工长连接，协议上前后端都可以主动发送消息。当前项目主要使用“后端 → 前端”方向：

```text
ws://localhost:5173/api/tasks/{task_id}/ws
```

后端推送：

```json
{
  "status": "running",
  "workflow_stage": "planning",
  "progress": 60,
  "message": "正在生成分镜方案"
}
```

当前前端通过 WebSocket 发送的主要是 `ping`，后端返回 `pong`；创建任务、保存分镜、确认渲染等业务命令仍使用 HTTP REST。

因此应表述为：

```text
HTTP REST：业务控制面
WebSocket：实时进度体验层
数据库 + HTTP GET：持久化事实来源与断线恢复手段
```

### 3.5 为什么 LLM 调用使用 HTTP 非流式

后端调用 LLM 的模式是：

```text
后端 POST Prompt、上下文和模型参数
→ LLM Provider 生成
→ 同一个 HTTP 响应返回完整文本或 JSON
→ 后端解析、校验
→ 写入状态
→ 下一阶段读取
```

Planner、Reviewer 的下游都需要完整结构化结果。例如半截 JSON：

```json
{ "storyboard": [
```

不能安全交给 Renderer。因此当前不需要为了逐 Token 展示而引入 SSE，也不需要为了阶段式请求维持 WebSocket 长连接。

不是说 SSE 或 WebSocket 不能传 Agent 数据，而是当前收益不足：

| 场景 | 合适方案 |
|---|---|
| 聊天答案逐字展示 | SSE |
| 实时语音、持续双向交互 | WebSocket / Realtime API |
| Planner 完整 JSON 交给 Renderer | HTTP 非流式 |
| 长任务阶段和进度推送给前端 | WebSocket |

### 3.6 三条链路总结

| 链路 | 当前选择 | 原因 |
|---|---|---|
| 浏览器 ↔ FastAPI 业务操作 | HTTP REST | 易鉴权、校验、重试和表达错误码 |
| FastAPI → 浏览器任务进度 | WebSocket | 后端需要在长任务中主动推送 |
| 后端/Agent → LLM Provider | HTTP 非流式 | 下游依赖完整、可校验的结构化产物 |

## 4. JWT、安全与任务隔离

### 4.1 JWT 是什么

JWT 是登录成功后后端签发的带签名身份凭证：

```text
账号密码登录
→ 后端验证
→ 返回 access_token
→ 前端后续请求携带 Authorization: Bearer <token>
→ 后端验证签名和过期时间
→ 获得当前 user_id
```

JWT 解决“你是谁”，不能自动解决“你能否访问这个任务”。后端还必须进行资源归属校验：

```text
Task → Project → User
Material → Project → User
```

认证和授权的区别：

```text
Authentication：你是谁？
Authorization：你是否有权操作这个资源？
```

### 4.2 当前安全边界

- 常规 HTTP 项目、素材、任务、分镜和评测接口使用身份与归属校验；
- 模型 API Key 加密存储，对外返回掩码；
- 当前任务 WebSocket 没有像 HTTP Router 一样完成 Token 和任务归属校验。

后续应补：WS 握手认证、任务归属验证、连接数限制、消息范围控制和速率限制。

## 5. 异步任务队列与状态机

### 5.1 为什么不能让一个 HTTP 请求一直等待

视频分析、Whisper、VLM、LLM 和渲染可能耗时数分钟。若浏览器一直等待一个 HTTP 响应，会出现超时、断线、无法展示进度和难以恢复等问题。

当前流程：

```text
前端 POST 创建任务
→ 后端写入 Task(pending)，立即返回 task_id
→ 任务放入 asyncio.Queue
→ 单 worker 顺序消费
→ 调用分析/规划/渲染子进程
→ 更新 Task.status/progress/logs
→ broadcaster 通过 WebSocket 推送
```

### 5.2 状态机

```text
pending
→ running
→ awaiting_confirmation
→ pending / running
→ success

任一执行阶段 → failed
```

`awaiting_confirmation` 表示分镜草案已生成、等待用户编辑确认，不是最终成功。

### 5.3 当前方案的限制

当前是单进程内存 `asyncio.Queue` 和单 worker：

- 进程重启可能丢失尚未恢复的排队消息；
- 多实例不能共享内存队列；
- 单 worker 限制吞吐；
- 缺少生产级租约、心跳、死信和任务抢占。

生产化可以演进到 Redis/RabbitMQ + Celery/RQ/Arq，并增加幂等任务、重试、死信队列、worker 心跳、租约和 WebSocket Pub/Sub。

## 6. LLM 异常、半截 JSON 与稳定性

### 6.1 核心原则

> 半截模型输出不能交给下一个 Agent。只有完整、解析成功且通过 Schema 与业务校验的产物才能进入共享状态。

处理链路：

```text
网络失败 / 超时 / 读取中断
→ HTTP 调用抛错
→ 调用层重试

模型返回完整文本但 JSON 非法
→ JSON 解析失败
→ Planner 重新生成

JSON 可解析但业务不合法
→ 检查素材 ID、时长、字段范围
→ 拒绝或重新规划

重试耗尽
→ 记录日志和错误
→ 任务 failed，而不是污染下游状态
```

### 6.2 不同故障要分开处理

| 故障 | 例子 | 处理 |
|---|---|---|
| 网络故障 | 超时、连接拒绝、响应中断 | 重试，耗尽后失败 |
| 限流 | HTTP 429 | 等待后重试 |
| 输出截断 | `max_tokens` 不够 | 提高上限或重新生成 |
| 格式错误 | Markdown 包裹、缺字段 | JSON/Schema 校验失败后重试 |
| 业务错误 | 素材不存在、总时长非法 | 业务校验拒绝，重新规划 |

网络断开时，Provider 可能已经完成生成，只是响应没有返回。重试可能带来重复成本，所以生产化还应增加 request ID、幂等键、指数退避、随机抖动和调用成本上限。

## 7. 为什么使用 Multi-Agent

### 7.1 从四阶段模型出发

最初可以将任务抽象为：

```text
感知 → 决策 → 执行 → 校验
```

单 Agent 理论上也能完成，但这个任务具有多阶段、异构工具、高成本执行、结构化交付和审核回环等特点。如果所有职责都交给一个 Agent：

- 上下文会不断膨胀，当前任务重点容易被早期信息干扰；
- 一个 Agent 持有过多工具，误调用面扩大；
- 中间产物不稳定，阶段边界模糊；
- 最终效果差时难以判断是理解错、规划错还是执行错；
- 重试经常需要从大上下文重新开始。

Multi-Agent 的目的不是“Agent 越多越智能”，而是通过角色边界、结构化契约和 Harness 获得可控、可观测、可回溯和可恢复的工程系统。

### 7.2 为什么 Skill 派生 Sub-Agent 仍不能替代 Harness

Skill 可以告诉主 Agent“推荐怎么做”，甚至指导它派生 Sub-Agent，但 Skill 本质上仍主要是模型需要遵守的软指令。长任务中模型可能漏读、误解、跳步或在上下文冲突时不遵守 Skill。

关键路径不能只依赖“模型记得遵守”：

```text
软约束：Prompt / Skill 建议
硬约束：Graph 路由、Schema、Tool Scoping、状态机、验证门禁、最大迭代次数
```

### 7.3 单 Agent + Skill 与 Multi-Agent + Harness

| 维度 | 单 Agent + Skill | Multi-Agent + Harness |
|---|---|---|
| 流程控制 | 主 Agent 理解并遵守 Prompt | Graph/状态机控制关键路径 |
| 上下文 | 容易积累为大上下文 | 每个角色只获取当前阶段必要信息 |
| 工具权限 | 主 Agent 常持有大量工具 | Tool Scoping，按角色最小授权 |
| 中间产物 | 对话历史或自由文本 | Gene、Inventory、`VideoScheme`、Review 契约 |
| 错误定位 | 只能看到最终结果不好 | 能定位具体阶段和责任边界 |
| 失败处理 | Agent 自行决定是否重试 | Schema、回环、降级、最大迭代和显式失败 |
| 成本 | 简单、调用少 | 编排复杂、调用和延迟更多 |

### 7.4 七个专业 Agent 为什么这样拆

拆分依据不是名称，而是五个问题：

```text
输入上下文是否不同？
输出契约是否不同？
工具集合是否不同？
成功指标是否不同？
失败后是否需要独立归因和重试？
```

| 角色 | 为什么独立 | 主要输入 | 主要输出 |
|---|---|---|---|
| Analyst | 参考视频结构分析需要镜头、音频和全局叙事上下文 | 参考视频 | Structure Gene、结构分析 |
| Material Manager | 用户素材理解关注画面内容、质量、人物/场景和可用性，与参考片分析目标不同 | 用户素材 | MaterialInventory、Gap Report |
| Planner | 需要统一权衡 Hook、节奏、情绪、字幕和素材，过度拆开会破坏全片一致性 | Gene、Inventory、偏好、Skill | `VideoScheme` |
| Renderer | 将创作方案解释为确定性渲染组件和参数，解决“想怎么剪”到“代码怎么执行”的鸿沟 | `VideoScheme` | 渲染决策 |
| Creative | 当素材缺口无法直接剪辑时，负责补全或生成策略 | Gap、方案 | 补全素材/策略 |
| Assembler | 执行 Remotion/FFmpeg，关注媒体路径、编码和合成是否成功 | 方案、素材、渲染决策 | MP4、执行日志 |
| Reviewer | 独立检查结构保真和剪辑质量，避免规划者自己给自己打分 | Gene、Inventory、方案 | 评分、问题、重规划建议 |

### 7.5 Supervisor 的职责

Supervisor 是控制平面，不是“最聪明的业务专家”。它负责：

- 根据共享状态选择下一节点；
- 控制条件路由和审核回环；
- 判断是否完成、失败或超过最大迭代；
- 防止节点随意跳过必要阶段。

准确说法是“Supervisor 管理状态驱动的控制流”，而不只是“监控数据流”。

### 7.6 为什么不把所有东西都 Agent 化

以下任务更适合确定性代码：

- JSON Schema 校验；
- 素材 ID 和归属检查；
- 时间轴计算；
- FFmpeg 探测与全片解码；
- 文件读写、哈希和版本管理；
- 阈值门禁和最大迭代计数。

LLM 更适合语义理解、创意规划、复杂素材匹配和开放式质量判断。工程上应使用“LLM 负责不确定语义，代码负责确定性约束”。

## 8. Agent 如何通信，以及 Harness 是什么

### 8.1 图内 Agent 通信

完整 LangGraph 中的 Agent 不是通过 HTTP、SSE、WebSocket 或 A2A 互相聊天，而是通过 `ViralEngineState` 共享结构化状态：

```text
Analyst 写 source_genes / source_structures
→ Material Manager 写 material_inventory / gap_report
→ Planner 读取这些字段并写 scheme
→ Reviewer 读取 scheme 并写 review_result / feedback
→ Supervisor 根据状态决定继续、回环或结束
```

这属于共享状态/黑板模式。Agent 之间传递结构化摘要、引用和路径，而不是传递原始视频字节或无限增长的聊天记录。

Web 分阶段路径的状态主要保存在 SQLite Task 和任务文件目录，不能把所有 Web 状态都称为 `ViralEngineState`。

### 8.2 Agent Harness 的组成

Harness 是模型之外，保证 Agent 系统能够稳定运行的工程外壳：

```text
Agent Harness
├── Graph / 状态机：控制顺序、分支、回环和终止
├── State / Memory：保存跨节点结构化上下文
├── Schema：约束每阶段输入输出
├── Tool Registry：统一工具元数据和参数校验
├── Tool Scoping：限制每个角色可调用的工具
├── Retry / Fallback：处理模型、媒体和渲染异常
├── Observability：阶段日志、耗时、Token、错误和产物
├── Evaluation：方案、成片、运行和 Skill 评测
└── Persistence：任务状态、JSON、报告和 MP4
```

因此 Harness Engineering 的重点不是多写 Prompt，而是把模型的不确定性包在可控制、可检查、可恢复的系统里。

### 8.3 A2A、MCP 与 Function Calling 边界

| 概念 | 含义 | 当前项目 |
|---|---|---|
| A2A | 独立 Agent 系统之间的网络协作协议 | 未使用；图内节点同进程共享状态 |
| MCP | Client/Server/transport 组成的工具与资源协议生态 | 未完整接入 |
| MCP Tool 兼容定义 | `name / description / inputSchema` | 已实现并用于工具注册和校验 |
| Function Calling | 模型选择工具并生成结构化参数 | 具备工具定义与派发能力，但主链路多为确定性调用 |

不能把“工具 Schema 与 MCP 格式相似”直接说成“完成 MCP 协议接入”。完整 MCP 还需要 Client、Server、能力发现、传输和生命周期管理。

## 9. 核心数据结构：Gene、Memory、VideoScheme、Skill

### 9.1 Structure Gene：迁移什么

Gene 表示参考视频的结构功能，而不是具体物体：

- Hook 的位置和方式；
- 每个镜头承担的功能；
- 镜头时长比例和节奏角色；
- 情绪递进和高潮位置；
- 镜头之间的关系；
- 硬约束和软偏好。

例如原片开头是“飞机冲出云层”，用户没有飞机素材。系统不应要求复制飞机，而应迁移“强运动、强视觉冲击、前 3 秒抓注意力”的 Hook 功能，再从用户素材中寻找同功能替代。

### 9.2 MaterialInventory 与 MaterialGene：有什么素材

MaterialInventory 描述当前任务中的具体素材，包括 ID、类型、内容、质量和适用镜头。MaterialGene 是适合长期统计的脱敏摘要，例如：

- 视频/图片数量；
- 是否有运动、人物、风景、建筑素材；
- 主要场景和标签；
- 素材丰富度区间。

长期 Experience 默认保存 MaterialGene，不保存用户原始素材文件，也不依赖绝对路径。

### 9.3 Working Memory：这次任务发生了什么

`ViralEngineState` 是一次图运行的共享工作记忆，保存当前任务所需的 Gene、素材库存、方案、Reviewer 反馈、迭代次数、错误和日志。

Working Memory 不是跨用户的永久知识库。任务结束后，可复用经验应以脱敏 Experience 和 Skill 的形式沉淀。

### 9.4 VideoScheme：规划与执行之间的 IR

`VideoScheme` 是 Planner、前端编辑、Reviewer、Renderer 和评测共用的结构化中间表示：

```text
Gene + Inventory + 用户要求 + Skill
→ Planner
→ VideoScheme
→ 前端编辑/确认
→ Reviewer 检查
→ Renderer/Assembler 执行
→ 评测定位到镜头
```

它包含：

- 目标主题、平台、时长和结构类型；
- 分镜顺序、素材 ID、镜头功能和时长；
- 字幕、转场、情绪、运镜、包装；
- Gene 引用和适配原因；
- Skill 的 selected/loaded/declared/verified 轨迹；
- 渲染组件和 FFmpeg 时间线。

它的价值是把自然语言计划变成可编辑、可验证、可执行和可追溯的契约。

### 9.5 Skill 与 Experience 的区别

```text
Working Memory：这次任务正在发生什么
Experience：过去某次任务在什么条件下采取什么动作、结果如何
Skill：多个可信 Experience 共同支持的可复用方法
```

Skill 决定“在当前素材条件下怎么剪得更好”，Gene 决定“本次参考视频需要迁移什么结构”。优先级是：

```text
用户显式要求
> Gene 硬约束
> Editing Skill
> 模型自由发挥
```

## 10. 评测体系：不能只看最终总分

### 10.1 第一层：方案 Reviewer

Reviewer 评估的是 `VideoScheme`，不是最终 MP4。当前包含 10 个主要维度：

1. `structure_fidelity`：结构保真；
2. `hook_appeal`：Hook 吸引力；
3. `content_adaptation`：内容适配；
4. `rhythm`：节奏；
5. `emotion_coherence`：情绪连贯；
6. `gap_filling_quality`：素材缺口补全；
7. `packaging_consistency`：包装一致性；
8. `completeness`：方案完整性；
9. `subtitle_quality`：字幕质量；
10. `material_coverage`：素材覆盖。

同时把问题分成两类：

```text
Fidelity：参考结构是否迁移正确
Quality：在不破坏结构的前提下，素材、转场、字幕和节奏是否剪得自然
```

Fidelity 问题通常反馈给 Planner 恢复 Gene；Quality 问题要求优化方案但不能破坏 Gene。

### 10.2 第二层：成片评测

方案合理不等于 MP4 正确。渲染后还要检查真实成片：

- 全片能否解码；
- 文件和时长是否合理；
- 是否存在音轨或异常静音；
- 是否有黑屏和长静帧；
- 按分镜时间轴抽取代表帧；
- 视觉模型检查 Hook、分镜兑现、素材适配、连续性、字幕和包装；
- 问题附带秒级时间证据。

成片视觉模型分数当前主要用于诊断，阈值仍需人工标注视频校准，不应直接当作绝对真值。

### 10.3 第三层：Agent 系统运行评测

除了视频效果，还应评估系统本身：

| 类别 | 示例指标 |
|---|---|
| 任务成功 | 完成率、阶段覆盖率、失败阶段 |
| 结构正确 | JSON/Schema 通过率、非法素材引用、时长合法性 |
| 工具使用 | Tool 参数有效率、越界调用、失败率 |
| 工作流 | 路由正确性、回环次数、最大迭代命中 |
| 稳定性 | 超时、重试、降级路径、恢复能力 |
| 性能成本 | 总耗时、各阶段耗时、Token、模型请求和成本 |
| 可观测性 | 日志完整性、错误证据、产物和版本可追踪性 |

### 10.4 评测闭环

```text
Planner 生成方案
→ Skill 规则验证
→ 10 维 Reviewer
→ 未通过则反馈 Planner
→ 用户确认
→ 渲染 MP4
→ 技术检测 + 抽帧视觉评测
→ 运行报告和 Skill Experience
```

## 11. Skill 在线应用闭环

### 11.1 Skill 的两层文件

Registry 是机器可读契约：

```jsonc
{
  "id": "hook",
  "version": "1.0.0",
  "status": "active",
  "priority": 90,
  "routing_weight": 1.0,
  "applicable_stages": ["planning", "opening"],
  "applicable_shot_functions": ["hook"],
  "validation_rules": ["hook_first_shot", "hook_fast_opening"],
  "description": "前 3 秒 Hook 的剪辑策略"
}
```

Markdown 是 Planner 阅读的完整方法：

```text
references/hook.md
├── 适用条件
├── 推荐动作
├── 不适用条件
├── 与 Gene 冲突时的优先级
└── 验证规则解释
```

### 11.2 混合路由

当前 Router 分两层：

```text
第一层：Gene 确定性规则
→ 选出必须使用的 Skill

第二层：LLM 读取用户目标、Gene、MaterialGene 和 Registry description
→ 补充规则未覆盖但确实相关的 Skill
```

语义层只能增加 active Skill，不能删除确定性结果；LLM 路由失败时降级为纯规则结果。

路由只读取 Registry 元信息，不会先把所有 Markdown 塞进上下文。选中后才加载对应文件，这就是渐进式披露：

```text
扫描轻量元数据
→ 选中 Skill ID
→ 加载少量相关 Markdown
→ 注入 Planner
```

### 11.3 四层执行追踪

Router 选中不等于 Planner 真正执行。项目把链路拆成四层：

| 字段 | 含义 | 失败时排查 |
|---|---|---|
| `selected` | Router 判断本任务需要该 Skill | 路由规则、description、Gene 映射 |
| `loaded` | Markdown 确实进入 Planner 上下文 | 文件、active 状态、Prompt 构建 |
| `declared` | Planner/分镜明确声明采用 | Skill 清晰度、适用性、模型遵循 |
| `verified` | 可观察规则验证动作确实落在方案里 | Scheme 字段、规则和实际动作 |

示例：

```jsonc
{
  "skill_id": "transition",

  // Router 判断需要转场知识
  "selected": true,

  // transition.md 已进入 Planner Prompt
  "loaded": true,

  // Planner 声称采用了转场 Skill
  "declared": true,

  // 实际转场字段不符合规则，所以验证失败
  "verified": false
}
```

归因方式：

```text
未 selected → 路由漏选
selected 但未 loaded → 编排/文件/注入故障
loaded 但未 declared → Skill 不适用、描述不清或 Planner 未遵循
declared 但未 verified → 口头采用，动作没有真实落地
verified 但效果仍差 → Skill 本身、适用边界、素材或其他决策有问题
```

轨迹会写入 `VideoScheme.skill_evaluation` 和 `evaluation/skill_evaluation.json`，用于后续归因。

## 12. Skill 离线发现与沉淀

### 12.1 为什么不能一次成功就生成 Skill

一条视频成功可能来自素材质量、参考片难度、随机性或多个策略共同作用。单次经验不能证明某个动作具有跨任务价值。

正确原则是：

```text
单次任务 → Experience
多条相似且可信的 Experience → Candidate Skill
受控实验通过 → Active Skill
```

### 12.2 Experience 采用“宽进严出”

只要任务执行，就保存 Run Experience；存在可观察 Skill 决策时，保存 Decision Experience。收集阶段不直接删除失败数据，因为失败记录可用于诊断和反例边界。

Run Experience 记录任务级信息：

- 任务状态；
- Gene 摘要；
- MaterialGene；
- 使用过的 Skill；
- Reviewer、成片和运行结果。

Decision Experience 记录一个具体决策：

```jsonc
{
  // 哪次运行产生的经验
  "run_id": "run_001",

  // 这条经验属于哪类决策
  "decision_type": "hook",

  // 当时满足的结构与素材条件
  "conditions": {
    "video_type": "travel_vlog",
    "has_motion_material": true,
    "has_landscape_material": true,
    "target_rhythm": "fast"
  },

  // Planner 最终采取的可观察动作
  "action": {
    "opening_material_type": "motion_landscape",
    "first_shot_duration": 1.2,
    "subtitle_in_first_shot": true
  },

  // 这条 Skill 链路是否真的走通
  "execution": {
    "selected": true,
    "loaded": true,
    "declared": true,
    "verified": true
  },

  // 最终质量结果
  "outcome": {
    "quality_score": 88,
    "reviewer_passed": true,
    "run_success": true,
    "render_status": "passed"
  }
}
```

### 12.3 隐私：保存素材基因，不保存素材本身

经验库不应长期复制用户视频、图片和绝对路径。默认保存：

- 素材数量和类型分布；
- 是否包含人物、运动、风景和建筑；
- 脱敏标签与质量摘要；
- 实际剪辑动作；
- 评测结果和证据引用。

Embedding 也不天然匿名，仍需权限和保留周期治理。

### 12.4 大量 Experience 如何处理

假设已经有数百条经验，离线挖掘按以下步骤进行：

#### 第一步：质量分类

不把数据直接物理删除，而是标记不同用途：

| 状态 | 处理方式 |
|---|---|
| 未 `selected` | 路由漏选诊断，不进入动作效果样本 |
| 未 `loaded` | 注入故障样本 |
| 未 `declared` | 路由过宽或 Planner 未采用 |
| 未 `verified` | 执行反例 |
| 缺少质量结果 | 暂不进入效果挖掘 |
| verified 且结果完整 | 进入候选模式挖掘 |

#### 第二步：归一化

统一同义标签、数值区间和字段表达，例如：

```text
旅行 Vlog / travel vlog → travel_vlog
首镜 1.1s / 1.2s / 1.4s → very_short
素材 1～4 个 → few
```

归一化避免相同策略因为措辞和小数差异被拆成很多组。

#### 第三步：条件和动作分组

```text
group_key = decision_type + normalized_conditions + normalized_action
```

每个组统计：

- `sample_count` 和去重后的 `run_count`；
- `verified_rate`；
- `success_rate`；
- `mean_quality_score`；
- 与同条件其他动作的观察性差异。

历史关联只用于发现候选，不能当作因果证明。

#### 第四步：生成 Candidate

只有达到样本量、验证率、成功率和质量门槛的最佳动作组才生成 Candidate。Candidate 包含：

- 适用条件；
- 明确动作；
- 不适用边界；
- 可观察验证规则；
- 来源组、样本量和质量证据；
- `causal_claim=false`。

当前实现使用确定性模板生成 Candidate，避免 LLM 凭空创造规则。以后可以让 LLM 优化文字表达，但统计门槛和实验门禁必须由普通代码控制。

### 12.5 Candidate 校验

Candidate 进入实验前执行：

- 必填 Schema 检查；
- instructions 是否可执行；
- validation rules 是否可观察；
- 条件 + 动作指纹去重；
- 高相似候选检查；
- 相同条件下动作冲突告警。

同条件冲突不一定立即删除，因为两个动作可能都合理；它们需要通过固定任务集 A/B 裁决。

### 12.6 固定任务集 A/B 与消融实验

为了判断 Skill 是否真的带来提升，应固定：

- 相同参考视频和用户素材；
- 相同模型、Prompt、温度和渲染配置；
- 相同 Reviewer 和成片评测；
- 唯一变化是启用或禁用 Candidate。

```text
baseline：不启用 Candidate
candidate：启用 Candidate
```

同一个 case 必须同时运行两个 variant，并采用稳定交叉顺序，减少缓存和执行顺序偏差。分析指标包括：

- 平均质量提升；
- Candidate 胜率；
- 延迟回退比例；
- 成本回退比例；
- 配对样本数量。

样本不足返回 `inconclusive`；质量或胜率不达标、成本或时延退化过大返回 `reject`；全部通过才返回 `promote`。

### 12.7 晋升、版本归档与回滚

Candidate 晋升必须通过：

```text
Candidate 结构校验
+ 观察样本门槛
+ 固定任务集受控实验
→ Active Skill
```

更新已有 Skill 时不会覆盖掉整份人工 Markdown，而是：

1. 将旧 Registry 定义和 Markdown 归档到版本目录；
2. 在原有 Markdown 后增量加入数据学习规则；
3. 合并验证规则；
4. 更新版本和来源 Candidate/Experiment；
5. 保留旧版本以支持显式回滚。

紧急 `force` 发布会记录审计事件，但不应作为正常流程。

### 12.8 路由权重学习

系统根据跨任务证据使用 Beta 平滑估计保守更新 `routing_weight`，并有限吸收受控实验结果。权重范围受到限制，避免少量样本把路由推向极端。

关键安全边界：

> `routing_weight` 只影响 LLM 语义候选的排序；不能停用或删除 Gene 确定性必选结果。

### 12.9 已实现的模块

| 文件 | 职责 |
|---|---|
| `skills/experience.py` | Run/Decision Experience 抽取、任务 JSON 和 SQLite 幂等持久化 |
| `skills/mining.py` | 归一化、质量过滤、增量处理和统计分组 |
| `skills/candidates.py` | Candidate 生成、Schema、去重和冲突检查 |
| `skills/experiments.py` | 固定任务集、配对 A/B/消融、质量/成本/时延分析 |
| `skills/lifecycle.py` | 晋升门禁、归档、回滚和路由权重学习 |
| `skills/pipeline.py` | `ingest/mine/experiment/promote/rollback/learn-weights` CLI |
| `skills/router.py` | Gene 规则 + LLM 语义补充的混合路由 |
| `skills/verifier.py` | selected/loaded/declared/verified 和规则验证 |
| `skills/analytics.py` | 多次运行的观察性 Skill 聚合 |

任务收尾时，`OutputManager` 会 best-effort 刷新 Experience。学习链路失败只记录日志，不能反向拖垮视频生成主任务。

## 13. 从用户点击到最终视频的完整链路

```text
1. 用户登录
   → FastAPI 验证账号
   → 返回 JWT

2. 用户创建项目并上传参考视频/素材
   → HTTP multipart/form-data
   → 后端检查身份与项目归属

   → HTTP POST
   → Task 状态设为 pending
   → 返回 task_id
   → 任务进入 asyncio.Queue

   → 后端持续推送阶段、进度和日志
   → HTTP GET 作为断线查询兜底

5. 分析阶段
   → VLM/镜头时间轴/Whisper 分析参考视频
   → 生成 Structure Gene
   → Material Manager 分析用户素材
   → 生成 Inventory / MaterialGene / Gap Report

6. 规划阶段
   → Skill 混合路由
   → 按需加载 Markdown
   → Planner 输出 VideoScheme
   → Schema、素材 ID、时长和 Skill 规则检查

7. 人机协作点
   → Task = awaiting_confirmation
   → 前端展示分镜
   → 用户编辑、保存、确认

8. 渲染阶段
   → Renderer 生成渲染决策
   → Creative 处理素材缺口

9. 评测阶段
   → 10 维方案 Reviewer

   → 生成运行和 Skill 报告

10. 经验沉淀
    → Run / Decision Experience
    → 写入任务目录和 SQLite
    → 后续离线挖掘 Candidate Skill
```

## 14. 技术选型：用了什么、为什么；没用什么、为什么

| 问题 | 当前选择 | 为什么 | 没有选择/边界 |
|---|---|---|---|
| 前端框架 | React + Vite | 组件化、状态驱动、开发服务器启动快 | Vite 是构建工具，不是后端 |
| 后端框架 | FastAPI | 类型校验、异步接口、OpenAPI、Python AI 生态衔接好 | FastAPI 不是 AI 引擎本身 |
| 业务通信 | HTTP REST | 请求—响应明确、鉴权和状态码成熟 | 没有把所有命令塞进 WebSocket |
| 进度通信 | WebSocket | 后端可主动实时推送 | 当前主要单向使用，且待补握手鉴权 |
| LLM 调用 | HTTP 非流式 | 下游需要完整 JSON | 没有为了内部 Token 展示使用 SSE |
| 任务队列 | `asyncio.Queue` + 单 worker | 本地原型简单可调试 | 不是持久化分布式队列 |
| Agent 编排 | LangGraph | 显式状态、条件边和审核回环 | Web 产品路径不是每次都跑完整图 |
| 中间表示 | `VideoScheme` | 可编辑、校验、渲染和追踪 | 不直接让 Renderer 解析自由文本 |
| 工具契约 | `name/description/inputSchema` | 统一注册和参数校验 | 兼容 MCP Tool 定义，不等于完整 MCP |
| 视频渲染 | Remotion + FFmpeg | 前者适合组件化时间轴，后者擅长媒体探测和处理 | 需要降级和超时控制 |
| 经验存储 | SQLite + JSON | 可解释、低依赖、适合当前规模 | 暂未先上向量数据库 |

## 15. 高频误区与纠正

| 错误说法 | 正确说法 |
|---|---|
| 前后端通过 WebSocket 通信 | 业务操作主要是 HTTP REST；WebSocket 用于任务进度 |
| REST 是一种协议 | REST 是基于 HTTP 的接口设计风格 |
| SSE 就是逐字协议 | SSE 是 HTTP 上的单向事件流，逐 Token 只是常见用法 |
| 不用 WebSocket 调 LLM，因为后端不需要给 LLM 发消息 | 后端当然要发送 Prompt；当前是一次请求—完整响应，不需要长连接 |
| Agent 之间通过 WebSocket 通信 | 图内 Agent 通过共享结构化状态通信 |
| Skill 被 Router 选中就代表使用成功 | 必须区分 selected、loaded、declared、verified |
| 使用 Skill 后平均分高，说明 Skill 有效 | 这是关联，只能用受控 A/B/消融证明因果 |
| 工具采用 MCP 字段就代表完整接入 MCP | 当前只是 MCP Tool 定义兼容，不含完整 Client/Server |
| JWT 防止项目知识冲突 | JWT 证明身份；归属校验防止越权和数据混用 |
| `async` 就能无限并行 | 并发仍受 worker 数、CPU/GPU、API 限流和媒体资源限制 |
| Reviewer 的 10 维分数就是 Agent 系统全部评测 | 还要评估工作流、工具、稳定性、延迟、成本和最终 MP4 |

## 16. 面试回答模板

### 16.1 项目整体介绍（约 90 秒）

> 这是一个面向旅行 Vlog 的参考结构迁移系统。它不是让模型从零随意生成视频，而是先通过镜头时间轴、VLM 和 Whisper 分析参考片，提取 Hook、镜头功能、节奏、情绪和音频等 Structure Gene，再由素材管理模块理解用户上传的风景、人物和建筑素材。Planner 将 Gene、素材库存、用户偏好和按需加载的 Editing Skill 组合成结构化 `VideoScheme`，用户可以在 React 前端编辑确认，之后由 Remotion 和 FFmpeg 完成渲染。
>
> 工程上，前端使用 React + Vite，后端使用 FastAPI、JWT、SQLite、异步任务队列和 WebSocket。HTTP REST 负责项目、任务和分镜等业务操作，WebSocket 负责推送长任务进度，后端调用 LLM 使用非流式 HTTP，因为下游需要完整 JSON。独立 CLI 使用 LangGraph 编排 Supervisor 和七个专业 Agent；Web 为了支持用户确认采用分阶段脚本链路。
>
> 系统还设计了两层视频评测和一套 Skill 学习闭环：先评估分镜方案，再检查真实 MP4；每次任务产生脱敏 Experience，多条可信经验经过增量挖掘形成 Candidate Skill，只有通过固定任务集 A/B 后才能晋升，并保留版本和回滚能力。

### 16.2 为什么使用 Multi-Agent（约 90 秒）

> 我最初按感知、决策、执行、校验四阶段设计，但发现单 Agent 会同时承担差异很大的上下文和工具。参考视频分析关注 Hook、节奏和情绪结构，用户素材理解关注人物、风景、质量和可用性，所以感知拆成 Analyst 和 Material Manager。Planner 负责决定怎么迁移，但创作方案到可执行渲染参数之间还有语义鸿沟，因此执行又拆成 Renderer、Creative 和 Assembler。最后 Reviewer 独立检查结构保真和剪辑质量，Supervisor 负责控制路由、回环和终止。
>
> 多 Agent 的价值不是数量，而是可控和可归因。每个角色有最小上下文、独立 Tool Set 和结构化输出；关键路径由 LangGraph、Schema、验证门禁和最大迭代次数约束。单 Agent + Skill 虽然也能完成任务，甚至派生 Sub-Agent，但 Skill 仍主要是软指令，不能保证长任务里始终不漏步骤。Multi-Agent + Harness 把软建议变成可执行边界，代价是调用、协调和延迟更高，所以简单确定性步骤仍然使用普通代码。

### 16.3 Agent 之间和前后端如何通信（约 90 秒）

> 这个项目有三类不同通信。第一，LangGraph 图内 Agent 在同一进程中运行，不通过 HTTP 或 WebSocket互相聊天，而是读写 `ViralEngineState`，例如 Analyst 写 Gene，Material Manager 写库存，Planner 读取两者写 `VideoScheme`，Reviewer 再写反馈，Supervisor 根据状态路由。
>
> 第二，浏览器与 FastAPI 的项目、素材、任务和分镜操作使用 REST 风格 HTTP，因为它适合请求—响应、JWT 鉴权、资源归属和错误码。长任务进度通过 WebSocket 从后端实时推到前端；前端当前主要只发 ping，业务命令仍走 HTTP。
>
> 第三，后端调用 LLM 使用 HTTP 非流式请求。Planner 和 Reviewer 的下游都依赖完整 JSON，所以模型响应完成后才解析、校验并写入状态。SSE 更适合用户需要逐字看到答案的聊天场景，WebSocket 更适合实时音频等持续双向交互，都不是当前内部阶段式 Agent 调用的必要选择。

### 16.4 Skill 如何发现、应用和评估（约 90 秒）

> Skill 系统分在线和离线两个闭环。在线阶段，Router 先根据 Gene 做确定性选择，再由 LLM结合用户目标和脱敏素材摘要补充语义相关 Skill；只有命中的 Markdown 才进入 Planner。执行过程中分别记录 selected、loaded、declared、verified，区分路由、注入、模型采用和真实规则落地。
>
> 离线阶段不会把单次成功直接升级成 Skill。任务结束后先沉淀 Run 和 Decision Experience，只保留 Gene、MaterialGene、实际动作和评测结果，不长期复制用户素材。随着经验积累，系统过滤未加载、未声明、未验证和缺少质量结果的样本，对条件和动作归一化、分组并统计验证率、成功率和质量分，再生成 Candidate。
>
> Candidate 经过 Schema、去重、冲突检查以及固定任务集配对 A/B；达到质量提升、胜率、成本和时延门槛后，才更新 Registry 和 Markdown。旧版本会归档，支持回滚。历史统计只负责发现候选，不能替代受控实验的因果验证。

### 16.5 为什么不用 SSE 或 WebSocket 调 LLM（约 45 秒）

> 当前内部 Agent 不是聊天展示，而是阶段式生产结构化产物。Planner 的完整 `VideoScheme` 和 Reviewer 的完整评分 JSON 必须经过解析、Schema 和业务校验后才能进入下一阶段。SSE 流式输出到一半只是半截 JSON，不能提前消费；WebSocket 则需要额外维护长连接、心跳、消息关联和重连，而当前每次调用都是明确的一问一答。因此选择普通 HTTP 非流式响应更简单稳定。如果以后做面向用户的逐字聊天，我会使用 SSE；如果做实时语音双向交互，再考虑 WebSocket 或 Realtime API。

### 16.6 项目当前最大的不足（约 45 秒）

> 当前系统已经具备从规划、渲染、评测到 Skill 学习的 P0 代码闭环，但离生产还有差距。任务队列仍是单进程 `asyncio.Queue` 和单 worker，WebSocket 待补握手鉴权，Skill 阈值还没有大规模真实样本和人工标注校准，也缺少后台调度、审批 UI 和长期 Canary 监控。下一步我会优先做持久队列和幂等恢复、实时链路安全、固定标注集以及 Skill 的灰度与退化告警，而不是继续堆更多 Agent。

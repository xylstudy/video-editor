# 旅行 Vlog 多智能体视频编辑项目笔记

> 本文汇总项目复习中反复出现的“前后端架构、通信方式、LLM 调用、任务进度、Agent 状态流转”等问题。
>
> 原则：**当前代码已经实现的能力、当前架构选择的原因、没有采用或尚未完成的方案，必须分开说。** 面试时准确讲清边界，比堆砌术语更可信。

---

## 1. 项目的一句话定位

这是一个面向旅行 Vlog 的“参考视频结构迁移 + 用户素材自动成片”系统：分析参考视频的 Hook、镜头功能、节奏和情绪结构，理解用户素材，生成可编辑的 `VideoScheme` 分镜方案；用户确认后渲染为 MP4，并输出方案、成片和运行层面的评测报告。

它同时包含两部分：

```text
React + FastAPI 产品链路
  用户上传 → 创建任务 → 编辑/确认分镜 → 渲染 → 查看报告

LangGraph 多 Agent 引擎
  Supervisor + 7 个专业节点 → 分析/规划/补全/合成/审核
```

必须讲准确的边界：

> 当前 Web 的可编辑生成链路使用分阶段脚本编排；独立 CLI 入口才运行完整 LangGraph 图。不能说“用户在 Web 上创建的每个任务都会完整运行 Supervisor + 7 个 Agent 图”。

## 2. 总体架构：谁负责什么

```text
┌──────────────────────────────────────────────────────────────┐
│ 浏览器：React 前端 + Vite                                     │
│ 项目、素材、任务、分镜编辑、进度、视频、评测报告             │
└───────────────────┬───────────────────────┬──────────────────┘
                    │ HTTP REST             │ WebSocket
                    │ 创建/查询/编辑等       │ 任务阶段/进度/日志
                    ▼                       ▲
┌──────────────────────────────────────────────────────────────┐
│ FastAPI 后端                                                   │
│ Router、JWT 认证、归属校验、数据库、文件、任务队列、WS 管理  │
└─────────────────┬─────────────────────┬──────────────────────┘
                  │                     │
          ┌───────▼────────┐   ┌────────▼─────────────────────┐
          │ SQLite + 文件   │   │ AI / 视频引擎               │
          │ 用户/项目/任务  │   │ VLM、Whisper、LLM           │
          │ 素材/日志/路径  │   │ Remotion、FFmpeg、评测      │
          └────────────────┘   └──────────────────────────────┘
```

### 2.1 前端做什么

前端位于 `web/frontend`，使用 React 构建页面，Vite 作为开发服务器与构建工具。前端负责的是用户体验和交互：

- 登录注册；
- 创建/查看项目，上传参考视频与用户素材；
- 创建任务，展示任务状态、进度与日志；
- 展示并编辑 `VideoScheme` 分镜；
- 确认分镜、播放最终视频、查看评测报告；
- 助手聊天界面。

前端**不直接**访问 SQLite、文件系统、LLM API Key、FFmpeg 或 Agent 状态。它始终通过 FastAPI 调用业务能力。

### 2.2 后端做什么

后端位于 `web/backend`，使用 FastAPI。它是统一服务入口，负责：

- 定义项目、素材、任务、聊天、认证等 API Router；
- JWT 身份认证和资源归属校验；
- 将用户/项目/素材元数据/任务状态写入 SQLite；
- 保存上传媒体、分镜 JSON、报告、MP4 等文件产物；
- 创建后台任务，调度分析、规划、渲染、评测脚本；
- 将进度写入 `Task.progress` / `Task.logs`，并推给前端；
- 调用 AI 与视频处理引擎。

因此不要说“FastAPI 就是 AI 引擎”。准确说法是：

> FastAPI 负责业务入口、状态管理和任务调度；它再调用 AI/视频引擎完成模型分析、规划、渲染和评测。

## 3. 本地开发：为什么也需要 HTTP，端口是怎样工作的

### 3.1 本地仍然是客户端与服务端通信

HTTP 不等于访问互联网。即使浏览器和服务端都在同一台电脑，浏览器仍然通过 HTTP 请求本机服务：

```text
localhost / 127.0.0.1 = 当前这台电脑的回环地址
```

当前开发配置是两个进程、两个端口：

```text
React + Vite 前端开发服务器：http://localhost:5173
FastAPI + Uvicorn 后端服务：  http://127.0.0.1:8000
```

端口可以理解为同一台电脑上不同网络服务的“门牌号”。一台电脑可以同时运行前端、后端、数据库等多个服务，只要监听端口不同。

### 3.2 URL 的组成

```text
http://localhost:5173/api/tasks/123?detail=true
│      │         │    │              │
协议    主机名     端口  路径           查询参数
```

- `http`：通信协议；线上通常是加密的 `https`；
- `localhost`：本机；
- `5173`：Vite 前端服务端口；
- `/api/tasks/123`：后端资源路径；
- `?detail=true`：可选查询参数。

浏览器从业务视角是“请求 URL、得到响应”；更底层会根据主机和端口连接对应服务，再发送 HTTP 请求。

### 3.3 Vite Proxy：本项目最容易混淆的细节

浏览器访问的是：

```text
http://localhost:5173
```

前端 API 统一以相对路径 `/api` 开始。`web/frontend/vite.config.js` 配置了代理：

```text
浏览器
  → http://localhost:5173/api/tasks/123
  → Vite Proxy
  → http://127.0.0.1:8000/api/tasks/123
  → FastAPI
```

因此开发环境中可能有两段 HTTP：

```text
① 浏览器 → Vite:5173
② Vite:5173 → FastAPI:8000
```

Vite 也配置了 `ws: true`，所以 `/api` 下的任务 WebSocket 同样由 Vite 转发给 FastAPI。

**为什么选 Vite Proxy：** 前端代码只使用 `/api/...`，无需到处写死 `8000`；本地开发避免浏览器直接跨域访问后端；线上部署时容易改成同域反向代理。

**生产环境不一定还是两个对外端口：** 常见做法是 Nginx 监听 `https://example.com:443`，将 `/` 返回 React 构建静态文件，将 `/api` 和 WebSocket 反向代理给内部 FastAPI。前后端仍可以是两个进程，但用户只看到一个域名。

## 4. HTTP、REST、JSON：普通业务操作怎么通信

### 4.1 概念不要混淆

| 名称 | 是什么 | 不是什么 |
|---|---|---|
| HTTP | 请求—响应通信协议 | 不等于 REST |
| REST | 基于 HTTP 组织资源接口的设计风格 | 不是协议、不是“数据格式” |
| JSON | 结构化文本数据格式 | 不适合直接传大型视频二进制 |
| HTTP 非流式 | 一次请求等待一次完整响应的使用方式 | 不是新协议 |

### 4.2 当前使用：REST 风格 HTTP API

前端主动发送 HTTP 请求，后端处理并返回 JSON、文件或错误码：

| 用户动作 | 常见方法 | 目的 |
|---|---|---|
| 登录 | `POST` | 发送账号密码，获得 Token |
| 创建项目/任务 | `POST` | 创建新资源或触发动作 |
| 查询任务 | `GET` | 获取任务状态、结果、日志 |
| 编辑分镜 | `PUT` | 更新 `VideoScheme` 草案 |
| 确认并渲染 | `POST` | 触发下一阶段任务 |
| 删除资源 | `DELETE` | 删除项目或素材 |

上传图片/视频不能简单塞进 JSON，使用 `multipart/form-data`；最终 MP4 是媒体文件响应；任务、分镜和报告等结构化信息通常用 JSON。

### 4.3 为什么选 REST，而不是所有操作都走 WebSocket

创建项目、上传素材、保存分镜、确认渲染等操作都是明确的“请求 → 校验 → 结果”业务，HTTP REST 更适合：

- URL 和 HTTP Method 能清楚表达资源与动作；
- JWT、权限、状态码、请求校验工具链成熟；
- 出错时能用 401/403/404/409/422 等明确表达原因；
- 无需维持长连接，复杂度低。

WebSocket 能做双向业务命令，但如果只为了发一个“保存分镜”指令就建立/维护长连接，收益很小，反而需要额外处理心跳、断线、重连、消息顺序和请求关联。

## 5. JWT、认证与授权：如何隔离不同用户的数据

### 5.1 JWT 是什么

JWT（JSON Web Token）是登录成功后后端签发的、带签名的身份凭证。

```text
用户提交账号密码
→ 后端验证成功
→ 返回 access_token
→ 前端在后续 HTTP 请求中携带：
  Authorization: Bearer <access_token>
→ 后端验证签名和过期时间，得到当前用户身份
```

JWT 通常由三段组成：

```text
Header.Payload.Signature
```

Payload 可以包含用户标识和过期时间；签名保证 Token 未被篡改。JWT 不是加密保险箱，不能在其中存密码、模型 API Key 等敏感信息。

### 5.2 认证和授权的区别

```text
认证 Authentication：你是谁？
授权 Authorization：你是否有权操作这个资源？
```

在本项目里：

```text
请求带 JWT
→ FastAPI 得到当前 user_id（认证）
→ 沿 Task → Project → User 或 Material → Project → User 检查归属（授权）
→ 允许或拒绝访问
```

它解决的是“越权访问/数据混用”，不是“项目知识冲突”。例如用户 A 不能查看、修改或下载用户 B 的项目、素材、任务和视频。

### 5.3 当前安全边界

- 常规 HTTP 项目、素材、任务、分镜、评测接口：有用户身份和资源归属校验；
- 模型 API Key：加密存储，对外返回掩码；
- **任务 WebSocket：当前没有像 HTTP Router 一样完成 Token/任务归属校验。**

因此不能说“所有实时消息都完成了鉴权”。后续应补：WS 握手 Token 认证、任务归属校验、连接数限制、消息范围控制。

## 6. 任务队列与状态：为什么不让一个 HTTP 请求一直等到视频生成完

视频分析、Whisper 转写、LLM 规划、Remotion 渲染都可能耗时数十秒到数分钟。如果浏览器一直等一个 HTTP 响应：

- 容易超时；
- 用户无法知道任务是否仍在执行；
- 浏览器断线后难以恢复；
- 后端资源会长期被连接占用。

因此当前流程是：

```text
前端 POST 创建任务
→ 后端创建 Task（pending）并返回 task_id
→ 放入进程内 asyncio.Queue
→ 一个 worker 顺序取出任务
→ 调用分析/规划/渲染子进程
→ 写入 Task.progress / Task.logs / Task.status
→ 推送实时进度
```

### 6.1 任务状态机

```text
pending → running → awaiting_confirmation → pending → running → success
                                  └──────────────────────────→ failed
```

- `pending`：等待 worker；
- `running`：正在执行；
- `awaiting_confirmation`：草案已生成，等待用户编辑/确认，**不是最终成功**；
- `success`：最终渲染与必要检查完成；
- `failed`：任务失败，保留日志和原因。

数据库中的 `Task.status/progress/logs` 是事实来源；实时连接断开后，前端可通过 `GET /api/tasks/{id}` 获取最新状态。

### 6.2 当前选择与未采用方案

| 项目 | 当前选择 | 为什么 | 未采用/后续方向 |
|---|---|---|---|
| 队列 | 单进程 `asyncio.Queue` + 单 worker | 本地原型简单、调试成本低 | Redis/RabbitMQ + Celery/RQ/Arq；支持持久化、多 worker、多实例 |
| 任务状态 | SQLite 中的 Task + 文件产物 | 可查询、可恢复，避免 MP4 塞数据库 | 生产可加事件流、任务租约、幂等键 |
| 用户确认点 | 草案生成后再渲染 | 让用户控制内容，避免未确认就消耗昂贵渲染 | 全自动模式可以去掉，但会降低可控性 |

`async` 不等于无限并行。当前单 worker 顺序处理，吞吐仍受模型响应、CPU/内存、视频解码/渲染和 API 限流影响。

## 7. WebSocket：为什么用于任务进度，当前双向实际怎么用

### 7.1 WebSocket 是什么

WebSocket 是建立连接后支持双向主动发消息的长连接协议：

```text
前端  ⇄  后端
```

协议能力是全双工；但某个项目实际使用时可以主要只用其中一个方向。

### 7.2 当前项目的用法

任务详情页使用任务 ID 建立连接：

```text
浏览器：ws://localhost:5173/api/tasks/{task_id}/ws
       ↓ Vite Proxy（ws: true）
FastAPI：/api/tasks/{task_id}/ws
```

后端在任务运行时主动发送：

```json
{
  "status": "running",
  "workflow_stage": "planning",
  "progress": 60,
  "message": "正在生成分镜方案"
}
```

前端监听消息，更新 React State，于是进度条和日志实时变化：

```text
30% 正在分析 → 60% 正在规划 → 90% 正在渲染 → 100% 完成
```

### 7.3 前端是否通过 WebSocket 发送业务消息

当前**没有**。当前业务职责是：

| 方向 | 当前内容 |
|---|---|
| 后端 → 前端 | 任务状态、阶段、进度、日志、成功/失败 |
| 前端 → 后端 | 主要是 `ping`，后端回 `pong`，用于保活 |

创建任务、上传素材、保存分镜、确认渲染等命令都使用 HTTP REST。

未来若需要“取消任务、暂停/恢复渲染、动态修改执行参数”，可通过 WebSocket 增加 `cancel_task`、`pause_render`、`resume_task` 等消息；但这些不是当前已实现功能。

### 7.4 为什么不是前端一直轮询

轮询是前端每隔几秒 `GET /api/tasks/{id}`。它简单，但会产生延迟和大量无变化请求；任务执行阶段也不够即时。

当前选择“WebSocket 推送 + HTTP 查询兜底”：

```text
WebSocket：实时体验层
数据库 + HTTP GET：持久化事实层、断线恢复手段
```

## 8. SSE、WebSocket、HTTP 非流式：为什么 LLM 选普通 HTTP

### 8.1 先看三者的关系

```text
HTTP 协议
  ├─ 普通非流式响应：请求一次，完整返回一次
  └─ SSE：服务端在 HTTP 连接上持续单向推送事件

WebSocket 协议
  └─ 长连接，客户端和服务端均可主动发送消息（全双工）
```

SSE 不支持“客户端主动推送”；WebSocket 支持全双工；HTTP 非流式是一次性请求—完整响应。REST 是接口设计风格，不与它们处在同一层级。

### 8.2 三条通信链路，不能混为一谈

| 链路 | 当前技术选型 | 内容 | 为什么 |
|---|---|---|---|
| 浏览器 ↔ FastAPI 业务操作 | HTTP REST | 登录、上传、任务、分镜、报告、聊天 | 典型请求—响应，易鉴权、校验、表达错误码 |
| FastAPI → 浏览器任务进度 | WebSocket | 状态、阶段、百分比、日志 | 长任务中后端需要主动通知前端 |
| 后端/Agent → LLM Provider | HTTP 非流式 POST | Prompt、上下文、完整文本/JSON | 下游依赖完整结构化产物，阶段式调用 |

### 8.3 当前不使用 SSE 调 LLM 的原因

**不是 SSE 不能用于 Agent 通信。** SSE 可以传文本、Token、甚至分段 JSON；但当前 Agent 主链路没有这个需要。

Planner 需要输出完整的 `VideoScheme`，Reviewer 需要输出完整评分 JSON：

```text
完整 LLM 输出
→ JSON 解析
→ Schema 校验
→ 业务校验（素材是否存在/归属、时长是否合法）
→ 写入状态
→ 下一个阶段读取
```

如果模型流式输出到一半：

```json
{ "shots": [
```

这是不完整 JSON，不能安全交给 Renderer 或 Reviewer。使用 SSE 还需要额外处理事件拼接、半截 JSON、断流、重连、去重、展示与内部状态分离；对当前“无需给用户逐字展示内部 Agent 输出”的场景没有明显收益。

**什么场景适合 SSE：** 聊天机器人希望用户看到模型逐字出现；此时可以一边将 Token 通过 SSE 推给浏览器，一边在后端缓冲完整内容，完成后再做结构化解析。当前项目聊天/Agent 调用不是这种逐字展示模式。

### 8.4 当前不使用 WebSocket 调 LLM 的原因

后端确实需要与 LLM 通信，但模式是：

```text
后端主动 POST Prompt、上下文、模型参数
→ LLM Provider 处理
→ LLM Provider 通过同一个 HTTP 响应返回完整结果
→ 当前调用结束
```

这不是 LLM 无缘无故向后端“推送”，而是标准请求—响应。

当前 Agent 是阶段式调用：

```text
分析结果 → Planner 完整方案 → Reviewer 完整反馈 → 下一阶段
```

不需要维持长连接，也不需要在模型生成过程中让双方持续发新消息。若改成 WebSocket，需要额外处理：

- 建连、心跳和断线重连；
- 多次模型调用的消息 ID 和关联；
- 并发和顺序；
- 半截消息、取消与恢复；
- 与 LLM 供应商接口的兼容性。

这些复杂度对当前完整 JSON 的阶段式流程没有足够收益。WebSocket 在本项目服务的是“后端 → 前端任务进度”，不是“后端 → LLM 调用”。

### 8.5 什么时候考虑 WebSocket / SSE 调模型

| 需求 | 更可能的选择 | 原因 |
|---|---|---|
| 用户要看聊天答案逐字出现 | SSE | 单向服务端推送，浏览器支持好，足够简单 |
| 用户实时发送音频、实时收到语音/文本 | WebSocket / Realtime API | 持续双向低延迟交互 |
| Planner 需要完整 JSON 给 Renderer | HTTP 非流式 | 先拿完整、可校验产物再进入下一阶段 |

## 9. LLM 响应中断、半截 JSON 与重试

### 9.1 关键原则

> 半截 LLM 输出不能传给下一个 Agent。只有完整、解析成功且校验通过的结构化产物才能写入状态。

当前 `config/llm_client.py` 使用 `httpx.AsyncClient` 调用 OpenAI-compatible `/chat/completions`，带 `LLM_TIMEOUT`。如果网络波动或响应中断：

```text
连接失败 / 超时 / 读取中断
→ HTTP 调用报错
→ 重试
→ 拿到完整结果后才继续
```

调用层对网络连接/超时等错误会重试，达到上限后抛出异常；对 429 限流会等待后再重试。Planner 侧对“模型返回内容但 JSON 不合法”的情况还会再尝试生成（最多 3 次）。

```text
LLM 中断或返回无效 JSON
→ 丢弃不完整结果
→ 请求重试 / JSON 生成重试
→ 成功：完整结果通过校验，进入下一阶段
→ 耗尽：异常向上，任务记录错误并标为 failed
```

### 9.2 不同故障要区分

| 故障类型 | 例子 | 当前/合理处理 |
|---|---|---|
| 网络故障 | 超时、连接拒绝、读到一半断开 | HTTP 重试，最终失败并记录日志 |
| 服务限流 | HTTP 429 | 等待后重试 |
| 输出截断 | `max_tokens` 不够，JSON 末尾缺失 | 提高上限或重新生成，再做 JSON 校验 |
| 格式错误 | 模型输出 Markdown、解释文字 | JSON 解析失败，重试/修复 |
| 业务错误 | 素材 ID 不存在、总时长超限 | 业务校验拒绝，要求重新规划 |

网络失败有一个“结果不确定性”：后端断线时，模型服务可能其实已完成生成，只是响应没回来。重试可能增加模型成本。因此生产化可以增加请求 ID、幂等键、指数退避与随机抖动、调用追踪、Token/成本上限。它们是后续方向，不要说成当前全部实现。

## 10. Agent 之间究竟如何通信

### 10.1 LangGraph 图内通信：共享状态，不是网络协议

独立 CLI 的完整 LangGraph 图中，各 Agent 不是用 HTTP、SSE、WebSocket 或 A2A 互发聊天消息，而是通过 `ViralEngineState` 这个共享工作记忆传递结构化产物：

```text
Analyst
  → 写 source_genes / source_structures

Material Manager
  → 写 material_inventory / gap_report

Planner
  → 读 Gene + 素材库存 + 偏好 + Skill
  → 写 VideoScheme

Reviewer
  → 读完整 VideoScheme
  → 写 review_result / feedback

Supervisor
  → 读共享状态，决定下一个节点、回环或结束
```

这类似“共享白板（shared blackboard）”模式。传递的是结构化摘要、库存、路径、引用和方案，而不是把原始视频字节或无边界聊天记录塞到 Prompt 中。

### 10.2 Web 产品路径的状态在哪里

Web 分阶段脚本路径不直接跑完整 Graph 时，状态主要保存在：

```text
SQLite Task：状态、进度、日志、路径、版本号
任务目录：素材、Gene、VideoScheme JSON、报告、MP4
```

因此不能把 Web 任务状态全部称为 `ViralEngineState`；它们是两条入口下的不同状态承载方式。

### 10.3 A2A、MCP、Function Calling 的边界

| 名称 | 是什么 | 当前项目情况 |
|---|---|---|
| A2A | 独立 Agent 系统之间的协议 | 未实现；当前图内节点同进程共享状态 |
| MCP | Agent 与外部工具/资源的 Client-Server 协议生态 | 未实现完整 Client/Server/transport |
| MCP Tool 定义兼容格式 | `name / description / inputSchema` 工具元数据 | 已实现并用于统一工具注册、校验 |
| Function Calling | 模型选择工具并给出结构化参数 | 有角色化工具/参数 Schema/派发能力，但主 Web/Graph 链路大多直接调用专家方法 |

因此不要说“已经完整接入 MCP”或“当前主链路完全由模型自主 Function Calling 驱动”。准确说法是：

> 项目实现了 MCP Tool 定义兼容的工具契约、Tool Scoping 和参数校验，为动态工具调用保留能力；但当前主链路主要采用确定性专家方法调用，尚未接入完整 MCP Client/Server，也未让动态工具循环覆盖全部主流程。

## 11. 为什么有多 Agent，角色如何划分

最初可以用“感知 → 决策 → 执行 → 校验”四阶段解释系统；但真正设计时按 **输入上下文、输出产物、工具集合、成功指标、失败归因** 拆分角色，而不是为了凑 Agent 数量。

| 阶段 | 为什么要拆 | 当前角色与产物 |
|---|---|---|
| 感知 | 参考视频结构分析与用户素材理解的输入、目标、工具、复用粒度不同 | Analyst → Structure Gene；Material Manager → Inventory / Gap Report |
| 决策 | Hook、节奏、字幕、转场高度耦合，过度拆分会破坏叙事一致性 | Planner 统一生成 `VideoScheme` |
| 执行 | 创作决策“做什么”和技术实现“怎么渲染”存在语义鸿沟；缺素材也需要策略 | Renderer、Creative、Assembler → 渲染策略、补全、MP4 |
| 校验 | 方案合理不等于最终视频可解码、画面达标 | Reviewer + 成片技术/视觉评测 |
| 控制 | 需要控制节点路由、审核回环与终止条件 | Supervisor（控制平面，不是业务专家） |

Supervisor 的准确职责是：读取共享状态、调度下一 Agent、控制条件路由、审核回环和终止；不要只说它“监控数据流”。

## 12. `VideoScheme`、Memory、Gene、Skill：为什么需要结构化中间表示

### 12.1 `VideoScheme`

`VideoScheme` 是 Planning、前端分镜编辑、Reviewer、Renderer 和评测共用的结构化中间表示（IR）：

```text
参考结构 + 素材库存
→ Planner 输出 VideoScheme
→ 用户可编辑
→ Reviewer 可审查
→ Renderer 可执行
→ 评测可定位到具体镜头
```

它的价值不是“把 JSON 存下来”，而是将不确定的自然语言计划变成可验证、可编辑、可渲染、可追溯的契约。

### 12.2 Gene、Memory、Skill 的区别

| 概念 | 含义 | 生命周期 | 例子 |
|---|---|---|---|
| Gene | 某条参考片抽取出的结构基因 | 与参考视频绑定，可复用 | Hook 位置、镜头功能、节奏/情绪曲线 |
| Working Memory | 一次图执行的共享上下文 | 一次工作流运行期间 | `ViralEngineState` 的库存、方案、反馈 |
| Skill | 跨任务复用的剪辑经验/规则 | 可持续沉淀 | Hook、转场、字幕包装策略 |

Experience 与 Skill 也要区分：Experience 是某次历史任务中“什么条件下采取了什么动作、得到什么结果”的案例；Skill 是从多个可信 Experience 中抽象出的跨任务方法。三者可以概括为：

```text
Working Memory：这次任务发生了什么
Experience：过去某次任务是怎么做的
Skill：多个任务共同支持的可复用方法
```

当前 Skill 以规则路由和 Markdown 知识为主，并非向量数据库 RAG；不要声称已有 embedding 检索，除非后续真实接入。

### 12.3 Skill 系统的两个闭环

完整的 Skill 系统应拆成两个闭环：

```text
在线使用闭环：
Gene / MaterialGene / 当前阶段
→ Skill Router
→ 注入 Planner
→ 生成 VideoScheme
→ 规则验证
→ Reviewer 与成片评测

离线进化闭环：
任务产物
→ Experience
→ 质量过滤与分组统计
→ Candidate Skill
→ A/B 或消融实验
→ 人工审核
→ Active Skill
```

当前项目同时实现了在线使用链路和离线学习 P0：任务收尾自动抽取 Experience，SQLite 负责幂等持久化，离线程序完成归一化、质量过滤、增量挖掘、Candidate 生成与校验；Candidate 必须通过固定任务集配对 A/B 或消融实验，才允许按策略晋升，旧版本可回滚。该闭环已经具备可运行代码和测试，但还没有生产级定时调度、人工标注平台和大规模真实数据校准，因此不能把“平台具备能力”说成“已经在数百条线上视频上验证有效”。

### 12.4 一个完整 Skill 应包含什么

目标状态下，Skill 不应只是一段模糊 Prompt，而应包含：

```json
{
  "skill_id": "travel-motion-opening-hook",
  "version": "1.0.0",
  "status": "active",
  "description": "旅行 Vlog 运动镜头开场策略",
  "applicable_conditions": [
    "video_type=travel_vlog",
    "opening_hook=weak",
    "material_has_motion_shot=true"
  ],
  "instructions": [
    "前 3 秒优先选择运动感强的素材",
    "首镜头时长控制在 0.8 至 1.5 秒",
    "尽量在首个音乐节拍附近切换镜头"
  ],
  "negative_constraints": [
    "没有运动素材时不要强制使用",
    "慢节奏叙事视频不优先使用快切"
  ],
  "validation_rules": [
    "opening_contains_motion_shot",
    "first_shot_duration_in_range"
  ],
  "evidence": {
    "source_experience_count": 24,
    "experiment_id": "experiment_001"
  }
}
```

其中最关键的是：适用条件、执行动作、不适用边界、验证规则和来源证据。当前注册表已经覆盖 ID、版本、状态、优先级、阶段、功能与验证规则；负面约束、实验结果和证据生命周期属于后续扩展。

相关实现见 [Skill Registry](../viral-structure-engine/skills/video-editing/registry.json)、[Registry Loader](../viral-structure-engine/skills/registry.py) 与 [Skill Router](../viral-structure-engine/skills/router.py)。

### 12.5 Skill 在一次任务中如何调用

```text
参考视频 Gene
+ 用户素材的结构化特征
+ 当前任务阶段
+ 用户偏好
        ↓
Skill Router 选择适用的 Active Skill
        ↓
记录 Skill 版本、优先级和触发原因
        ↓
把 Skill Markdown 内容注入 Planner 上下文
        ↓
Planner 生成 VideoScheme
        ↓
Skill Verifier 检查方案是否真正落地
        ↓
Reviewer 与成片评测补充结果
```

Router 判断“下次是否需要调用”时，会使用混合路由：先由 Gene 镜头功能的确定性规则选出必需 Skill，再把用户目标、Gene 摘要、脱敏后的素材摘要和 Skill Registry 中的 `id / description` 交给 LLM 做语义补充。LLM 只能增加 `active` Skill，不能删除或覆盖规则结果；语义调用异常时自动降级为纯确定性路由。路由轨迹会记录 `deterministic_rule`、`llm_semantic` 或二者共同命中，并保存 `routing_mode` 与降级错误。完整 Markdown 仍只在最终命中后读取，因此保持渐进式加载。

### 12.6 `selected / loaded / declared / verified` 四层追踪

| 状态 | 产生位置 | 含义 | 能定位的问题 |
|---|---|---|---|
| `selected` | Skill Router | Router 判断当前任务需要该 Skill | 本该选择却未选择，说明路由条件可能有问题 |
| `loaded` | 编排/Prompt 构建层 | Skill 内容确实注入 Planner 上下文 | 选中但未加载，说明上下文传递或编排有问题 |
| `declared` | Planner / `VideoScheme` | Planner 或分镜明确声明采用该 Skill | 已加载但未采用，可能是 Planner 未理解、未遵守或认为不适用 |
| `verified` | Skill Verifier | 方案通过该 Skill 的可观察规则检查 | 声称采用但验证失败，说明实际方案不合规 |

流程是：

```text
应该使用
↓ selected

实际传给 Planner
↓ loaded

Planner 明确采用
↓ declared

方案满足可观察规则
↓ verified
```

例如：

```json
{
  "skill_id": "transition",
  "version": "1.0.0",
  "selected": true,
  "loaded": true,
  "declared": true,
  "verified": false,
  "failed_rules": ["transition_config_is_empty"]
}
```

这表示 Router 选中了转场 Skill，规则也注入了 Planner，Planner 还声明自己用了转场；但实际 `VideoScheme` 的转场配置为空。因此问题位于 Planner 方案或结构化输出，而不是 Router。

常见归因关系：

| 结果 | 优先排查位置 |
|---|---|
| 没有 `selected` | Router 的触发条件 |
| `selected=true`、`loaded=false` | 编排和 Prompt 注入 |
| `loaded=true`、`declared=false` | Planner 理解、遵循程度或实际适用性 |
| `declared=true`、`verified=false` | `VideoScheme` 字段和规则合规性 |
| `verified=true`、结果仍然差 | Skill 本身、路由边界、素材质量、其他 Skill 或渲染环节 |

这些数据不是用完即丢的临时变量，而是持续写入方案和 `skill_evaluation.json` 的运行审计记录。相关实现见 [Skill Verifier](../viral-structure-engine/skills/verifier.py)。

### 12.7 如何评估一个 Skill 好不好

Skill 评估要分三层，不能只看最终视频总分。

#### 12.7.1 路由质量

判断 Skill 是否在正确场景中被选中，可以统计：

```text
选中次数
实际加载次数
被 Planner 采用次数
被判断不适用的次数
不同 Gene 条件下的触发分布
```

某 Skill 被选中 100 次却只有 20 次被采用，可能说明路由规则过宽、适用条件定义不清，或者 Skill 内容没有帮助 Planner。

#### 12.7.2 执行合规性

```text
加载率 = loaded / selected
采用率 = declared / loaded
验证通过率 = verified / declared
```

这些指标分别回答：是否正确注入、Planner 是否采用、采用后是否真正满足规则。

#### 12.7.3 结果表现

将 Skill 轨迹与下游结果关联：

- Reviewer 总分及 Hook、节奏、情绪等分项；
- 成片可解码性、时长、音轨、黑屏和静帧结果；
- 运行成功率、耗时和成本；
- 如果以后增加用户行为记录，还可参考用户修改幅度、确认或退回情况。

这里必须区分“关联”和“因果”：使用某 Skill 的任务得分较高，只能说明二者相关；素材质量、其他 Skill、模型波动和渲染参数都可能影响结果。当前 [Skill Analytics](../viral-structure-engine/skills/analytics.py) 提供的是观察性聚合，不能宣称已经证明某 Skill 导致质量提升。

### 12.8 每次任务如何沉淀 Experience

一次任务结束后不应直接创建新 Skill，而应先生成一条可追溯 Experience。Experience 的结构是：

```text
什么条件
+ 采取了什么实际动作
+ Skill 是否正确执行
+ 最终结果如何
+ 原始证据在哪里
```

任务结束节点可以由确定性 `ExperienceExtractor` 读取：

```text
Gene
MaterialGene / MaterialInventory
最终 VideoScheme
Skill Trace
Reviewer Report
Render / Run Evaluation
```

再输出：

```json
{
  "experience_id": "exp_run_001",
  "run_id": "run_001",
  "conditions": {
    "video_type": "travel_vlog",
    "hook_strength": "weak",
    "rhythm_curve": "fast_slow_fast",
    "material_has_motion_shot": true
  },
  "actions": {
    "verified_skills": ["hook", "rhythm"],
    "opening_shot_type": "moving_landscape",
    "opening_duration_sec": 1.2,
    "first_cut_at_sec": 1.1
  },
  "outcomes": {
    "reviewer_score": 8.6,
    "hook_score": 9.0,
    "render_passed": true,
    "black_frame_detected": false
  },
  "evidence": {
    "scheme_path": "planner/scheme_final.json",
    "skill_evaluation_path": "evaluation/skill_evaluation.json"
  }
}
```

这一阶段主要是确定性字段提取，不是让 LLM 凭空“反思出一条经验”。LLM 更适合在多条可信 Experience 上做后续归纳。

最好同时保存两种粒度：

| 粒度 | 作用 |
|---|---|
| Run Experience | 描述整个任务的输入、整体方案和最终结果，适合分析系统整体表现 |
| Skill Experience | 只保留某个 Skill 的适用条件、实际动作、四层状态和对应分项结果，适合做 Skill 归因与挖掘 |

例如一条视频同时使用 Hook、节奏、转场和字幕；如果只看总分，很难判断具体哪个策略有效。按 Skill 拆分 Experience 可以减少无关上下文，但仍不能替代受控实验。

### 12.9 素材数据与隐私：长期保留 MaterialGene，而非默认保留原素材

用于长期 Skill 挖掘时，不应默认把用户原视频、音频和抽帧放入知识库。更合理的数据生命周期是：

```text
用户原素材
→ VLM / Whisper / 镜头分析
→ MaterialGene / MaterialInventory
→ 当前任务规划和渲染
→ 到达用户约定的保留期限
→ 删除原视频、音频、抽帧和临时文件
→ 长期保留脱敏的素材特征、剪辑动作和评测结果
```

MaterialGene 可以保留：场景类型、景别、镜头运动、运动强度、亮度、质量、是否有人物/语音、情绪标签、语义标签及适合承担的镜头功能。默认不应把人脸、声纹、精确位置和真实文件路径写入长期 Experience。

需要准确表达：原素材不是技术上“绝对不能保存”，而是只在任务执行、结果交付、问题追溯和用户授权的保留周期内保存；长期 Skill 学习应采用数据最小化原则。Embedding 也不天然等于匿名数据，仍需要权限、脱敏和保留策略。

### 12.10 数据积累后如何处理

当积累 10、100、1000 条 Experience 后，不能把所有原始记录一次性塞给 LLM。应采用分层和增量处理：

```text
原始任务产物
→ 结构化 Experience
→ Experience 数据库索引
→ 质量过滤
→ 按视频类型、目标问题和 Gene 分组
→ 聚合统计与代表性抽样
→ LLM 归纳 Candidate Skill
```

第一版可用 SQLite 建立轻量索引，数据量和并发需求扩大后再迁移 PostgreSQL。数据库主要保存：

```text
experience_id / run_id
video_type / gene_features / material_features
actions / verified_skills
reviewer_score / render_passed
data_path / processed / cluster_id
created_at / miner_version
```

大体积媒体文件与完整运行产物放文件或对象存储，数据库只保存结构化字段和受控路径。

质量过滤示例：

```text
100 条任务
→ 85 条正常完成
→ 70 条成片检查通过
→ 45 条 Reviewer 达到门槛
→ 32 条相关 Skill 已 verified
→ 进入候选经验池
```

失败案例不应全部删除，它们可以作为负样本帮助识别 Skill 的不适用条件。

第一版可以按以下组合进行确定性分组：

```python
group_key = (
    video_type,
    target_problem,
    verified_skill_id,
)
```

后续再接入 Embedding 和聚类发现文字不同但语义相近的案例。每天只处理 `processed=false` 的新增 Experience，将其分配到已有分组并更新统计，不需要每次重新读取全部原视频。

### 12.11 如何从 Experience 产生 Candidate Skill

只有某个模式在多个相似、可信的正反案例中重复出现，才值得创建候选。例如：

```text
场景：旅行 Vlog + Hook 较弱 + 存在运动素材
样本数：24

使用运动镜头开场：18 条
验证通过：16 条
平均 Hook 分数：8.7

未使用运动镜头开场：6 条
平均 Hook 分数：7.4
```

系统从该分组选择：

- 3 至 5 条高分正例；
- 2 至 3 条普通案例；
- 2 至 3 条失败或反例；
- 该分组的聚合统计。

LLM 只读取统计摘要和少量代表性案例，输出结构化 Candidate Skill，包括适用条件、执行动作、负面约束、验证规则、来源 Experience 和预期效果。LLM 在这里负责归纳，不负责篡改原始证据。

Candidate 生成后还要检查：

- Schema 是否完整；
- 描述是否具体、可执行；
- 是否能转换成可观察验证规则；
- 是否与已有 Skill 重复或冲突；
- 是否只描述一个案例而缺乏泛化性；
- 来源证据和样本量是否足够。

### 12.12 Candidate Skill 的生命周期与因果验证

建议的生命周期是：

```text
draft → candidate → experiment → active → deprecated
```

| 状态 | 含义 |
|---|---|
| `draft` | 刚从历史经验中归纳，尚未通过校验 |
| `candidate` | 已通过格式、去重、冲突和可验证性检查 |
| `experiment` | 只允许在实验任务中显式启用 |
| `active` | 实验和人工审核通过，允许正常 Router 路由 |
| `deprecated` | 无效、过时、存在副作用或已被新版本替代 |

要证明 Candidate Skill 真正有效，需要在固定测试集上做 A/B 或消融实验：

```text
同一批参考视频与素材
├── A 组：禁用 Candidate Skill
└── B 组：启用 Candidate Skill
```

比较 Reviewer 分数、成片技术/视觉质量、人工盲评、成功率、成本和时延；必要时重复多次以降低模型随机性。如果 B 组在足够样本上稳定提升、没有显著副作用，再由人工审核升级为 `active`。因此“历史统计表现更好”是候选证据，受控实验才更接近因果验证。

### 12.13 当前已经实现与尚未实现

当前已实现：

- 人工编写的 Editing Skill Markdown；
- 版本化 Skill Registry；
- 根据 Gene 做确定性必选、再结合用户目标和素材摘要做 LLM 语义补充的混合路由；
- Skill 内容注入 Planner；
- `selected / loaded / declared / verified` 四层追踪；
- 可观察规则校验；
- Reviewer、成片检查和运行评测结果回写；
- `skill_evaluation.json` 持久化；
- 跨任务的观察性基础统计；
- Web Agent 规划路径从预分析报告重建 Gene 并接入 `SkillRouter`。

混合路由已经接入 LangGraph Planner 和 Web `run_pipeline_e2e.py`；`route_by_llm` 不再只是预留接口。当前语义层读取 Registry 描述而非全部 Skill 正文，失败时保留规则结果。离线学习器可以根据跨任务证据保守更新 `routing_weight`；该权重只调整语义候选排序，不能删除 Gene 的确定性必选项。它仍不是向量 RAG。

当前离线 P0 已实现：

- 从任务产物自动生成 Run / Decision Experience；
- SQLite Experience 索引、幂等 upsert、归一化和增量处理；
- 未加载、未声明、未验证、缺少质量结果的分层过滤；
- 按“决策类型 + 条件 + 动作”聚合统计并生成 Candidate；
- Candidate Schema、去重、同条件冲突和可验证性检查；
- 固定任务集配对 A/B / 消融实验、质量/成本/时延门禁；
- 策略化自动晋升、版本归档、回滚和保守路由权重学习。

仍需生产化增强的是：后台定时调度、完整的数据保留/到期删除治理、人工标注与审批 UI、Embedding 聚类，以及在大规模真实样本上校准挖掘与晋升阈值。

另外，无 LLM 的 `editing_transfer` 路径不使用 Planner，因此不会注入 Editing Skill。不能把所有渲染路径都描述为已经执行 Skill 闭环。

### 12.14 Skill 设计面试回答

> 我们把 Skill 系统设计为在线使用和离线进化两个闭环。在线阶段，Router 根据参考视频 Gene、素材基因和任务阶段选择 Skill，并记录版本与触发原因；随后通过 selected、loaded、declared、verified 四级状态，判断 Skill 是否被正确选择、实际注入 Planner、进入 VideoScheme，以及满足可观察的执行规则。每次任务会保存 Skill 评测轨迹，并关联 Reviewer 和成片检测结果，用于定位路由、注入、规划或执行问题。
>
> 离线阶段不会把单次成功任务直接变成 Skill，而是先把条件、实际剪辑动作、执行轨迹、评测结果和证据整理为 Experience。随着案例积累，使用数据库索引、质量过滤、场景分组和增量统计，从多个相似的正反案例中归纳 Candidate Skill。用户原始素材只在任务和授权保留周期内使用，长期经验库主要保存脱敏后的 MaterialGene、剪辑动作和评测结果。
>
> Candidate Skill 还需要经过结构校验、去重、冲突检查以及固定任务集 A/B 或消融实验，才能升级为 Active Skill。当前项目已经实现自动 Experience 抽取、增量挖掘、Candidate 生成、受控实验、版本晋升与回滚；同时仍然把历史聚合视为观察性线索，只有配对实验结果才能进入晋升门禁。生产环境还应在自动策略门禁外增加人工审批和长期监控。

## 13. 评测：评什么、什么时候评、为什么不能只看一个分数

| 层次 | 评测对象 | 当前关注点 |
|---|---|---|
| 方案 Reviewer | Gene、素材库存、`VideoScheme` | 结构保真、Hook、节奏、情绪、素材覆盖等 10 维 |
| 成片检查 | 最终 MP4 | 可解码、时长、音轨、黑屏/静帧风险、抽帧视觉一致性 |
| 运行评测 | 日志、阶段产物、调用记录 | 是否真正完成、错误在哪、产物是否齐全/非 mock |

10 维 Reviewer 是**方案评测**，不是“最终 MP4 画质的 10 项指标”。最终视频的技术/视觉质量由渲染后的检查补充。

`score` 用于诊断和比较；`success` 表示关键阶段和硬性检查是否通过。高分不等于文件一定可播放，文件可播放也不代表创作质量一定高。

## 14. 高频误区速查

| 误区 | 正确说法 |
|---|---|
| REST、SSE、WebSocket 是三种同级协议 | HTTP 和 WebSocket 是协议；REST 是 HTTP API 风格；SSE 建立在 HTTP 上 |
| HTTP 只能在线上使用 | 本地 `localhost` 服务也通过 HTTP 通信 |
| WebSocket 是全双工，所以项目一定双向传业务命令 | 协议全双工；当前业务主要后端推送进度，前端仅保活 |
| LLM 不需要和后端通信，只会推送结果 | 后端主动 HTTP POST Prompt，LLM 服务响应完整结果 |
| SSE 不支持 Agent 通信 | SSE 可以传任意事件；只是当前 Agent 需要完整 JSON，无需 Token 级流式传递 |
| 后端调用 LLM 不用 WS，是因为只能单向 | 实际是阶段式请求—响应，HTTP 足够且复杂度更低 |
| JWT 防止项目“知识冲突” | JWT 认证身份；配合归属校验防止跨用户越权与数据混用 |
| `asyncio` 就是高并发 | 当前单 worker 顺序消费，`async` 主要避免 I/O 阻塞 |
| 所有 Web 任务都跑完整 LangGraph 图 | 当前 Web 是分阶段脚本链路；完整图是独立 CLI 入口 |
| MCP 格式注册 = 完整 MCP 接入 | 当前只是 Tool 定义兼容，未实现 MCP Client/Server 协议链路 |

## 15. 面试回答模板

### 15.1 前后端架构与通信（约 90 秒）

> 前端采用 React + Vite，负责登录、项目和素材管理、任务创建、分镜编辑、进度和结果展示；后端采用 FastAPI，负责 API 路由、JWT 身份认证、项目/任务资源归属校验、数据库与文件管理，以及异步任务调度。当前本地开发时 Vite 运行在 5173 端口，FastAPI 运行在 8000 端口；Vite 通过 Proxy 将 `/api` 和 WebSocket 请求转发给后端。普通业务操作，如上传、创建任务、编辑和确认分镜，使用 REST 风格 HTTP API；视频分析和渲染是长耗时任务，后端创建 Task 后由 `asyncio.Queue` 的 worker 执行，并通过 WebSocket 向前端推送阶段、进度与日志。数据库中的任务状态是事实来源，WebSocket 负责实时体验和断线前的增量同步。

### 15.2 为什么 LLM 调用不用 SSE 或 WebSocket（约 45 秒）

> 后端调用 LLM 采用普通 HTTP 非流式请求。后端主动发送 Prompt、上下文、模型参数和结构化输出要求，等待模型返回完整的 `VideoScheme` 或 Reviewer JSON，再执行 JSON、Schema 和业务校验，并写入状态供下一阶段使用。SSE 并非不能用于 Agent 通信，但它的 Token 流更适合面向用户的逐字展示；当前内部 Agent 依赖完整结构化产物，流式会增加半截 JSON、断流恢复和事件拼接复杂度。WebSocket 适合实时语音、持续双向交互等场景；当前 Agent 是阶段式请求—响应，维护 WebSocket 的心跳、重连、消息关联没有足够收益。项目中的 WebSocket 主要用于后端向 React 前端推送长任务进度。

### 15.3 网络中断时怎样保证下游 Agent 不被污染（约 30 秒）

> 非流式调用下，后端不会把半截 LLM 输出交给下游。只有收到完整 HTTP 响应、成功解析 JSON 并通过 Schema 和业务校验后，结果才会写入 `VideoScheme` 或共享状态。当前调用层配置超时并对网络异常和限流进行重试，Planner 对 JSON 解析失败也有重试；重试耗尽后任务记录错误并标为失败，而不是带着不完整方案继续渲染。

## 16. 为什么使用 Multi-Agent，而不只用“单 Agent + Skill”

### 16.1 结论先行

> 单 Agent + Skill 可以完成简单任务，甚至可以按 Skill 派生 Sub-Agent；但 Skill 通常是 Prompt 层的软约束，不能保证长任务中模型一定严格按流程执行。对于本项目的多模态、长链路、高成本视频工作流，采用 Multi-Agent 的核心目的不是增加 Agent 数量，而是把关键流程从“模型记得这样做”转为“系统要求这样做”，获得更强的可控性、可追溯性和失败隔离能力。

### 16.2 Skill 能做什么，不能做什么

Skill 是可复用的领域经验、操作说明或工具能力，例如：

```text
先分析参考片结构，再匹配素材；
开头使用 Hook；
素材不足时优先找同功能替代；
Reviewer 不通过时修改分镜。
```

如果这些内容主要以 Prompt 形式注入给一个总 Agent，它本质上是在告诉模型“应该怎样做”。模型仍然要自己判断：

```text
是否调用该 Skill？
何时调用？
传入哪些上下文？
Skill 的结果是否可信？
是否要遵守 Reviewer 反馈？
是否已经可以结束？
```

因此 Skill 是**软约束**，不是传统程序里的强制 `if/else` 或状态机。长任务、复杂上下文或用户的临时指令都可能让模型出现：

- 漏调或错调 Skill；
- 跳过“素材分析/审核”等关键步骤；
- 错误理解某个 Skill 的适用条件；
- 忘记前面约定的执行顺序；
- 忽略 Sub-Agent 或 Reviewer 的中间反馈；
- 把未经校验的自然语言结果直接交给渲染层。

### 16.3 “Skill 派生 Sub-Agent”为什么仍不够

假设一个总 Agent 根据 Skill 派生 Analyst、Planner、Reviewer 等 Sub-Agent：

```text
总 Agent
  → 判断是否创建某个 Sub-Agent
  → 决定传入什么上下文
  → 决定是否检查其输出
  → 决定下一步调用谁
  → 决定何时停止
```

关键控制权仍由总 Agent 的自然语言决策掌握，因此仍可能发生：

```text
没有创建 Material Manager
→ Planner 在缺少素材库存时硬生成分镜

Reviewer 返回“不通过”
→ 总 Agent 忽略反馈，直接调用渲染

Analyst 输出不完整 Gene
→ 总 Agent 未校验，继续进入下游
```

如果这些“Sub-Agent”有独立角色 Prompt、独立上下文、独立工具集、独立结构化产物和明确交接，那么从系统设计角度，它已经是 Multi-Agent；名称叫 Skill 还是 Sub-Agent 不改变这一点。

判断是否是 Multi-Agent，不看函数名字，而看是否存在独立的：

```text
职责边界 + 上下文边界 + 工具边界 + 输出契约 + 失败归因边界
```

### 16.4 单 Agent + Skill 与 Multi-Agent 的关键差异

| 维度 | 单 Agent + Skill | Multi-Agent + Harness |
|---|---|---|
| 流程控制 | 主要依赖主 Agent 理解并遵守 Prompt | Graph/状态机/条件边约束关键路径 |
| 角色上下文 | 容易积累为一个很长的大上下文 | 各角色只拿当前阶段必要信息 |
| 工具能力 | 主 Agent 往往持有较多工具 | Tool Scoping：按角色最小授权 |
| 中间产物 | 可能是对话历史或非结构化文本 | Gene、Inventory、`VideoScheme`、Review 等结构化契约 |
| 错误定位 | “最终结果不好”但难判断哪里错 | 可定位分析、规划、渲染、评测中的具体阶段 |
| 失败处理 | 主 Agent 自己决定是否重试/忽略 | Schema 门禁、业务校验、回环、最大迭代、显式失败 |
| 适用任务 | 简单、短链路、低风险、线性任务 | 多阶段、异构、高成本、需审核/人机协作任务 |
| 代价 | 调用少、简单、成本低 | 协调复杂、调用更多、延迟/成本更高 |

这里“上下文过长”应准确表述为：**上下文膨胀、信息干扰和指令冲突会降低模型在当前任务上的聚焦和稳定性。** Multi-Agent 不会神奇地消灭所有信息，但可以按角色做最小上下文注入。例如 Planner 只需要 Gene、素材库存、偏好、相关 Skill 和 Reviewer 反馈，而不应读取所有原始日志、渲染命令和无关媒体细节。

### 16.5 本项目如何将软约束变成可执行的控制

本项目的 Multi-Agent 设计不是“七个 Prompt 串起来”，而是使用 Harness 将关键行为约束住：

```text
ViralEngineState：共享且结构化的运行期状态
VideoScheme：规划、编辑、审核、渲染共用的中间表示
角色与 Tool Scoping：不同角色只拥有必要能力
Graph 条件路由：决定节点间的合法流转和审核回环
Schema / 业务校验：拒绝不完整、非法、不属于当前项目的产物
Reviewer：生成者与评估者分离，失败后反馈 Planner
最大迭代次数：防止无限再规划
日志、产物与评测报告：支持定位和复盘
人工确认点：最终渲染前由用户确认分镜
```

理想的关键门禁逻辑是：

```text
没有 source_gene 或 material_inventory
→ 不允许 Planner 进入生成方案阶段

VideoScheme 未通过 JSON / Schema / 业务校验
→ 不允许 Renderer / Assembler 渲染

Reviewer 不通过
→ 回到 Planner，而不是直接交付

超过最大迭代次数
→ 显式失败并记录原因，而不是无限循环

MP4 不可解码
→ 不允许任务标为 success
```

注意：Multi-Agent 本身不自动保证可靠。如果只是 Agent A 用自由文本呼叫 Agent B，再由 B 自由文本呼叫 C，没有状态、契约、校验和终止条件，只是把一个大 Agent 的不确定性拆成多个小 Agent。真正的可靠性来自上面的 Harness。

### 16.6 为什么本项目不把所有事情都强行 Agent 化

Multi-Agent 有成本：更多 LLM 调用、更多延迟、更高 Token 成本，以及节点协调、状态同步、评测和调试复杂度。

因此合理的选择是混合式架构：

```text
需要语义理解、创作决策、开放式反馈的步骤
→ 适合 Agent / LLM

需要确定性执行、文件写入、时长计算、媒体渲染、权限检查的步骤
→ 适合普通代码、Schema、状态机、FFmpeg/Remotion
```

这也是当前 Web 主链路采用分阶段脚本与人工确认，而不是让所有步骤都由 LangGraph 自主决定的原因。

### 16.7 面试回答（约 90 秒）

> 单 Agent 加 Skill 可以完成简单任务，也能通过 Skill 派生 Sub-Agent；但 Skill 大多是 Prompt 层的软约束，不能保证长任务中模型一定按既定顺序执行、不会漏调或错调 Skill，也不能保证它会正确检查和使用 Sub-Agent 的中间结果。随着任务变长，主 Agent 还容易出现上下文膨胀、目标漂移和错误难归因的问题。
>
> 因此我们使用 Multi-Agent 不是为了增加角色数量，而是按输入上下文、输出产物、工具边界和评价标准拆分职责。Analyst 输出参考片的 Structure Gene，Material Manager 输出素材库存，Planner 生成 `VideoScheme`，Renderer、Creative 和 Assembler 分别处理渲染策略、素材缺口和媒体合成，Reviewer 独立审核并反馈再规划。角色之间通过结构化状态和 `VideoScheme` 交接，而不是只传自然语言。
>
> 不过 Multi-Agent 本身也不等于可靠。真正的可控性来自 Harness：Graph 路由、结构化状态、Schema 和业务校验、工具权限边界、Reviewer 回环、最大迭代次数、日志、评测和人工确认。这样模型即使出错，也更容易被限制在当前阶段、定位原因、重试或显式失败，而不会让半成品直接污染下游渲染。

## 17. 问题：Skill 如何被发现、沉淀、应用、评估并持续迭代？

### 17.1 先说结论和当前项目边界

Skill 不是从某一条视频中直接“提取”出来，也不是一次任务结束后让 LLM 自由总结一段 Prompt。合理的完整链路是：

```text
在线任务持续运行
→ 宽进严出地收集 Run / Decision Experience
→ 某类相似 Experience 达到样本门槛
→ 离线清洗、归一化、分组和正反例统计
→ 发现“条件—动作—结果”的重复模式
→ LLM 将有统计证据的模式归纳为 Candidate Skill
→ Schema、去重、冲突和可验证性检查
→ 固定测试集 A/B 或消融实验
→ 人工审核
→ Active Skill
```

当前代码已经完成：人工 Editing Skill、Registry、混合路由、按需加载、四层执行追踪、规则验证、Experience 自动抽取、SQLite 增量挖掘、Candidate 生成/校验、固定任务集实验和版本晋升/回滚。已有的基础 `references/*.md` 仍来自人工整理；新 Candidate 只有在达到样本门槛并通过配对实验后，才会生成/更新 Markdown 和 Registry。当前仓库没有真实的数百条线上样本和人工标注结果，所以只能说“学习闭环已经实现”，不能虚构“已从几百条视频验证出稳定 Skill”。

### 17.2 Experience 收集采用“宽进严出”

只要真实任务启动，就可以产生 Run Experience；只有实际发生了某类剪辑决策，才产生对应的 Decision Experience。收集阶段不根据分数高低提前删除数据，也不因为 Skill 没有加载、没有声明或验证失败就丢弃记录。

```text
任务创建
→ 建立 Run Experience 空壳
→ Analyst 写入 Gene
→ Material Manager 写入脱敏 MaterialGene
→ SkillRouter 写入 selected / loaded
→ Planner 写入实际 VideoScheme 和剪辑动作
→ Verifier 写入 declared / verified
→ Reviewer 写入方案分项结果
→ Renderer / 成片评测写入技术和视觉结果
→ 成功、失败或取消时 Finalize
```

收集阶段主要做四件事：

1. 将离散产物整理成统一 Schema；
2. 记录字段是否完整、任务运行到哪个阶段；
3. 去重并标记真实、Mock、重试、失败和取消任务；
4. 删除或隔离不应进入长期经验库的原素材路径、人脸、声纹、精确位置等隐私。

收集阶段不做这些事：

- 不因为低分就删除；
- 不因为 `verified=false` 就删除；
- 不因为没有加载现有 Skill 就删除；
- 不把一次高分直接升级成 Skill；
- 不把全部原始视频、抽帧和运行日志塞进 Experience；
- 不让 LLM 修改实际发生过的条件、动作和结果。

### 17.3 Run Experience 与 Decision Experience

| 类型 | 什么时候产生 | 保存什么 | 用途 |
|---|---|---|---|
| Run Experience | 真实任务一启动就可以建立 | 执行阶段、成功/失败/取消、产物覆盖、错误与耗时 | 稳定性、阶段覆盖和运行评测 |
| Decision Experience | 实际产生了某类剪辑决策时 | 条件、实际动作、执行状态、分项结果和证据 | 评估已有 Skill、发现新 Skill |

如果任务在素材分析阶段就失败：

```text
有 Run Experience
没有 VideoScheme
没有实际 Hook / Rhythm / Transition 决策
因此没有对应的 Decision Experience
```

一条正常视频任务则可能产生：

```text
1 条 Run Experience
+ 1 条 Hook Decision Experience
+ 1 条 Rhythm Decision Experience
+ 若干条 Transition Decision Experience
+ 若干条 Material Matching Decision Experience
+ 1 条 Subtitle Decision Experience
```

### 17.4 一条 Decision Experience 长什么样

下面使用 JSONC 讲解；`//` 是中文注释，真正写入 JSON 文件时需要去掉注释。

```jsonc
{
  // 本次视频生成任务的唯一编号，用于回查原始证据
  "run_id": "run_001",

  // 本条记录描述的是哪一类剪辑决策
  "decision_type": "hook",

  // 当时在什么条件下做决策
  "conditions": {
    // 视频类型：旅行 Vlog
    "video_type": "travel_vlog",

    // 原来的开场吸引力较弱
    "original_hook_strength": "weak",

    // 用户素材中存在运动感较强的镜头
    "has_motion_material": true,

    // 用户素材中存在风景镜头
    "has_landscape_material": true,

    // 目标视频希望采用较快节奏
    "target_rhythm": "fast"
  },

  // Planner 最终采取了什么实际剪辑动作
  "action": {
    // 开场选择运动风景素材
    "opening_material_type": "motion_landscape",

    // 第一镜头持续 1.2 秒
    "first_shot_duration": 1.2,

    // 是否在第一个明显音乐节拍附近切镜头
    "cut_near_first_beat": true,

    // 前 3 秒内是否使用字幕或文字 Hook
    "subtitle_in_first_3s": true
  },

  // 已有 Skill 的选择、注入和执行情况
  "execution": {
    // Router 是否判断需要该 Skill
    "selected": true,

    // Skill 内容是否实际注入 Planner
    "loaded": true,

    // Planner 是否声明采用
    "declared": true,

    // 方案是否真正满足可观察规则
    "verified": true
  },

  // 采用这些动作后的结果
  "outcome": {
    // Reviewer 的 Hook 维度分数
    "hook_score": 9.0,

    // Reviewer 的节奏维度分数
    "rhythm_score": 8.5,

    // 最终视频是否渲染成功
    "render_passed": true,

    // 成片是否出现黑屏
    "black_frame": false
  },

  // 原始证据位置与生成版本，用于回查而非全部注入 LLM
  "evidence": {
    "scheme_path": "planner/scheme_final.json",
    "evaluation_path": "evaluation/skill_evaluation.json",
    "schema_version": "1.0.0"
  }
}
```

这还不是 Skill，只是一条事实证据。它表达的是：在某种视频和素材条件下，系统采取了某些真实动作，这些动作是否正确执行，以及结果如何。

### 17.5 第一轮“过滤”不是删除，而是分类建分析视图

假设积累了 100 条 Experience，正确做法不是把失败、低分、未加载的数据删掉，而是根据分析目的分池：

```text
100 条 Experience
├── 字段损坏、无法恢复
├── 任务中途终止
├── selected=true、loaded=false
├── loaded=true、declared=false
├── declared=true、verified=false
├── verified=true、效果较好
├── verified=true、效果较差
└── 没有使用已有 Skill，但存在明确实际动作
```

| 数据状态 | 是否从原始库删除 | 主要用途 |
|---|---|---|
| 条件、动作和结果都缺失且无法恢复 | 不进入效果挖掘；保留最小错误记录 | 数据质量诊断 |
| 任务中途终止 | 保留 | 系统稳定性与阶段失败分析 |
| `selected=true, loaded=false` | 保留 | Skill 文件读取、Prompt 注入和编排故障 |
| `loaded=true, declared=false` | 保留 | 路由是否过宽、Planner 是否理解/采用 |
| `declared=true, verified=false` | 保留 | 指令清晰度、Schema 和执行合规性 |
| `verified=true` 且高分 | 保留 | 正例与候选策略证据 |
| `verified=true` 且低分 | 保留 | 反例、不适用边界和潜在副作用 |
| 未加载已有 Skill但实际动作明确 | 保留 | 对照组或全新 Skill 发现 |

真正需要排除出创作效果分析的，主要是：无法知道条件/动作/结果的数据、无法区分真实与 Mock 的数据、重复数据，以及缺失目标分项评测且无法补算的数据。即使排除，也尽量只从某个分析视图排除，不随意物理删除原始审计记录。

### 17.6 评估已有 Skill 与发现新 Skill 是两件事

评估已有 Skill 时，需要研究：

```text
selected → loaded → declared → verified → outcome
```

如果 `loaded=false`，不能说该 Skill 导致结果好或坏，因为 Planner 根本没有看到它；但这条数据仍可诊断注入链路。

发现新 Skill 时，不能只看已有 Skill 是否 `verified`。Planner 可能在没有任何现有 Skill 指导时，自主产生了一个反复有效的新动作，例如：

```jsonc
{
  // 当前没有一个已有 Skill 被选中或加载
  "selected_existing_skill": false,

  // 但是最终方案确实出现了可观察动作
  "observed_action": {
    "opening_material": "motion_landscape",
    "first_shot_duration": 1.1,
    "cut_near_first_beat": true
  },

  // 结果较好
  "hook_score": 9.1
}
```

如果类似动作在多个相似任务中重复有效，它反而可能是新 Candidate Skill 的来源。因此要区分：

```text
Skill verified：已有 Skill 是否正确落地
Action observed：某个具体剪辑动作是否真实发生
```

新 Skill 挖掘关注的是：条件是否完整、动作是否可观察、结果是否可评估，而不要求该动作以前已经属于某个 Skill。

### 17.7 几百条 Experience 后具体怎么处理

不是按“总数达到 500 条”就自动总结，而是看某一类相似决策是否达到有效样本门槛。例如：

```text
500 条 Decision Experience
├── Hook：100 条
│   ├── 旅行 Vlog 弱 Hook：30 条
│   ├── 人物口播 Hook：25 条
│   └── 其他场景：45 条
├── Rhythm：120 条
├── Transition：100 条
├── Subtitle：80 条
└── Material Matching：100 条
```

如果“旅行 Vlog + 弱 Hook + 有运动素材 + 快节奏”只有 3 条，即使总量有 500 条，也不足以产生可信 Skill。真正的处理流程是：

#### 第一步：按决策类型分类

```text
hook / rhythm / emotion / transition / subtitle /
material_matching / structure_adaptation
```

不同类型使用不同目标指标，例如 Hook 看 `hook_score`，节奏看 `rhythm_score`，素材匹配看功能适配和素材覆盖。

#### 第二步：归一化条件和动作

不同任务可能使用这些近义表达：

```text
moving_landscape / dynamic_scenery / 运动风景 / 动态山景
```

需要统一为：

```text
motion_landscape
```

连续值也要分桶：

```text
first_shot_duration
├── very_short：小于 0.8 秒
├── short：0.8～1.5 秒
├── medium：1.5～2.5 秒
└── long：大于 2.5 秒
```

第一版应优先用确定性字典、枚举和区间规则归一化；只有自由文本难以归一时，才使用 LLM 或 Embedding 辅助。

#### 第三步：按“条件 + 动作指纹”分组

```text
条件组：
travel_vlog + weak_hook + motion_material_available + fast_rhythm

动作 A：
motion_landscape + short_duration + beat_cut

动作 B：
static_landscape + long_duration + no_beat_cut
```

然后统计：

| 条件 | 动作 | 样本数 | 平均 Hook 分 | 技术通过率 |
|---|---|---:|---:|---:|
| 旅行 Vlog、弱 Hook、有运动素材 | 动作 A | 14 | 8.8 | 92% |
| 旅行 Vlog、弱 Hook、有运动素材 | 动作 B | 8 | 7.2 | 88% |

#### 第四步：计算候选证据

```text
support：满足条件并采用该动作的有效样本数
verified_rate：声明采用后真正通过规则验证的比例
lift：同类条件下，采用动作与未采用动作的平均结果差
stability：该规律在不同项目/子场景是否方向一致
side_effect：是否损害其他维度、成功率、延迟或成本
```

示例：

```text
使用运动短镜头开场：Hook 平均分 8.8
同类条件未使用该动作：Hook 平均分 7.3
观察性 lift = 1.5
```

这个 lift 只是候选证据，不是因果结论；因为素材质量、模型波动和其他 Skill 仍可能影响结果。

#### 第五步：达到门槛后才生成 Candidate

可以先使用示例门槛：

```text
同类有效样本数 >= 15
覆盖不同项目数 >= 5
verified_rate >= 80%
观察性 lift >= 0.5
技术失败率没有明显上升
没有严重负面指标
```

这些阈值不是当前既定事实，需要在真实数据上校准。

### 17.8 普通代码与 LLM 各负责什么

普通代码负责：

```text
Schema 校验
去重
Mock/真实任务标记
质量过滤
字段归一化
条件与动作分组
样本计数
均值、通过率和 lift 计算
正例、普通案例和反例抽样
```

LLM 只在统计规律已经出现后负责：

```text
把多个结构化案例归纳成适用条件
把动作指纹整理成可执行步骤
根据失败反例总结不适用条件
生成简洁的 name / description
提出可观察 validation_rules
```

不采用：

```text
几百条完整 Experience
→ 一次性全部塞给 LLM
→ 让模型自由决定有什么规律
```

而采用：

```text
程序发现有证据的重复模式
→ 只给 LLM 统计摘要和少量代表性正反例
→ LLM 结构化归纳 Candidate Skill
```

### 17.9 什么值得进入 Skill，什么只留在证据库

一个正式 Skill 的核心公式是：

```text
Skill = 适用条件 + 可执行动作 + 不适用边界 + 验证规则
```

| 内容 | 是否进入 Skill 正文 |
|---|---|
| 适用条件 | 是 |
| 具体执行步骤 | 是 |
| 不适用条件和冲突优先级 | 是 |
| 可观察验证规则 | 是 |
| 少量正例和反例 | 可选 |
| Skill ID、版本、状态 | 进入 Registry |
| 样本量、实验编号、来源摘要 | 进入 Registry/Evidence 元数据 |
| 几百条完整 Experience | 否，留在证据库 |
| 用户原视频、音频、抽帧 | 否 |
| 用户素材真实路径与身份信息 | 否 |
| 完整 Reviewer 报告 | 否，保留引用 |
| `run_001` 的单次高分 | 否，只是一条证据 |

下面这些不能直接叫 Skill：

```text
“西湖照片适合放第一镜”       → 当前任务的具体决策
“mat_001 应该放在开头”        → 当前素材引用
“run_001 的 Hook 得分为 9”    → 评测证据
“让视频更高级”                → 不可执行、不可验证的空泛描述
“使用某条 FFmpeg 命令”        → 工程 Tool/运行策略，不是 Editing Skill
```

可抽象的 Skill 则是：

```text
当旅行 Vlog 的 Hook 较弱，且存在运动感较强的风景素材时，
前 3 秒优先使用 0.8～1.5 秒的运动镜头，并尽量在首拍附近切换；
慢节奏治愈叙事或没有运动素材时不强制采用；
通过首镜头素材类型、时长和前三秒信息密度进行验证。
```

### 17.10 可能沉淀出的具体 Skill

当前七个 Skill 更像知识家族，自动挖掘产生的应是更具体、可测试的场景化子 Skill：

```text
video-editing
├── hook
│   ├── travel-motion-opening-hook
│   ├── static-photo-information-hook
│   └── spoken-quote-opening-hook
├── rhythm
│   ├── pre-climax-progressive-acceleration
│   └── photo-duration-alternation
├── material-matching
│   └── functional-establishing-substitution
├── structure-adaptation
│   └── preserve-function-when-material-missing
├── emotion
│   ├── emotion-climax-build-up
│   └── healing-ending-closure
├── transition
│   ├── emotion-aware-soft-transition
│   └── high-energy-impact-transition
└── subtitle
    ├── info-shot-subtitle-reinforcement
    └── first-three-seconds-title-packaging
```

几个具体例子：

| Candidate Skill | 适用条件 | 动作 | 验证方式 |
|---|---|---|---|
| 旅行 Vlog 运动镜头开场 | 弱 Hook、有运动风景素材、快节奏 | 前 3 秒使用短运动镜头，首拍附近切换 | 首镜头类型、时长、前三秒 Hook |
| 高潮前递进加速 | Gene 有高潮，高潮前有足够镜头 | 高潮前逐步缩短镜头，高潮保留展示时间 | 镜头时长趋势、高潮位置 |
| 场景建立功能替代 | Gene 要 establishing，但没有同类素材 | 用宽景、地标、环境素材替代具体物体 | 镜头功能与 adaptation 记录 |
| 治愈型柔和转场 | 情绪连续、能量较低 | 使用 fade/dissolve/blur，避免 glitch | 转场合法性、重复率、情绪匹配 |
| 信息镜头字幕强化 | `info` 镜头且画面信息不足 | 提炼短字幕并保证阅读时长 | 字幕存在、长度和持续时间 |

这些名称和规则只是目标设计示例，不代表当前仓库已经自动生成了这些子 Skill。

### 17.11 Candidate Skill 的结构

```jsonc
{
  // 候选 Skill 的唯一编号
  "skill_id": "travel-motion-opening-hook",

  // 目前只是候选，正常 Router 不应自动启用
  "status": "candidate",

  // 告诉混合 Router：这个 Skill 做什么、什么时候考虑
  "description": "旅行Vlog开场Hook较弱且存在运动素材时，使用运动镜头短开场",

  // 适用条件
  "applicable_conditions": {
    "video_type": "travel_vlog",
    "hook_strength": "weak",
    "motion_material": "available",
    "target_rhythm": "fast"
  },

  // Planner 可执行的动作
  "instructions": [
    "前3秒优先使用运动感较强的风景素材",
    "首镜头控制在0.8至1.5秒",
    "尽量在首个明显音乐节拍附近切换"
  ],

  // 从低分和失败反例中总结出的边界
  "negative_constraints": [
    "没有运动素材时不强制使用",
    "慢节奏治愈型叙事不优先使用",
    "不能覆盖Reference Gene的关键镜头功能"
  ],

  // 后续如何检查 Planner 是否真正执行
  "validation_rules": [
    "opening_uses_motion_material",
    "first_shot_duration_is_short",
    "cut_near_first_beat"
  ],

  // 历史统计只能作为候选证据
  "evidence": {
    "sample_count": 24,
    "verified_count": 18,
    "average_score": 8.8,
    "baseline_score": 7.3,
    "observed_lift": 1.5,
    "experiment_status": "not_started"
  }
}
```

真正交给 Planner 的主要是 description、适用条件、动作、负面约束和验证规则；大量来源 Experience 继续留在证据库，通过 ID 回查，不进入每次 Prompt。

### 17.12 Candidate 如何变成 Active Skill

```text
draft
→ candidate
→ experiment
→ active
→ deprecated
```

Candidate 首先检查：

- Schema 是否完整；
- 是否具体、可执行、可验证；
- 是否与已有 Skill 重复；
- 是否与 Gene 优先级或已有 Skill 冲突；
- 是否只是某一条特殊视频的偶然经验；
- 是否有足够来源和正反例。

然后在固定任务集上做：

```text
同一批参考视频、素材、模型和 Prompt
├── A 组：不启用 Candidate Skill
└── B 组：启用 Candidate Skill
```

比较 Reviewer 分项、人工盲评、成片技术质量、任务成功率、成本和延迟。B 组在足够样本上稳定提升且没有严重副作用后，再人工审核升级为 `active`。升级时需要生成/更新 Registry 条目和对应 Markdown；当前混合 Router 的语义层可根据 description 补充命中，若需要确定性必选，还应把适用条件接入规则或改造为 Registry 驱动路由。

### 17.13 数据量增大后的存储和增量处理

不把几百条 Experience 全部塞给 LLM，也不每次重新处理所有原视频。推荐：

```text
原始任务产物：按保留策略归档/删除
Experience JSON：保留结构化证据
SQLite/PostgreSQL：保存轻量索引和统计字段
Candidate Repository：保存候选、版本与实验结果
```

索引至少记录：

```text
experience_id / run_id / decision_type
conditions / action_signature / execution_status
reviewer_scores / render_passed
processed / cluster_id / miner_version / created_at
```

每次离线任务只处理 `processed=false` 的新增数据：

```text
昨天已处理 500 条
+ 今天新增 30 条
→ 只归一化和分组新增 30 条
→ 更新已有分组的 support、均值、通过率和 lift
→ 重新判断哪些分组达到 Candidate 门槛
```

用户原视频主要服务当前任务，长期挖掘默认只保留脱敏 MaterialGene、实际剪辑动作、评测结果和证据引用；Embedding 也不天然匿名，仍要受权限和保留策略约束。

### 17.14 已实现的离线组件划分

```text
skills/experience.py
→ 自动抽取 Run / Decision Experience，生成任务级 JSON，并幂等写入 SQLite

skills/mining.py
→ 归一化条件与动作；过滤未加载、未声明、未验证和缺结果数据；增量更新分组统计

skills/candidates.py
→ 生成 Candidate，执行 Schema、重复、同条件冲突和可验证性检查

skills/experiments.py
→ 固定任务集、配对 A/B / 消融试验、结果记录和质量/胜率/成本/时延分析

skills/lifecycle.py
→ 晋升门禁、旧版本归档、显式回滚和 routing_weight 保守学习

skills/pipeline.py
→ 提供 ingest / mine / experiment / promote / rollback / learn-weights 命令入口
```

当前 P0 没有先上向量数据库，而是使用 SQLite、明确字段、规则分桶和可审计门禁；自由文本规模增大后再增加 Embedding 聚类。Candidate 目前采用确定性模板把统计模式转成结构化策略，避免 LLM 凭空发明规则；以后可以让 LLM 负责语言归纳，但统计门槛和实验门禁仍由普通代码控制。

### 17.15 Candidate 通过后，怎样发布成可用 Skill

Candidate 通过 Schema、去重、冲突检查、A/B 或消融实验和人工审核后，不能只把 `status` 改成 `active`；还需要形成机器可路由与 Planner 可阅读的两层产物。

#### 第一层：Registry 中的机器可读契约

```jsonc
{
  // Router 和评测系统使用的稳定 ID
  "id": "travel-motion-opening-hook",

  // 每次修改规则都应产生新版本，不能静默覆盖
  "version": "1.0.0",

  // 只有 active 才能进入正常任务路由
  "status": "active",

  // 给语义 Router 判断“做什么、什么时候用”
  "description": "旅行Vlog开场Hook较弱且存在运动素材时，使用运动镜头短开场",

  // 候选适用阶段和镜头功能
  "applicable_stages": ["planning", "opening"],
  "applicable_shot_functions": ["hook"],

  // Verifier 用于检查 Planner 是否真的执行
  "validation_rules": [
    "opening_uses_motion_material",
    "first_shot_duration_in_range",
    "cut_near_first_beat"
  ],

  // 便于追溯来源，但不把全部 Experience 塞进每次 Prompt
  "evidence": {
    "experiment_id": "exp_skill_001",
    "source_experience_count": 24
  }
}
```

#### 第二层：给 Planner 阅读的 Markdown

```text
references/travel-motion-opening-hook.md
├── 适用条件
├── 推荐动作
├── 不适用条件
├── 与 Gene 冲突时的优先级
├── 正例/反例
└── 验证规则解释
```

Registry 回答“它是谁、是否启用、什么时候考虑、怎么验证”；Markdown 回答“具体怎么做”。证据库继续保存来源 Experience 和实验报告，不全部进入 Skill 正文。

当前项目的 Registry 与 reference 已具备这种分层。现有七个基础 reference 是人工整理的；生命周期管理器已经能在候选通过门禁后自动更新 Registry、生成 Markdown、归档旧版本并回滚。当前缺少的是图形化人工审批界面，命令行晋升仍是显式的发布动作。

### 17.16 新任务来了以后，Skill 怎么被选择

发布为 `active` 后，Skill 才能进入下一次任务的混合路由。当前项目的正式规划路径是：

```text
用户目标
+ Reference Gene
+ 脱敏 MaterialGene / MaterialInventory 摘要
+ 当前任务阶段
        ↓
第一层：确定性 Gene 规则路由
        ↓
得到不可被 LLM 删除的必选 Skill
        ↓
第二层：LLM 语义补充路由
        ↓
结合 Registry 的 id / description 补充 active Skill
        ↓
合并、去重、状态校验
        ↓
得到最终 SkillPlan
```

#### 确定性层负责稳定性

当前 `SkillRouter` 根据 Gene 的镜头功能映射：

```text
hook → hook
establishing → material-matching + structure-adaptation
climax → emotion + rhythm
transition → transition
info → subtitle
closing → emotion + subtitle
```

结构迁移还会默认加入 `structure-adaptation`。这些结果是规则必选集合，保证明显的关键 Skill 不会因 LLM 波动而漏掉。

#### 语义层负责补充规则未覆盖的需求

语义路由只看到：

```text
用户目标
Gene 结构摘要
最多一定数量的脱敏素材特征
Registry 中各 Skill 的 id 和 description
确定性层已经选中的 Skill
```

它不会读取用户原素材路径和个人知识全文，也不会一开始加载全部 Skill Markdown。LLM 只能增加 `active` Skill，不能删除或覆盖确定性结果；调用失败时，`routing_mode` 记录为 `hybrid_fallback_deterministic`，任务继续使用规则结果。

#### 当前新 Skill 接入路由的边界

一个新 Skill 要能被语义层发现，需要：

```text
Registry 中有 active 条目
+ references 中有对应 Markdown
+ description 能准确说明“做什么、什么时候用”
```

如果还希望它成为确定性必选项，当前实现仍需要更新 `SHOT_FUNCTION_TO_REFS` 等映射；Registry 的 `applicable_shot_functions` 尚未完全取代硬编码规则。后续可以继续改成 Registry 驱动的确定性路由，避免两处配置同步。

### 17.17 为什么仍然叫渐进式加载

混合路由不是先把所有 Skill 正文交给 LLM。它分三层：

```text
第一层：轻量目录
Registry 的 id / description / status / version
→ 用于发现和选择

第二层：完整 Skill 说明
只有最终命中的 references/*.md
→ 注入 Planner

第三层：来源证据和扩展资源
Experience、实验报告、脚本或更多参考资料
→ 需要诊断或复盘时才读取
```

这和 Claude Code/Codex 的“元数据常驻、SKILL.md 命中后加载、references/scripts 再按需读取”思想相似；区别是本项目不仅根据用户文本语义匹配，还先用 Reference Gene 做领域确定性路由。

渐进式加载的价值：

- 减少 Prompt 长度和 Token 成本；
- 避免字幕、转场、Hook 等无关知识互相干扰；
- 让每次注入都有明确触发原因；
- 便于统计某个 Skill 被选择、采用和验证的全过程；
- 失败时可以降级到确定性集合。

### 17.18 Skill 被选中后，怎样真正应用到视频规划

Router 输出 `SkillPlan`，例如：

```jsonc
{
  // 本次使用混合路由
  "routing_mode": "hybrid",

  // 最终命中的 Skill
  "references": [
    "structure-adaptation",
    "hook",
    "travel-motion-opening-hook"
  ],

  // 每项都记录版本、选择来源和触发原因
  "decisions": [
    {
      "skill_id": "hook",
      "skill_version": "1.0.0",
      "selected_by": "deterministic_rule+llm_semantic",
      "triggers": [
        "Gene 含 hook 镜头功能",
        "LLM 根据用户需求、Gene 与素材上下文判断相关"
      ]
    }
  ]
}
```

`collect()` 随后只读取这些命中的 Markdown，组成 `skill_context`，再和以下内容一起进入 Planner：

```text
Reference Gene：本次迁移什么结构
MaterialInventory：当前有哪些可用素材
用户要求：明确偏好和约束
Editing Skill：在当前素材条件下怎么剪好
Reviewer 反馈：迭代时具体修改什么
```

Planner 最终输出结构化 `VideoScheme`，包括：

- 每个分镜使用什么素材；
- 镜头功能、时长、字幕和转场；
- Gene 引用；
- Skill 引用；
- 素材替代与结构适配说明。

决策优先级始终是：

```text
用户显式要求
> Reference Gene 硬约束
> Editing Skill 建议
> 模型自由发挥
```

Skill 是可复用策略，不允许覆盖用户明确要求和 Gene 的关键结构。LangGraph 首轮路由结果还会写入共享 `skill_plan`，Reviewer 回环继续复用，避免同一任务每轮重新语义路由而产生 Skill 集合漂移。

### 17.19 怎样知道 Skill 有没有被真正应用

“Router 选中了”不能等于“Planner 用好了”。当前项目把全过程拆成四层：

| 状态 | 谁产生 | 含义 | 失败时优先排查 |
|---|---|---|---|
| `selected` | SkillRouter | Router 判断当前任务需要该 Skill | 路由条件、description、Gene 映射 |
| `loaded` | 编排/Prompt 层 | 完整 Markdown 确实注入 Planner | 文件读取、active 状态、上下文传递 |
| `declared` | Planner / VideoScheme | Planner 或具体分镜明确声明采用 | Prompt 清晰度、Planner 遵循、适用性 |
| `verified` | SkillVerifier | 方案通过可观察规则检查 | Scheme 字段、动作是否真实落地 |

例如：

```jsonc
{
  "skill_id": "transition",

  // Router 判断需要转场知识
  "selected": true,

  // transition.md 已注入 Planner
  "loaded": true,

  // Planner 声称采用了该 Skill
  "declared": true,

  // 但实际转场字段为空，因此验证失败
  "verified": false,

  "failed_rules": ["transition_config_is_empty"]
}
```

归因关系：

```text
没有 selected
→ 路由漏选

selected=true、loaded=false
→ 编排或上下文注入故障

loaded=true、declared=false
→ Planner 未采用、Skill 不适用或描述不清

declared=true、verified=false
→ Planner 只是“口头使用”，实际方案不合规

verified=true、效果仍然差
→ 继续检查 Skill 本身、适用边界、素材、其他决策或渲染
```

四层状态会进入 `VideoScheme.skill_evaluation` 并持久化为 `evaluation/skill_evaluation.json`；它不是只存在于内存中的临时布尔值，而是任务级审计证据。

### 17.20 Skill 应该怎样评估

Skill 评估至少分四层，不能只看最终视频总分。

#### 第一层：路由评估——该不该选

关注：

```text
不同 Gene/素材场景下的选中分布
确定性与语义层各自命中了什么
语义层补充了多少真正有用的 Skill
某 Skill 被选中后是否经常 not_applicable
人工标注下的路由 Precision / Recall（未来）
```

当前可以做选中次数、触发原因和后续采用率统计；若要严格计算路由准确率，还需要一批人工标注“本任务应选哪些 Skill”的基准集。

#### 第二层：链路评估——是否正确送到 Planner

```text
加载率 = loaded_count / selected_count
```

加载率低说明不是 Skill 内容效果问题，而是文件、状态、编排或 Prompt 构建链路有问题。

#### 第三层：执行评估——Planner 是否正确采用

```text
采用率 = declared_count / loaded_count
合规率 = verified_count / declared_count
```

采用率低可能是路由过宽、Skill 描述不清或 Planner 判断不适用；合规率低说明动作没有真正进入 `VideoScheme`，应优化输出 Schema、Prompt 或验证门禁。

不同 Skill 的可观察规则不同：

| Skill | 示例验证内容 |
|---|---|
| Hook | 首镜头功能、前三秒时长、视觉/文字 Hook |
| Rhythm | 镜头时长是否有变化、高潮段落是否存在 |
| Emotion | 情绪标签、递进与高潮位置 |
| Transition | 转场是否合法、是否全部重复 |
| Subtitle | 信息镜头是否有文字、长度是否合法 |
| Material Matching | 素材是否存在、功能替代是否有记录 |
| Structure Adaptation | 结构适配是否有可解释的 adaptation trace |

#### 第四层：结果评估——正确执行后效果如何

把 `verified` 的 Skill 轨迹关联到：

- 10 维方案 Reviewer 的相关分项；
- 最终 MP4 的解码、时长、音轨、黑屏和静帧；
- 分镜抽帧视觉审核；
- 运行成功率、耗时、模型调用和 Token 成本；
- 如果以后增加用户行为数据，还可参考修改幅度、确认、退回和人工盲评。

这里必须坚持：

```text
关联统计 ≠ 因果证明
```

例如“使用 Hook Skill 的任务平均分更高”，可能是因为这批任务本身素材更好，也可能同时使用了 Rhythm Skill。当前 `analytics.py` 只能提供观察性聚合。要证明 Skill 导致提升，必须固定参考视频、用户素材、模型、温度和 Prompt，做有/无该 Skill 的 A/B 或消融实验，并查看不同子场景，而不是只看总平均。

### 17.21 评估结果如何反过来改进 Skill

评估不是生成一份报告就结束，它应驱动不同位置的修正：

| 观察到的问题 | 应修改什么 |
|---|---|
| 本该选择却未 `selected` | 确定性映射、Registry description、适用条件 |
| 经常 selected 但 not applicable | 缩窄适用条件或降低语义误选 |
| selected 但未 loaded | 文件、状态、编排和 Prompt 注入 |
| loaded 但未 declared | Skill 步骤、示例、负面约束或 Planner Prompt |
| declared 但未 verified | VideoScheme Schema、动作表达、验证门禁 |
| verified 但结果经常较差 | Skill 内容、适用边界、版本或路由逻辑 |
| 某些子场景有效、另一些无效 | 拆成更细的场景化子 Skill |
| 新版本效果退化 | 回滚旧版本并标记新版本 deprecated |

因此完整反馈回路是：

```text
Experience
→ Candidate Skill
→ 实验与审核
→ Active Skill
→ 混合路由
→ Planner 应用
→ selected / loaded / declared / verified
→ Reviewer + 成片 + 运行评测
→ 跨任务聚合
→ 调整路由、修改版本、拆分/合并或停用 Skill
→ 新一轮验证
```

Skill 更新时应保留版本和来源证据，不能直接覆盖旧内容：

```text
1.0.0：当前线上稳定版本
1.1.0-candidate：修改适用条件的新候选
1.1.0-experiment：只在实验任务启用
1.1.0：实验通过后成为 active
1.0.0：保留，便于历史回放和回滚
```

### 17.22 从发现到评估的完整数据流

```text
【发现与沉淀】
真实任务执行
→ Run / Decision Experience
→ 脱敏、去重、完整性标记
→ 按决策类型分类
→ 条件与动作归一化
→ 正反例分组与统计
→ Candidate Skill
→ 校验、A/B、人工审核
→ Active Skill + Registry + Markdown

【下一次应用】
用户目标 + Gene + MaterialGene
→ 确定性规则选必需 Skill
→ LLM 根据 description 语义补充
→ active 校验、合并和去重
→ 只加载命中的 Markdown
→ Planner 生成 VideoScheme

【执行追踪】
selected
→ loaded
→ declared
→ verified
→ 保存 skill_evaluation.json

【效果评估】
路由选择与触发原因
+ Planner 遵循度
+ Skill 规则合规性
+ Reviewer 分项
+ 成片技术/视觉结果
+ 运行成功率、成本和延迟
→ 跨任务观察性聚合
→ 固定测试集因果实验

【持续迭代】
修改适用条件 / description / instructions / validation_rules
→ 新版本 Candidate
→ 再实验
→ 晋升、回滚或 deprecated
```

### 17.24 面试回答总结

> 我们不会在单次任务结束后直接让 LLM 生成新 Skill，而是先采用“宽进严出”的方式沉淀 Experience。所有真实任务都会产生 Run Experience；发生了可观察剪辑决策时，再产生 Decision Experience，记录当时的 Gene 和脱敏素材条件、实际剪辑动作、selected/loaded/declared/verified 状态、Reviewer 分项和成片结果。未加载、验证失败和低分数据不会简单删除，它们分别用于注入故障、执行合规、反例边界和对照分析。
>
> 当某一类相似 Experience 达到样本门槛后，离线程序先按决策类型分类，做字段归一化、条件与动作分组，并计算样本量、验证率、成功率和同类观察性差异。程序只对有统计支持的重复模式生成包含适用条件、执行动作、不适用边界和验证规则的 Candidate Skill。当前实现使用确定性模板生成 Candidate；未来即使增加 LLM 做语言归纳，也不能让它绕过统计和实验门禁。
>
> Candidate 需要经过 Schema、去重、冲突检查以及固定任务集的配对 A/B 或消融实验，达到质量提升、胜率、成本和时延门槛后，生命周期管理器才会更新 Registry 和 Markdown，同时归档旧版本以支持回滚。跨任务证据还能用 Beta 平滑学习语义路由权重，但权重不能取消 Gene 确定性规则。项目已经实现这套 P0 闭环和测试，不过真实效果仍需要大规模任务与人工标注校准，不能把代码能力夸成线上业务结论。

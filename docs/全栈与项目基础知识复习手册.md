## 1. 先建立一个完整画面：这个系统到底在做什么

用户提供两类输入：

1. 一条参考 Vlog：希望借鉴它的节奏、叙事顺序、镜头功能和情绪起伏；
2. 用户自己的旅行图片或视频素材：最终成片必须主要使用这些素材，而不是复制参考片画面。

系统把“参考片的表达方式”抽象出来，再结合用户素材生成一个可编辑的分镜方案 `VideoScheme`。用户可以在线修改、确认分镜，之后才执行耗时的最终渲染，并得到视频和评测报告。

可以把它理解为一家数字化视频工作室：

```text
用户（提出目标、上传素材、确认方案）
  │
  ├─ 前端 React：给用户操作界面、展示进度和结果
  │
  ├─ 后端 FastAPI：认证、接收请求、校验权限、记录数据、创建任务
  │
  ├─ 异步任务系统：把耗时分析/渲染从 HTTP 请求中拆出去
  │
  ├─ 视频与 Agent 引擎：分析、规划、生成分镜、渲染、评测
  │
  └─ 数据库 + 文件系统：保存元数据、状态、JSON、素材和 MP4
```

其中 **前端不是 Agent**，**后端也不是 Agent**。Agent 引擎只是后端调用的一个复杂业务能力。完整产品还需要用户界面、任务状态、数据存储、权限控制和媒体交付。

### 1.1 从点击按钮到拿到成片的数据流

```text
浏览器
  │ 1. 登录、创建项目、上传素材（HTTP REST）
  ▼
FastAPI 后端
  │ 2. 身份/归属校验，写入用户、项目、素材、任务记录
  ▼
SQLite + 文件系统
  │ 3. TaskQueue 领取耗时任务
  ▼
分析 / 规划脚本
  │ 4. 提取参考结构、分析素材，生成 VideoScheme 草案
  ▼
数据库与任务目录
  │ 5. 任务进入 awaiting_confirmation，前端展示并允许编辑
  ▼
用户确认
  │ 6. 发起最终渲染任务
  ▼
Remotion / FFmpeg + 评测脚本
  │ 7. 输出 MP4、技术诊断、视觉抽检与运行报告
  ▼
前端任务页（WebSocket 收进度，HTTP 拉最终状态）
```

注意：当前 Web 的“可编辑生成链路”是分阶段脚本编排；独立 CLI 才会启动完整 LangGraph 图。不能说“所有 Web 任务都运行了 Supervisor + 7 个 Agent 的完整图”。后面会专门解释这两个入口的区别。

## 2. Web 开发最基础的分层：前端、后端、数据库和文件

### 2.1 前端是什么

前端（Frontend）就是用户在浏览器中看得见、点得动的部分。本项目的前端采用 React，负责：

- 登录、项目管理、上传参考视频和用户素材；
- 创建任务、展示每个阶段的进度和日志；
- 展示可编辑的分镜，允许用户调整镜头、素材、字幕、转场等；
- 展示最终视频和评测报告；
- 提供助手聊天界面。

前端不应该直接访问数据库、模型 API Key 或本地视频文件。它只负责展示和收集用户操作，再通过 API 请求后端。

### 2.2 后端是什么

后端（Backend）运行在服务器进程中。本项目用 FastAPI 实现，负责：

- 提供 `/api/...` 接口；
- 验证用户身份、判断用户是否拥有某项目/任务；
- 校验请求数据是否符合规则；
- 写数据库、保存上传文件、创建后台任务；
- 调用分析、规划、渲染、评测脚本；
- 将任务进度推送给前端。

一个很好记的划分是：**前端决定“怎么让用户用”，后端决定“这件事能不能做、怎样可靠地做”。**

### 2.3 数据库和文件系统为什么要分开

数据库擅长存储、查询和关联“小而结构化”的数据，例如：

| 类型 | 适合存在哪里 | 本项目例子 |
|---|---|---|
| 用户、密码哈希、角色 | 数据库 | `User` |
| 项目名称、创建者 | 数据库 | `Project` |
| 素材名称、所属项目、文件路径 | 数据库 | `Material` |
| 任务状态、进度、日志、产物路径 | 数据库 | `Task` |
| 原始视频、图片、最终 MP4 | 文件系统/对象存储 | 上传素材、`result.mp4` |
| 较大的 JSON 产物 | 文件系统 | Gene、`VideoScheme`、评测报告 |

不把 MP4 直接塞进 SQLite 的原因是：视频体积大、顺序读写为主、数据库备份和查询都会变重。数据库保存“它在哪里、属于谁、现在是什么状态”，文件系统保存“实际的大文件内容”。

这个方案也有边界：数据库更新成功但文件写入失败，或反过来，都可能出现不一致。当前项目通过阶段状态、日志和产物检查来降低影响，但并没有跨数据库和文件系统的强事务。生产环境可进一步使用对象存储、临时文件、完成标记、补偿清理任务等手段。

### 2.4 一个容易混淆的概念：三种“状态”

本项目至少有三类状态，不能混为一谈：

| 名称 | 在哪里 | 用来做什么 | 示例 |
|---|---|---|---|
| React UI state | 浏览器内存 | 控制页面显示 | 弹窗是否打开、当前选中的分镜 |
| Task 数据库状态 | 后端数据库 | 记录任务真实生命周期 | `pending`、`running`、`success`、`failed` |
| `ViralEngineState` | LangGraph 一次图执行的内存 | Agent 节点间传递工作记忆 | `source_genes`、`material_inventory`、`scheme` |

React 刷新页面后会丢失普通内存状态；数据库状态可恢复；Graph state 是一轮 Agent 图执行的共享上下文，不等于用户长期记忆。

## 3. React 基础：页面为什么能“随数据变化而变化”

### 3.1 React 是什么

React 是构建用户界面的 JavaScript 库。它的核心想法是：**界面 = 数据状态的函数**。当数据变化时，React 重新计算需要展示的界面并更新浏览器 DOM。

传统写法经常是“找到某个 DOM 元素，再手动修改它”；React 更常见的写法是“修改状态，页面自动跟着变”。

```jsx
function TaskStatus({ task }) {
  return <p>当前进度：{task.progress}%</p>
}
```

如果 `task.progress` 从 30 变成 60，组件重新渲染后，页面就显示 60%。

### 3.2 组件、Props、State

1. **组件（Component）**：可复用的 UI 单元，例如任务卡片、分镜编辑器、进度条。
2. **Props**：父组件传给子组件的只读输入。例如 `TaskDetail` 把某个任务传给 `ProgressPanel`。
3. **State**：组件内部会变化的数据。例如当前是否加载中、当前编辑哪一个镜头。

类比：组件像“任务详情页”这台机器；Props 像机器收到的原料；State 像机器内部当前的开关和临时记忆。

### 3.3 受控表单与分镜编辑

分镜编辑器中，输入框、下拉框、镜头列表要和 JavaScript 状态绑定。用户改字幕时，前端先更新本地草稿；点击保存后，才由 HTTP `PUT` 请求发送给后端。

这样做的好处是：用户可以连续修改多个字段再提交，页面也能立即反馈；后端仍然是最终校验者，防止用户绕过前端构造非法请求。

### 3.4 前端路由和接口层

前端“路由”指不同 URL 显示不同页面，例如项目页、任务详情页、助手页。它不同于后端路由：

- 前端路由：决定浏览器显示哪个 React 页面；
- 后端路由：决定服务器用哪个函数处理 `/api/tasks/...` 请求。

前端通常将 API 调用集中在 `src/api.js` 一类文件中，而不是到处手写 `fetch`。这样可以统一：API 地址、Bearer Token、错误处理、返回数据格式。

## 4. HTTP、REST、JSON：浏览器如何向后端办事

### 4.1 HTTP 是什么

HTTP 是浏览器和服务器最常用的通信协议。它的基本模型是：

```text
客户端发请求 Request  →  服务端处理  →  服务端回响应 Response
```

一次请求通常包含：

- URL：请求哪个资源，例如 `/api/tasks/123`；
- Method：要做什么操作；
- Headers：附加信息，例如认证 Token、内容类型；
- Body：提交的数据；
- Status Code：服务器处理结果，例如 200、401、404；
- Response Body：服务器返回的数据，例如 JSON。

### 4.2 REST 不是协议

REST 是一种基于 HTTP 设计业务 API 的风格，不是另一种通信协议。常见约定如下：

| HTTP 方法 | 直观含义 | 例子 |
|---|---|---|
| `GET` | 查询 | `GET /api/tasks/123` |
| `POST` | 创建或触发动作 | `POST /api/projects`、创建渲染任务 |
| `PUT` | 用完整内容更新资源 | `PUT /api/tasks/123/storyboard` |
| `PATCH` | 更新部分字段 | 更新聊天上下文 |
| `DELETE` | 删除 | 删除项目或素材 |

不是说用了这些动词就天然安全或 RESTful；真正关键是权限校验、参数校验、幂等性和错误处理。

### 4.3 JSON 是什么

JSON 是文本形式的结构化数据格式，适合前后端、LLM 和脚本之间交换数据：

```json
{
  "task_id": 123,
  "status": "running",
  "progress": 45,
  "workflow_stage": "planning"
}
```

它很适合传递任务状态和分镜结构；但不适合直接放二进制视频。视频上传需使用 `multipart/form-data`，视频下载则是媒体文件响应。

### 4.4 HTTP 状态码最常见的含义

| 状态码 | 含义 | 项目场景 |
|---|---|---|
| 200 | 请求成功 | 查询到任务、保存分镜成功 |
| 201 | 创建成功 | 创建项目、创建素材记录 |
| 400 | 请求内容不合法 | 参数或业务规则不满足 |
| 401 | 未登录或 Token 无效 | 没有合法身份 |
| 403 | 已登录但无权访问 | 访问他人的项目/任务 |
| 404 | 资源不存在 | 任务 ID 不存在 |
| 409 | 状态/版本冲突 | 分镜 revision 过期 |
| 422 | 数据格式校验失败 | Pydantic 校验请求字段失败 |
| 500 | 服务端内部错误 | 脚本异常或未处理错误 |

尤其要区分 401 和 403：**401 是“你是谁还没证明”，403 是“我知道你是谁，但你不能做这件事”。**

## 5. FastAPI 基础：后端如何定义接口

### 5.1 FastAPI 是什么

FastAPI 是 Python Web 框架。它将 HTTP 请求映射到 Python 函数，并利用类型标注和 Pydantic 做请求/响应校验。

概念示例：

```python
@router.get("/api/tasks/{task_id}")
def get_task(task_id: int, current_user: User = Depends(get_current_user)):
    ...
```

- `@router.get(...)`：这个函数处理 GET 请求；
- `{task_id}`：从 URL 中读取路径参数；
- `task_id: int`：框架会将它校验为整数；
- `Depends(...)`：依赖注入，统一获取当前登录用户；
- 返回值：FastAPI 序列化成 JSON 响应。

### 5.2 Router（路由模块）为什么要拆分

后端不能把所有接口写进一个文件。本项目按业务拆成项目、素材、任务、聊天、认证等 Router。好处是：

- 代码更容易定位；
- 每组接口可以复用认证和校验逻辑；
- 后续扩展不会把一个入口文件写成几千行；
- 接口职责更清楚。

例如任务 Router 关注创建任务、查询任务、分镜保存/确认、WebSocket；项目 Router 关注项目资源；聊天 Router 关注会话和消息。

### 5.3 Pydantic：为什么后端不能相信前端

前端校验是为了用户体验，但任何人都可以绕过网页直接调用 API。因此后端必须再校验。

Pydantic Model 用于定义字段类型、是否必填、取值范围和嵌套结构。例如分镜每一镜的时长、素材 ID、字幕、转场类型都应满足规则。后端校验不通过就拒绝写库/渲染。

这和 Agent 的 `VideoScheme` 校验是同一个工程思想：**模型或外部调用的输出都不可信，进入下一阶段前要先收敛成受约束的数据结构。**

### 5.4 依赖注入是什么

依赖注入（Dependency Injection）不是“自动魔法”，可以理解为：框架在调用业务函数前，先替你准备公共依赖。

在本项目中，典型依赖是：

- 数据库会话；
- 当前登录用户；
- 权限校验。

这样每个接口无需重复解析 Token、连接数据库，且安全规则更集中。

## 6. 认证、授权与密钥：谁能做什么

### 6.1 认证和授权不是一件事

- **认证（Authentication）**：确认请求者是谁，例如登录后解析 JWT Token 得到用户 ID；
- **授权（Authorization）**：确认这个用户是否有权访问指定资源，例如任务是否属于这个用户的项目。

只做认证还不够。例如用户 A 带着自己的合法 Token 查询 `/api/tasks/999`，如果 999 属于用户 B，后端仍然应该拒绝。

### 6.2 JWT 的直观理解

用户登录成功后，后端生成一个有签名的 Token；前端在后续 API 请求中带上：

```text
Authorization: Bearer <token>
```

后端验证签名和过期时间，再识别用户身份。JWT 通常用于“证明身份”，不是存放密码或敏感业务数据的地方。

### 6.3 本项目的安全边界

常规 HTTP 项目/任务/分镜/评测接口会做用户身份与资源归属校验；模型 API Key 加密存储、对外返回时掩码。

但当前任务 WebSocket 端点没有像普通 HTTP 路由那样完成 Token 和任务归属校验。因此，准确的面试表述是：**HTTP 资源接口已做身份和归属校验；实时连接的握手认证与连接约束仍是下一步要补的安全项。**

不要说“系统所有接口绝对安全”。工程上能清楚说明边界，反而比泛泛而谈更加分。

### 6.4 为什么媒体 URL 带 Token 需要谨慎

浏览器原生 `<video>` 标签不方便带自定义 `Authorization` 头，所以有些实现会把 Token 放进媒体 URL 查询参数。这样能播放受保护资源，但 URL 可能被浏览器历史、日志、引用页记录。更稳妥的演进方向是短时效、限资源的签名 URL，或 HttpOnly Cookie 配合 HTTPS、CSP 等安全策略。

## 7. 数据库基础：为什么任务必须持久化

### 7.1 关系型数据库与 SQLModel

关系型数据库把数据组织成表（table）、行（row）和列（column）。例如：

```text
User 1 ── N Project 1 ── N Material
                   └── N Task
```

`1 ── N` 表示一对多：一个用户可以有多个项目，一个项目可以有多个素材和任务。

本项目使用 SQLite 作为轻量关系型数据库，并用 SQLModel 定义 Python 类和数据库表的映射。它的好处是开发简单、单文件部署方便；缺点是高并发、多实例写入能力有限，不应把它描述为生产级分布式数据库。

### 7.2 主键、外键和归属

- **主键（Primary Key）**：唯一标识一条记录，如 `task_id`；
- **外键（Foreign Key）**：指向另一张表的主键，如任务的 `project_id`；
- **归属校验**：通过 Task → Project → User 的关联，确认当前用户能否访问。

这就是为什么权限判断不能只看前端传来的 `user_id`：后端需要从可信 Token 得到当前用户，再沿着数据关系验证资源归属。

### 7.3 任务状态机

任务不是一个布尔值“完成/未完成”，而是会经过多个阶段：

```text
pending → running → awaiting_confirmation → pending → running → success
                                  └──────────────────────────→ failed
```

- `pending`：已创建，等待 worker 领取；
- `running`：分析、规划、渲染等正在执行；
- `awaiting_confirmation`：已经有可编辑草案，等待用户确认，不代表最终成片成功；
- `success`：最终渲染和必要检查完成；
- `failed`：任务失败，日志保留失败原因。

状态机的价值是限制非法跳转、支持恢复和排错。例如用户没有确认分镜时，不能直接进入最终渲染；失败后不能假装成功。

### 7.4 分镜 revision：如何处理“两个地方同时编辑”

用户打开分镜时，会看到一个版本号 `revision`；保存时把它一并提交。后端如果发现数据库里的版本已经变了，就返回 `409 Conflict`，要求客户端刷新后再编辑。

这叫**乐观并发控制**：先假设大多数情况下不会冲突，写入时再检测。它适合编辑冲突较少的场景。

它不等于完整的分布式事务，也不是多人实时协同编辑。当前实现主要是防止旧页面无意间覆盖较新的分镜。

## 8. 文件上传与媒体处理基础

### 8.1 为什么上传不是 JSON

图片和视频是二进制文件，不能高效地直接塞进 JSON。浏览器通常用 `FormData` 发出 `multipart/form-data` 请求：

```text
文件内容 + 文件名 + MIME 类型 + 其他表单字段
```

后端收到后应做：文件类型、大小、归属项目、保存路径、文件名安全等检查。仅信任客户端给出的扩展名或 `Content-Type` 是不够的，生产化还应做内容探测、病毒扫描和配额控制。

### 8.2 编码、封装与解码

- **编码（Codec）**：将原始音视频压缩，例如 H.264、AAC；
- **封装格式（Container）**：将视频流、音频流、元数据装进文件，例如 MP4；
- **解码**：把压缩后的媒体还原为可播放帧/音频样本；
- **转码**：解码后再用另一种参数重新编码。

“生成了一个 `.mp4` 文件”不代表一定能播放，因此成片检查要做探测和解码。

### 8.3 FFmpeg 和 FFprobe 分别做什么

- FFmpeg：处理、裁剪、拼接、转码、渲染、解码验证；
- FFprobe：读取媒体元信息，例如时长、视频流、音频流、编码格式。

本项目中 FFmpeg 既服务于素材/音视频处理，也参与成片技术检查。它不是 LLM，也不负责理解“画面好不好看”。

### 8.4 Remotion 为什么适合这个项目

Remotion 用 React 组件描述视频时间轴、字幕、图层、动画和视觉包装，然后渲染为视频。它适合将结构化 `VideoScheme` 变成可控的视觉成片。

当前 Web 的确认后渲染主路径是 Remotion。独立 Graph 的 Assembler 侧还有更基础的 FFmpeg 智能渲染/拼接回退。要准确区分：**“引擎里有 FFmpeg 回退”不等于“Web 最终渲染自动有 FFmpeg 回退”。**

## 9. 为什么长耗时任务不能一直占着 HTTP 请求

### 9.1 同步接口的问题

登录、查询任务只需毫秒到几秒；视频下载、VLM 分析、Whisper 转写、Remotion 渲染可能持续几十秒到数分钟。

如果浏览器发一个 HTTP 请求后一直等待：

- 容易超时；
- 用户不知道系统是否还活着；
- 连接中断后难以恢复；
- Web 服务器工作线程会被长时间占住。

所以创建任务接口通常立刻返回任务 ID；后台慢慢执行；用户之后查询或订阅任务进度。

### 9.2 `asyncio.Queue`、worker、子进程的角色

当前 `TaskQueue` 是单进程内的 `asyncio.Queue`：

```text
API 创建 Task（数据库为 pending）
  → 放入内存队列
  → 一个 worker 顺序取出
  → 更新 Task 为 running
  → 调用分析/渲染子进程并解析进度
  → 写 Task.progress / logs / status
```

- `asyncio.Queue`：进程内的待办队列；
- worker：持续取任务的后台协程；
- 子进程：运行耗 CPU、独立环境或长脚本的外部命令；
- 数据库：持久记录事实状态；
- WebSocket：把变化尽快通知给前端。

### 9.3 async 不是自动并行

`async` 的主要作用是避免 I/O 等待时阻塞事件循环，不等于任务一定大量并行。

当前项目一个 worker 顺序消费任务，吞吐受到单 worker、模型 API 限流、CPU/内存、视频解码和渲染资源限制。不能说“因为用了 asyncio 所以多个视频任务全部并行”。

### 9.4 当前方案的局限与生产化演进

内存队列的优点是简单，适合单机原型；缺点是：进程重启可能丢失未消费消息，多实例不能共享队列，单 worker 吞吐有限。

生产化可采用 Redis/RabbitMQ 等持久消息队列，加 Celery/RQ/Arq 等 worker 框架，并实现：

- 幂等键，避免重复渲染/重复扣费；
- 重试策略、退避和死信队列；
- 心跳/租约，识别崩溃的 worker；
- 多实例进度广播（pub/sub）；
- 根据任务 CPU/GPU/模型成本做资源调度。

这些是清晰的演进方向，不是当前已完成实现。

## 10. WebSocket、SSE、HTTP：通信方式别混淆

### 10.1 先记层级关系

```text
HTTP 协议
  ├─ REST 风格接口：资源 + GET/POST/PUT/DELETE
  ├─ 普通非流式响应：请求一次，完整返回一次
  └─ SSE：服务端持续单向推送事件（仍建立在 HTTP 上）

WebSocket 协议
  └─ 建连后，客户端和服务端可双向主动发送消息
```

所以 REST 不是协议；“HTTP 非流式”是使用方式；SSE 建立在 HTTP 上；WebSocket 是另一种长连接通信协议。

### 10.2 本项目的三条通信链路

| 链路 | 当前方式 | 传递内容 | 原因 |
|---|---|---|---|
| 浏览器 ↔ 后端业务接口 | HTTP REST | 登录、上传、项目/任务/分镜 CRUD、聊天 | 请求-响应明确，便于校验、鉴权、错误码处理 |
| 后端 → 浏览器任务进度 | WebSocket | 阶段、百分比、日志、成功/失败状态 | 长任务中后端要主动通知前端，避免高频轮询 |
| 后端/Agent → LLM Provider | 普通 HTTP 非流式 POST | 完整 prompt，返回完整文本/JSON | 需先拿到完整结构化结果，才做 JSON/业务校验并进入下一阶段 |

### 10.3 为什么任务进度使用 WebSocket

浏览器创建任务后会打开 `/api/tasks/{id}/ws`，后端在任务进度变化时推送消息。前端可以即时更新进度条和日志，不必每秒钟大量轮询。

不过 WebSocket 是“实时体验层”，数据库 `Task.progress` 和 `Task.logs` 才是可查询、可恢复的事实来源。用户断线重连后仍可通过 HTTP 获取任务最新状态。

### 10.4 为什么 Agent 调 LLM 没有使用 WebSocket

不要把“浏览器到后端的实时进度”与“后端到模型的调用”混为一谈。当前 Planner、Reviewer、聊天服务对 OpenAI-compatible 接口使用的是普通 HTTP 非流式请求：等待模型完整输出后，再解析并校验。

理由包括：

1. Agent 的下一步依赖完整 JSON；半截 JSON 无法可靠做 Schema 校验；
2. 业务是阶段式低频请求，不需要让模型服务持续主动推送双向消息；
3. WebSocket 需要处理心跳、断线重连、请求相关性、消息顺序、多路复用，复杂度更高；
4. 模型供应商本身提供的常见接口是 HTTP `/chat/completions`。

未来若要改善聊天逐字显示，适合在“后端到浏览器”增加 SSE；这不意味着 Agent 内部逻辑也必须改成流式。

## 11. Agent、LangGraph 和 Web 工作流：两条链路要讲准确

### 11.1 什么是 Agent

在这里，Agent 不是简单的一次 LLM 调用，而是一个有清晰职责、输入输出、提示词、可用工具和失败处理方式的专家节点。例如：

- 视频分析师：提取参考片的镜头功能和节奏；
- 素材管家：理解用户素材、建立素材库存；
- 规划师：生成可执行分镜；
- 审核者：检查方案是否保留结构、是否适配素材。

一个 Agent 是否有价值，不看名字是否酷，而看它是否有独立的：**输入上下文、输出产物、工具集合、成功指标和失败归因。**

### 11.2 为什么不只用一个大 Agent

基础流程可抽象为“感知 → 决策 → 执行 → 校验”。但将所有工作交给一个 Prompt 往往会出现：上下文混杂、工具权限过大、输出不可控、失败难定位。

因此项目按职责拆分：

| 阶段 | 为什么要拆 | 如何拆 | 主要产物 |
|---|---|---|---|
| 感知 | 参考片分析与用户素材理解的目标、输入和评价标准不同 | Analyst + Material Manager | Structure Gene、Material Inventory、Gap Report |
| 决策 | Hook、节奏、字幕、转场相互耦合，过度拆分反而丧失叙事一致性 | Planner 统一做全局方案 | `VideoScheme` |
| 执行 | “决定拍什么”与“技术上怎样渲染”有语义鸿沟；缺素材也需独立处理 | Renderer + Creative + Assembler | 渲染策略、补全策略、MP4 |
| 校验 | 方案合理不等于最终 MP4 可播放且画面达标 | Scheme Reviewer + 成片技术/视觉检查 | 分数、反馈、诊断报告 |

### 11.3 LangGraph 在做什么

LangGraph 将节点、共享状态、条件路由和循环表示为一个图。独立 CLI 的完整 Agent 图中：

```text
Supervisor
  → Analyst / Material Manager
  → Planner
  → Renderer / Creative / Assembler
  → Reviewer
  → 通过 / 反馈 Planner 再规划 / 结束
```

Supervisor 是控制平面：读取共享状态、判断当前缺什么、调度下一个专家、控制回环和终止条件。不要说它只是“监控数据流”，也不要说它替所有专家完成业务工作。

### 11.4 `ViralEngineState` 是 Agent 的“共享白板”

Agent 之间当前不是用 HTTP、SSE、WebSocket 或 A2A 互相聊天，而是同一个 LangGraph 进程内通过 `ViralEngineState` 传递结构化状态：

```text
Analyst 写 source_genes
Material Manager 写 material_inventory / gap_report
Planner 读上述信息，写 scheme
Reviewer 读 scheme，写 review_result / feedback
Supervisor 读状态决定路由
```

这是一种共享黑板（shared blackboard）/工作记忆模式。状态里放结构化分析结果、路径、引用和任务描述，不应把原始视频字节或无边界聊天记录全部塞进 Prompt。

### 11.5 Web 路径为什么没有直接跑完整 Graph

Web 产品强调用户先看草案、编辑、确认，再花成本渲染。当前它采用分阶段脚本：分析 → 预生成分镜 → 人工确认 → 渲染 → 评测。

CLI 图则主要表达多 Agent 的研究/编排能力。两者不是谁取代谁，而是面对不同入口：

- Web：产品交互和人机协作；
- CLI Graph：完整的多 Agent 编排实验路径。

准确地描述边界，远比把所有代码都包装成“全自动 Agent”更专业。

## 12. LLM、Function Calling、MCP 格式与结构化输出

### 12.1 LLM 输出为什么不能直接执行

大模型可能返回不完整 JSON、编造素材 ID、给出超出时长的镜头、调用不该调用的工具。正确流程是：

```text
LLM 输出
  → JSON 解析
  → Schema 校验（字段、类型、范围）
  → 业务校验（素材存在且属于当前项目、状态允许）
  → 执行/保存
```

`VideoScheme` 的核心价值不是“保存一个 JSON”，而是把不确定的自然语言计划收敛为前端可编辑、渲染器可消费、评测可追踪的中间表示（IR）。

### 12.2 Function Calling 是什么

Function Calling 指模型不直接只输出自然语言，而是选择一个工具名并给出结构化参数。例如：

```json
{
  "name": "inspect_material",
  "arguments": {"material_id": 42}
}
```

程序再校验参数并真正执行函数。它的价值是将“模型负责决策”与“程序负责可靠执行”分开。

当前项目已经实现角色化工具注册、参数 Schema 和动态派发能力，但主 Web 和主 Graph 流程大多直接调用专家方法，动态工具循环尚未作为主链路运行。因此面试应该说“实现了可接入的工具契约和校验层”，不能说“所有主链路都由模型自主 Function Calling 驱动”。

### 12.3 MCP 兼容格式不等于完整 MCP 接入

项目工具采用 `name / description / inputSchema` 的 MCP Tool 定义兼容格式：

- `name`：工具唯一名称；
- `description`：让模型/调用方理解工具用途和边界；
- `inputSchema`：基于 JSON Schema 的输入参数约束。

它带来统一注册、工具白名单和参数校验的价值。

但完整 MCP 协议还包括 Client/Server、传输层、能力发现、调用消息和生命周期管理。当前没有独立 MCP Server 与 MCP Client 通信，所以准确表述是 **“MCP Tool 定义格式兼容”**，而不是“已完整接入 MCP 协议生态”。

### 12.4 Tool Scoping：为什么每个 Agent 不该拥有全部工具

Tool Scoping 是按角色授予最小必要工具集。例如视频分析 Agent 不应该拥有删除项目或最终渲染工具。这样能：

- 缩小模型误调用的影响范围；
- 让提示词和调试更简单；
- 明确能力边界，利于权限审计和测试。

这和传统后端的最小权限原则是一致的。

## 13. 多模态、Gene、Memory、Skill 与 `VideoScheme`

### 13.1 多模态分析在做什么

参考 Vlog 不是只有文字。系统将多种信号组合起来：

- 镜头切分和时间轴：什么时候转场、每段多长；
- VLM 画面分析：风景、人物、动作、构图、镜头功能；
- Whisper 转写：旁白、口播、字幕语义；
- 音频信息：节奏、情绪和能量变化。

目的不是复制具体画面，而是抽象为可迁移的结构：开头 Hook、信息铺垫、高潮、收束、镜头节奏与情绪曲线。

### 13.2 Gene、Memory、Skill 三者怎么区分

| 名称 | 本质 | 生命周期 | 项目例子 |
|---|---|---|---|
| Gene | 本次参考视频提取的结构基因 | 和参考片绑定，可复用 | Hook 位置、镜头功能序列、节奏曲线 |
| Working Memory | 一次 Agent 工作流的共享上下文 | 一次运行期间 | `ViralEngineState` 中的库存、方案、反馈 |
| Skill | 跨任务可复用的剪辑经验/规则 | 可长期沉淀 | Hook 模板、转场规则、字幕包装策略 |

Skill 不等于 RAG。RAG 常指按查询从外部知识库检索资料；这里的 Skill 更接近带适用条件的可复用剪辑策略。当前以规则路由 Markdown Skill 为主，不应说已有向量数据库检索，除非后续真实接入。

### 13.3 `VideoScheme` 为什么是全链路的核心契约

`VideoScheme` 连接：

```text
分析结果 → Planner → 前端分镜编辑 → Reviewer → Renderer → 成片评测
```

它通常表达标题、目标时长、镜头顺序、每镜素材引用、字幕、转场、情绪、包装、BGM、Gene/Skill 引用等。

没有它，Planner 的自然语言输出很难稳定地被前端和渲染器理解；有了它，就能对每镜时长、素材存在性、总时长、字幕和转场做确定性校验，也能将评测问题定位到具体镜头。

## 14. 渲染与容错：从计划到 MP4 中间会出什么错

### 14.1 规划与执行的“语义鸿沟”

Planner 说的是创作意图：“第 1 镜用快速 Hook、第 3 镜配旁白、高潮处加快节奏”。Renderer/Assembler 必须把它落成技术细节：素材文件在哪、截取何处、字幕如何布局、动画何时开始、Remotion composition 怎样配置、最终如何编码。

因此规划与渲染不能混成同一个模糊步骤。分开后可以定位：是方案本身不合理，还是渲染实现失败。

### 14.2 常见失败类型和处理思路

| 失败类型 | 例子 | 合理处理 |
|---|---|---|
| LLM 格式错误 | JSON 截断、字段缺失 | 解析失败、重试或明确失败，不直接执行 |
| 业务约束错误 | 素材 ID 不存在、总时长超限 | 校验后拒绝/修正/要求重新规划 |
| 素材缺口 | 用户没有匹配“开场航拍”素材 | 找功能相近替代、调整方案、标记缺口 |
| 渲染异常 | 路径错误、组件异常、编码失败 | 记录命令和日志、失败报告、引擎侧尝试基础回退 |
| 成片技术异常 | 黑屏、无音轨、不可解码 | FFprobe/FFmpeg 检查，标记质量失败 |

容错的目标是提高“产生可诊断结果”的概率，不是承诺任何情况下质量不下降。基础拼接回退通常会牺牲转场、字幕或视觉包装复杂度。

## 15. 评测：不能只问“视频好不好看”

### 15.1 三类评测对象

| 评测层 | 评测对象 | 解决的问题 |
|---|---|---|
| 方案 Reviewer | `VideoScheme`、Gene、素材库存 | 方案是否保留结构、是否适配现有素材 |
| 成片检查 | 已生成 MP4 | 是否可解码、时长/音轨正常、是否疑似黑屏或静帧 |
| 运行评测 | 日志、阶段产物、模型调用记录 | 流程是否真的完成、哪里失败、是否使用了 mock |

### 15.2 10 维 Reviewer 评的是方案，不是最终画质

方案 Reviewer 关注 `structure_fidelity`、`hook_appeal`、`content_adaptation`、`rhythm`、`emotion_coherence`、`gap_filling_quality`、`packaging_consistency`、`completeness`、`subtitle_quality`、`material_coverage` 等维度。

它回答的是：“这个分镜方案是否像一个合理的爆款结构迁移方案？”而不是：“最终 MP4 是否没有黑屏、画面是否清晰？”

### 15.3 成片质量如何检查

渲染后可分层检查：

1. FFprobe 检查流、时长、编码、音轨；
2. FFmpeg 完整解码，确认媒体基本可读；
3. OpenCV 抽样检查黑屏/静帧等技术风险；
4. 按分镜抽帧交给 VLM，检查画面是否大致符合分镜意图；
5. 输出带秒级证据的诊断报告，便于人工复核。

抽帧视觉检查不是“逐帧理解整条视频”。它可发现代表性问题，却可能漏掉短暂问题，也可能把刻意的黑场转场误报为异常。面试中要清楚说明这种边界。

### 15.4 `score` 与 `success` 不一样

- `score`：诊断或对比用的评分；
- `success`：是否通过关键运行条件和阶段校验。

高分不等于任务必然成功，低分也不一定意味着文件无法播放。当前视觉分数和部分覆盖率更适合做诊断指标，尚未经过大规模人工标注校准，因此不宜作为绝对硬门槛来吹嘘。

## 16. 一个面试官最喜欢追问的完整例子

### 问：用户点“生成”后，系统内部发生了什么？

推荐按如下顺序回答：

> 用户先在 React 前端创建项目并上传参考视频、用户素材。前端用 HTTP REST 调用 FastAPI，后端从 JWT 获取用户身份，校验项目归属和上传内容后，将元数据写入 SQLite，将大文件落到任务目录。创建端到端任务时，后端不在 HTTP 请求里同步等待视频分析和渲染，而是创建 `Task` 记录并交给进程内 `asyncio.Queue` 的 worker。worker 调用分析和规划脚本：提取参考视频的镜头、视觉、语音与节奏结构，分析用户素材，并生成结构化 `VideoScheme` 草案。
>
> 草案生成后任务进入 `awaiting_confirmation`，前端通过任务 WebSocket 接收进度，同时仍可用 HTTP 拉取任务事实状态。用户在线修改分镜时，后端会校验素材归属、时长等规则，并通过 revision 避免旧版本覆盖新版本。用户确认后才执行 Remotion 渲染，随后用 FFprobe/FFmpeg 和抽帧视觉检查生成成片评测报告。这样将不确定的模型规划收敛为可编辑、可校验的中间表示，并把昂贵渲染放在人工确认之后。

若继续追问多 Agent，再补充：完整 LangGraph CLI 入口中以 Supervisor 和 7 个专家节点管理分析、素材、规划、渲染策略、补全、合成和审核；当前 Web 主链路为支持人工确认，采用分阶段脚本而非每次完整跑图。

## 18. 最终面试回答总结（约 90 秒）

> 这个项目是一个面向旅行 Vlog 的可编辑视频生成系统。前端用 React 提供项目、素材、任务和分镜编辑界面；后端用 FastAPI 管理认证、权限、任务状态和媒体资源。用户上传参考视频与自己的素材后，后端把用户、项目、任务等小型结构化数据存入 SQLite，把视频、图片、分镜 JSON 和 MP4 放在任务文件目录。由于视频分析和渲染耗时较长，创建任务接口会快速返回任务 ID，后台用单进程 `asyncio.Queue` 和 worker 顺序执行流程，进度写入数据库并通过 WebSocket 推到前端；HTTP 仍用于创建、查询和编辑等业务操作。
>
> AI 侧先通过镜头时间轴、VLM 和 Whisper 分析参考片结构，再分析用户素材，生成 `VideoScheme`。它是规划、前端编辑、审核和渲染共用的结构化中间表示，解决了 LLM 自由文本不稳定的问题。独立 CLI 的 LangGraph 路径里使用 Supervisor 加 7 个专职 Agent，通过 `ViralEngineState` 传递共享工作记忆；但当前 Web 为支持用户确认，采用分阶段脚本编排而不是每个任务完整运行图。最终渲染以 Remotion 为主，后续进行方案 Reviewer、MP4 技术检查和抽帧视觉检查。当前队列是单进程内存队列、WebSocket 仍待补握手鉴权，这些是我会继续向持久队列、多 worker 和更完整实时安全演进的方向。
